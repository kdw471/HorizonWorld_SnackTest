## 1. 데이터 개요

| 항목 | 값 |
|---|---|
| 필드 테이블 | 60판 (난이도 1~6, 각 10판) |
| 오브젝트 테이블 | 18행 (건전지 8색 + 블랙 건전지 8색 + 케이스 + 덮개) |
| 케이스 | 8개, 각 4칸 |

### 1.1 CSV 구조

| 컬럼 | 뜻 |
|---|---|
| `bCase1` ~ `bCase8` | 케이스 활성화 여부 (`1` / `0`) |
| `sA1` ~ `sD8` | 8개 케이스 × 4칸. **열 = 케이스 번호, 행 A~D = 칸 위치** |

`#PUZCategory` / `#Difficulty` / `#Order` 컬럼도 함께 들어 있어 인덱스 규칙을 교차 검증할 수 있다.

### 1.2 행 방향 — A가 최상단

CSV 의 `A → D` 는 **위에서 아래** 순서다. 구현 쪽 `BatteryCase.batteries` 는 **아래 → 위** 순서라 뒤집어 넣는다.

방향을 확정한 근거: 기획서 §7 은 블랙(미지) 건전지가 **최상단에 올 수 없다**고 못박고 있다.
A를 최상단으로 보면 위반 **0건**, D를 최상단으로 보면 위반 **125건**이다.

### 1.3 오브젝트 ID 규칙

```
4 2 0 0 2 0 5 0 1 3
└┬┘ │ └┬┘ └┬┘ └─┬─┘
 42 0  02  05   013
 │  │   │   │    └ 일련번호
 │  │   │   └────── 색상 01 R / 02 O / 03 Y / 04 G / 05 B / 06 I / 07 V / 08 P
 │  │   └────────── 유형 01 일반 건전지 / 02 블랙(미지) 건전지 / 00 케이스·덮개
 │  └────────────── 미사용
 └───────────────── 오브젝트 데이터 구분자
```

블랙 건전지(유형 02)는 **실제 색을 그대로 들고 있는** 별도 ID다.
즉 `4200205013` 은 "블랙으로 가려져 있지만 실제로는 B(파랑)인 건전지"다.
구현 쪽 `Battery { color, isRevealed }` 와 1:1로 대응한다.

### 1.4 난이도 곡선 (실측)

| 난이도 | 판 수 | 활성 케이스 | 채워진 케이스 | 여분(빈) 케이스 | 색 수 | 블랙 건전지 |
|---|---|---|---|---|---|---|
| 1 | 10 | 4 | 2 | 2 | 2 | 0 |
| 2 | 10 | 5 | 3 | 2 | 3 | 0 |
| 3 | 10 | 6 | 4 | 2 | 2~4 | 0 |
| 4 | 10 | 7~8 | 5~6 | 2 | 3~6 | 0 |
| 5 | 10 | 7 | 5~6 | 1~2 | 5~6 | 15~18 |
| 6 | 10 | 8 | 7 | 1 | 4~7 | 21 |

블랙 건전지는 **난이도 5부터** 등장한다. D6 은 채워진 케이스 7개 × 각 3개 = 21개로,
케이스마다 최상단 1개만 보이고 나머지 3개가 전부 가려져 있다.

## 2. 기획서와 데이터의 대조

### 2.1 데이터가 기획서와 정확히 일치하는 항목 (검증 완료, 위반 0건)

- 케이스는 항상 **비어 있거나 정확히 4개로 가득** 차 있다 (중간에 빈 칸이 뚫린 케이스 0건).
- 건전지가 들어 있는 케이스는 **반드시 활성 상태**다 (§3).
- **여분(빈) 활성 케이스가 항상 1~2개** 있다 (§4 "최소 1개, 최대 6개").
- 블랙 건전지가 **최상단에 노출된 채 시작하는 경우가 없다** (§7).
- 모든 색의 건전지 개수가 **4의 배수**다 — 즉 원리적으로 정렬을 끝낼 수 있다.
- 시작부터 이미 클리어 상태인 판이 없다.

### 2.2 기획서와 데이터가 어긋나는 항목

| # | 기획서 / 구현 | 데이터 | 처리 |
|---|---|---|---|
| 1 | 구현의 클리어 판정이 **"같은 색이 두 케이스에 나뉘어 있으면 미완성"** 으로 되어 있었다 | 한 색을 **8개**(케이스 2개 분량) 쓰는 판이 **13개** | 기획서 §2·§4 어디에도 색-케이스 1:1 제약이 없다. 판정을 "건전지가 든 모든 케이스가 같은 색으로 가득 찼는가"로 고쳤다. 안 고치면 그 13판은 **영원히 클리어 불가**였다 |
| 2 | 검증기가 색상별 개수를 **정확히 4개**로 요구 | 위와 같은 이유로 8개인 색이 존재 | **4의 배수**면 통과하도록 완화 |
| 3 | §5 건전지 색상 **10가지** | 실제로는 **8색** (R O Y G B I V P) | 구현의 `EBatteryColor` 10종은 그대로 두고, 기획 8색을 그중 8개 슬롯에 대응시켰다. 인디고(I)→`CYAN`, 바이올렛(V)→`PURPLE` 로 넣었고 `BROWN`·`GRAY` 는 기획 데이터에서 쓰이지 않는다. 실제로 보이는 색은 오브젝트 테이블의 메쉬가 정하므로 enum 값은 식별자 역할만 한다 |
| 4 | 난이도 1~5 전제 | 난이도 **6까지** 존재 | 난이도 테이블에 D6 추가 (제한시간 270초 / 색 7종 / 여분 케이스 1개 / 블랙 3개) |

### 2.3 CSV 자체의 흠

- 3행(한글 라벨)에 **오타**가 있다: `A7 좌표` 가 두 번(A7·A8 자리), `B2 좌표` 가 두 번(B1·B2 자리),
  `B7`·`C7`·`D7` 도 같은 식으로 중복돼 있다. 키 행(2행)의 `sA8`, `sB1` 등은 정상이므로 파싱에는 영향이 없다.
- 색상 01(R)의 메쉬 경로가 `SM_NPUZ_03_Battery_Black` 이다. 설명은 `건전지_R` 이므로
  빨강 메쉬가 아직 없어 임시로 검정 메쉬를 물려 둔 것으로 보인다. 리소스 확인이 필요하다.

## 3. 구현 변경 내역

### 3.1 새 파일

| 파일 | 내용 |
|---|---|
| `ColorSort_FieldData.ts` | **자동 생성.** CSV 60판 + 오브젝트 18행 (약 11KB) |
| `Documents/Tools/build_colorsort.py` | NPUZ_03 → `ColorSort_FieldData.ts` 변환기. 스택 뒤집기, 구멍·활성 여부·색상 배수·블랙 노출 검사를 함께 수행 |

```
8000306010|R?O?B?I;I?Y?G?V;V?R?O?B;B?I?Y?G;G?V?R?O;O?B?I?Y;Y?G?V?R;.
   인덱스  |                        케이스 1~8

  케이스  '-' 비활성 / '.' 활성 빈 케이스(여분) / 그 외는 아래→위 색 문자열
  색      R O Y G B I V P  (뒤에 '?' 가 붙으면 블랙(미지) 건전지)
```

`R?O?B?I` = 바닥부터 R(가려짐) → O(가려짐) → B(가려짐) → I(보임). 최상단만 공개된 상태다.

### 3.2 수정한 파일

| 파일 | 변경 |
|---|---|
| `ColorSort_Board.ts` | `isSolved()` 에서 "같은 색이 두 케이스에 있으면 미완성" 제약 제거 (§2.2-1) |
| `ColorSort_LevelGenerator.ts` | 색상별 개수 검증을 "정확히 4개" → "4의 배수" 로 완화 |
| `ColorSort_DataTables.ts` | CSV 필드 테이블을 기본값으로 사용, CSV 오브젝트 테이블(실제 메쉬 경로) 병합, 난이도 6 추가 |
| `ColorSort_Session.ts` | 한 퀘스트 안에서 같은 판이 다시 나오지 않도록 `_usedPuzzleIds` 추가 |
| `ColorSort_Tests.ts` | CSV 테이블 검증 테스트 추가 (배치 규칙 / 시작 클리어 / 전판 해 존재 / 난이도 커버리지) |

이 퍼즐은 원래 `DEFAULT_COLOR_SORT_FIELD_TABLE` 이 **빈 배열**이라 전적으로 절차적 생성기로 돌고 있었다.
이제 난이도 1~6 전부 기획 판이 먼저 쓰이고, 생성기는 폴백으로만 남는다.
