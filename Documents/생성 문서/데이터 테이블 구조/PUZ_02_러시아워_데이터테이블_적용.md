## 1. 데이터 개요

| 항목 | 값 |
|---|---|
| 필드 테이블 | 53판 (난이도 1~6) |
| 오브젝트 테이블 | 23행 |
| 보드 | 7×7 (기획서상 9×9 중 중앙 7×7) |

`NPUZ_02_FieldData.csv` 는 다른 퍼즐과 달리 `#PUZCategory` / `#Difficulty` / `#Order` 컬럼을
따로 들고 있어서, **인덱스 10자리 규칙(80 + 0 + 퍼즐2 + 난이도2 + 순서3)** 을 교차 검증할 수 있었다.
이 규칙은 PUZ_01~08 전체에 그대로 적용된다.

### 1.1 오브젝트 ID 규칙

```
4 1 2 2 1 2 0 0 1 0
└┬┘ │ │ │ │ │ └─┬─┘
 41 2 2 1 2 0   010
 │  │ │ │ │ │    └ 일련번호
 │  │ │ │ │ └────── 색상  1 빨강 / 2 파랑 / 0 무색
 │  │ │ │ └──────── 머리  1 U / 2 D / 3 L / 4 R / 0 없음
 │  │ │ └────────── 축    1 세로 / 2 가로 / 3 없음(1x1) / 0 없음
 │  │ └──────────── 길이  1~4
 │  └────────────── 유형  1 USB(목표) / 2 방해 블록 / 3 도착 포인트
 └───────────────── 오브젝트 데이터 구분자
```

| 유형 | 종류 | 개수 | 기획서 대응 |
|---|---|---|---|
| 1 | USB 목표 오브젝트 (1×2, 4방향 × 2색) | 8 | §5.1 |
| 2 | 방해 블록 (1×1, 2×1·V/H, 3×1·V/H, 4×1·V/H) | 7 | §5.2 |
| 3 | 도착 포인트 (4방향 × 2색) | 8 | §4 |

### 1.2 CSV 좌표 표기법 — 머리 칸 앵커

**이 데이터의 가장 중요한 해석 포인트다.** 길이 2~4짜리 오브젝트도 CSV 에는 **칸 하나에만** 적혀 있고,
몸통은 **머리 방향의 반대쪽으로** 뻗는다.

```
E4 칸에 4123120012 (길이 3, 세로, 머리 D)  →  C4, D4, E4 세 칸 점유 (머리는 E4)
```

53판 전체를 이 규칙으로 펼쳤을 때 **필드 이탈 0건, 겹침 0건**이었다.
반대 가설(좌측·상단 앵커)로 펼치면 이탈 228건 / 겹침 139건 / 52판 파손이므로, 머리 칸 앵커가 확정이다.

구현 쪽 좌표는 기획서 §7 대로 **좌측·상단 칸 기준**이라, 변환기가 이 차이를 흡수한다.

## 2. 기획서와 데이터의 대조

### 2.1 데이터가 기획서와 정확히 일치하는 항목 (검증 완료, 위반 0건)

- 모든 목표 USB 는 같은 색 도착 포인트와 **동일 선상**에 있다 (§5.1).
- **§6 [금지] 목표와 같은 이동 축을 가진 방해물이 목표–도착 지점 사이에 놓이지 않는다** — 53판 전부 위반 0건.
- 목표 개수는 최대 2개, 도착 포인트도 최대 2곳 (§4 / §5.1). 색은 항상 짝이 맞는다.
- 시작부터 이미 도착해 있는 목표는 없다.
- 오브젝트 길이는 1~4 (§5.2), 1×1 만 전 방향 이동.

### 2.2 기획서와 데이터가 어긋나는 항목

| # | 기획서 | 데이터 | 처리 |
|---|---|---|---|
| 1 | §4 도착 포인트는 **9×9 테두리 링**(유저에게 보이지 않는 공간)에 있다 | 7×7 안쪽 **가장자리 칸**에 오브젝트로 배치돼 있다 | 도달 판정을 "목표 앞머리가 도착 포인트 칸에 맞닿음" 하나로 통일했다. 링에 있을 때와 결과가 완전히 같아 기존 생성기 판은 그대로 동작한다 (아래 3.3) |
| 2 | §5.1 **난이도 3 이상**부터 목표 2개 | 실제로는 **난이도 5부터** (D5 절반, D6 전부) | 코드의 `MULTI_GOAL_MIN_DIFFICULTY = 3` 은 생성기용 값이라 그대로 뒀다. 기획 판은 데이터대로 나온다 |
| 3 | 난이도 1~5 전제 | 난이도 **6까지** 존재 | 난이도 테이블에 D6 추가 (제한시간 270초 / 3라운드 / 방해물 10~14 / 최소 이동 5~16 — CSV D6 실측에 맞춤) |
| 4 | §6 [필수] 모든 오브젝트는 최소 1칸 이상 움직일 수 있어야 한다 | **53판 중 52판이 위반** (총 301개 오브젝트가 처음부터 끼어 있음) | 기획서가 이 조항을 "**레벨 생성기** 필수 검증 항목"으로 분류하고 있으므로, 검증기에서 생성기 전용 규칙으로 분리했다 (아래 3.4) |
| 5 | §6 [금지] 같은 이동 방향 오브젝트로 한 줄을 가득 채울 수 없다 | 2판 위반 | 위와 같은 처리 (생성기 전용 규칙) |

### 2.3 CSV 자체의 흠

- **퍼즐 번호 오타 2건**: `8000303010`, `8000305001` 두 행은 퍼즐 번호가 `03`(정렬 퍼즐)로 적혀 있다.
  인덱스와 `#PUZCategory` 컬럼이 둘 다 `03`이지만, 내용은 러시아워 오브젝트(`41…`)이고
  이 파일에 들어 있으므로 `02`가 맞다. 난이도(`03`, `05`)와 순서는 정상이라
  변환 결과에는 영향이 없지만, 기획팀이 인덱스로 행을 찾을 때 헷갈릴 수 있다.
- **레벨 `8000206008`**: 도착 포인트 두 개가 `F7`(세로 USB용)과 `G7`(가로 USB용)에 붙어 있다.
  다른 판은 모두 가장자리 칸에 있는데 이 판만 한 칸 안쪽이다. 오타가 아니라, 같은 칸을 두 목표가
  쓸 수 없어서 어쩔 수 없이 어긋나게 놓은 것으로 보인다. §2.2-1 의 도달 판정을 쓰면 이 판도 정상 동작한다.

### 3.3 도달 판정을 일반화한 이유

기존 판정은 "목표가 플레이 공간의 해당 변에 밀착했는가" 였다. 도착 포인트가 링에 있을 때만 성립한다.
새 판정은 **"목표의 앞머리 칸이 도착 포인트 칸에 맞닿았는가"** 하나다.

- 도착 포인트가 링(전체 좌표 0 또는 8)에 있으면 → 변에 밀착한 것과 **결과가 완전히 동일**하다.
  절차적 생성기가 만드는 판의 동작은 바뀌지 않는다.
- 도착 포인트가 7×7 안쪽 칸에 있으면 → 목표가 그 앞 칸까지 와서 꽂힌다.
  꽂히면 기획서 §9 대로 **3칸(USB 2칸 + 포인트 1칸)** 을 점유한다.

### 3.4 §6 검증을 생성기 전용으로 분리한 이유

기획서 §6 의 제목이 "**배치 제약 (레벨 생성기 필수 검증 항목)**" 이다. 즉 이 조항들은
"사람이 만든 판이 반드시 지켜야 할 규칙"이 아니라 "자동 생성이 지켜야 할 품질 기준"이다.
실제로 기획 데이터는 52/53판이 "모든 오브젝트가 1칸 이상 움직일 수 있어야 한다"를 위반한다.
꽉 끼어 있는 조각이 있어야 퍼즐이 어려워지므로, 손으로 만든 판에서는 자연스러운 결과다.

따라서 `validate(board, { enforceGeneratorConstraints: false })` 로 부르면
[금지]·[필수] 두 항목을 건너뛴다. 기본값은 `true` 라 **생성기 동작은 그대로**다.

### 3.5 최소 이동 수를 미리 구해 넣은 이유

필드 테이블에는 `minimumMoves` 항목이 있는데 기획 CSV 에는 이 값이 없다.
변환 시점에 프로젝트의 BFS 솔버로 구해 넣었다 (`rushhour_minmoves.json`).
런타임에 매번 BFS 를 돌리지 않아도 되고, 난이도 튜닝의 근거 자료가 된다.

```bash
# 최소 이동 수 다시 구하기 (필드 데이터를 먼저 생성한 뒤)
npx tsc RushHour_Definitions.ts RushHour_FieldData.ts RushHour_DataTables.ts \
        RushHour_Board.ts RushHour_Solver.ts RushHour_LevelGenerator.ts \
        --outDir <임시폴더> --module commonjs --target ES2020 --baseUrl . --strict --skipLibCheck
# 임시폴더에서 RUSH_HOUR_FIELD_TABLE 을 순회하며 solver.solve(board, {maxStates: 2000000})
# 결과를 Documents/Tools/rushhour_minmoves.json 으로 저장한 뒤 build_rushhour.py 재실행
```
