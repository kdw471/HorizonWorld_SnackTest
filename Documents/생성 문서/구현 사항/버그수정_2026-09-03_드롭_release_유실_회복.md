# 버그수정 2026-09-03 — 떼도 안 놓이고, 한 번 더 터치해야 드롭된다

> 지시: "여전히 터치, 드래그, 드롭시 바로 터치가 종료됨을 인지 못하고 다시 한번 놓고
> 싶은 위치를 터치해야 그제서야 드롭되는 현상"
> 관련 문서: `버그수정_2026-09-02_드래그_놓기_판정_실패.md` (같은 계통의 앞선 수정)

## 1. 증상

오브젝트를 끌고 가서 손을 떼도 **놓이지 않고 잡힌 채 남는다.** 그 뒤 놓고 싶은 위치를
한 번 더 탭하면 **그 탭의 release 시점에야** 드롭이 된다.

앞선 수정(2026-09-02)은 "release 직전에 오는 exit 이 드랍 지점을 지우는" 경우를
고쳤지만, 이번 증상은 그보다 앞 단계다 — **release 이벤트 자체가 오지 않는다.**

## 2. 원인 — 모바일 Pressable 은 요소 밖에서 뗀 release 를 전달하지 않는 경우가 있다

실기 증상을 역산하면 이벤트 흐름이 이렇다.

```
칸 A 에서 집음(onPress) → B 로 끌고 감(onEnter/onExit) → B 에서 손을 뗌
   → release 가 어느 Pressable 에도 오지 않는다        ← 유실
   → 프레젠터의 _press 가 열린 채 남는다 (조각이 잡힌 채)
확인 탭: C 를 다시 터치
   → onPress(C): 단일 터치 강제로 무시됨 (기존 코드)
   → onEnter(C): hover 가 C 로 옮겨 감 (미리보기가 C 로 이동)
   → 탭의 release: 누른 요소와 뗀 요소가 같아 이번에는 전달됨 → 그제서야 C 에 드롭
```

"다시 터치한 위치에 드롭된다" 는 신고 내용과 정확히 일치한다. 즉 `Pressable` 은
**누른 요소 위에서 뗀 release 만** 확실히 전달하고, 드래그로 요소를 벗어난 채 떼면
release 가 어느 요소(전면 뗌 마감 레이어 포함)에도 오지 않는 경우가 있다.

## 3. 고친 방법 — down 겹침을 "앞 터치의 release 유실" 로 보고 그 자리서 마감한다

`PuzzleBoardPresenter.pointerDown()` / `itemDown()` 에서, 누름이 이미 열려 있는데
새 down 이 오면 **무시하는 대신** 앞 누름을 `pointerUp()` 으로 마감한 뒤 새 터치를
받는다. 마감 지점은 앞 드래그에서 **마지막으로 올라가 있던 진짜 칸**(`_lastInsideCell`)
— 즉 손을 뗐던 그 칸이다.

```
끌고 B 에서 뗌 (release 유실) → 아무 곳이나 다시 터치
   → 그 down 이 오는 순간 B 에 즉시 드롭 + 새 터치가 정상 시작
```

3D 시절 터치 라우터(`PuzzleTouchRouter.handleTouchStart`)가 쓰던 것과 같은 회복
규칙이다 — 같은 인덱스의 새 다운 = 이전 터치의 end 유실.

### 단일 터치 강제(PUZ_00 §8.1)와의 관계

예전에는 "조작 중 추가 down 은 완전히 무시" 였다. 그러나 `Pressable` 은 손가락을
구분해 주지 않으므로, **유실된 release 의 회복과 두 번째 손가락 무시를 동시에 만족할
방법이 없다.** "떼면 반드시 놓인다" 가 더 중요한 요구라(모바일 UX 규칙) 회복을 택했다.
두 번째 손가락을 대면 끌던 조각이 현재 위치에 놓이는 것이 새 동작이다 — 드래그가
영구히 붙잡히는 것보다 낫다.

## 4. 남는 한계

release 유실 자체는 플랫폼 동작이라 코드로 없앨 수 없다. 유실이 난 경우 화면에는
조각이 잡힌 채 남아 보이고, **다음 터치가 닿는 순간** 뗐던 칸에 놓인다. 실기에서
여전히 "한 박자 늦게 놓인다" 로 느껴지면, 그때는 Focused Interaction 의 전역 터치
이벤트(`Basics_Input_Screen.onTouchEnd`)를 보드 패널에 병행 구독하는 안을 검토한다
(퍼즐 중 Focused Interaction 진입이 전제라 이번에는 넣지 않았다).
