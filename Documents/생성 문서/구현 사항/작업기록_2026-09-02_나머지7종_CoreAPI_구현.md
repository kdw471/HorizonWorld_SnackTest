# 1. 8종이 공유하는 뼈대

`Switch_CoreAPI` 의 구조를 그대로 복제했다. 일곱 파일 모두 다음이 동일하다.

| 구획 | 내용 |
|---|---|
| `start()` | 서버 인스턴스면 로그만 남기고 종료. 로컬에서만 시스템을 만든다 |
| `constructSystems()` | 테이블 → 이벤트 → 세션 → 프레젠터 → 이벤트 구독 → 프레임 구동 → 허브 등록 |
| `dispose()` | 보드 unmount + 포커스 해제 + 싱글턴 정리 |
| props | `difficulty` / `autoStart` / `seed` / `focusCamera` / `boardCentre` / `cameraObject` / `cameraDistance` / `cameraFov` |
| 공개 API | `startQuestByDifficulty` / `startQuest` / `pause` / `resume` / `abort` |
| `*_READY` | 다른 시스템이 붙을 수 있게 알리는 `EventPublisher` |

**퍼즐마다 다른 것은 두 가지뿐이다** — 격자 규격을 어떻게 잡는가, 그리고 세션 이벤트를
어떤 칸 색으로 번역하는가. 규칙 판정은 어느 파일에도 없다 (PUZ_00 §7.1).

# 2. 퍼즐별 표현 결정

격자가 그대로 있는 퍼즐(연결)은 옮길 것이 없었다. 판단이 필요했던 것은 아래 다섯이다.

## 2.1 색 채우기 — 격자가 아니라 원형 다이얼

18칸짜리 원형 다이얼이라 격자에 얹을 방법이 자명하지 않았다.
전환 작업기록 §6.3 도 "별도 UI 가 필요하다"로 남겨 두었던 항목이다.

**새 UI 를 만들지 않고 5행 × 6열 격자의 테두리를 다이얼로 썼다.**
5×6 격자의 테두리 칸 수는 `2 × (5 + 6) - 4 = 18` 로 §3 의 칸 수와 정확히 일치한다.

```
 0  1  2  3  4  5
17  ·  ·  ·  ·  6
16  ·  ·  ·  ·  7
15  ·  ·  ·  ·  8
14 13 12 11 10  9
```

0번을 좌상단에 두고 시계방향으로 감는다. 안쪽 칸은 그리지 않으므로 눌리지도 않는다.
`PuzzleBoardUI_Panel` 을 한 줄도 고치지 않고 원형 회전을 표현한다.

바늘은 서 있는 칸의 테두리 강조 + 방향 화살표(`>` / `<`)로 나타낸다.
`NEEDLE_SLOT_CHANGED` 는 칸을 **넘어갈 때만** 나오므로, 레벨 로드 시점의 시작 칸은
`dial.getCurrentSlotIndex()` 로 직접 읽는다. 이것을 빠뜨리면 첫 칸을 넘어갈 때까지 바늘이 안 보인다.

## 2.2 정렬 — 한 열 = 한 케이스

모델이 격자가 아니라 케이스 8개의 스택이다 (§3). **열 수 = 케이스 수(8), 행 수 = 용량(4)** 으로 얹었다.
스택은 배열 마지막이 최상단이므로 `row = 용량 - 1 - 스택index` 로 뒤집어 그린다. 위로 쌓이는 그림이 되어
그랩/드랍 위치와 눈에 보이는 위치가 일치한다.

칸 번호에서 열만 꺼내면 곧 케이스 index 이므로 `beginDrag / hoverDrag / endDrag` 에 그대로 넘긴다.
격자 밖에서 손을 떼면 `endDrag(undefined)` 가 되어 §8 의 영역 밖 드랍(리스폰 대기 2초)이 된다.

시작부터 사용할 수 없는 케이스(§3)는 아예 그리지 않는다. 보이지 않는 칸은 눌리지 않으므로
잘못 잡는 경로가 원천적으로 사라진다. 반대로 **빈 자리는 반드시 그린다** — 드랍 대상이기 때문이다.

## 2.3 러시아워 — 테두리 링도 그린다

3D 시절에는 바깥 테두리 한 칸(도착 포인트 구역)을 보이지 않게 두었다. Custom UI 에서는 **그린다.**
결합(§9)이 "슬롯 쪽으로 반 칸 이상 더 끌기"인데, 보이지 않는 칸은 눌리지 않으므로
테두리를 감추면 USB 를 꽂을 방법이 사라진다.

그래서 전체 9×9 를 프레젠터 격자로 쓰고, 세션에는 플레이 로컬 좌표(`full - 1`)를 넘긴다.
테두리를 눌러 얻는 로컬 좌표 `-1` / `7` 은 결합 슬롯 범위 안이라 드래그 컨트롤러가 그대로 받아들인다.

**드래그 중 미리보기를 넣었다.** 보드의 실제 좌표는 손을 뗄 때 스냅되면서 바뀌므로(§7),
그 사이에 아무 변화가 없으면 무엇을 끌고 있는지 알 수 없다. `updateDrag()` 가 돌려주는 연속 좌표를
반올림해 그 자리에 미리 그린다. 컨트롤러가 이미 이동 가능 범위로 잘라 주므로(§8 경계 고정)
미리보기가 다른 오브젝트와 겹치지 않는다.

나란히 붙은 방해 오브젝트가 한 덩어리로 보이지 않도록, 방해물 색은 id 해시로 고른다.

## 2.4 레이저 — 인벤토리를 본 격자 안에 둔다

이 퍼즐만 필드 밖에 인벤토리가 있다 (§3 3.2). **보조 격자(`side`)는 표시 전용이라 누를 수 없으므로**
인벤토리도 본 격자에 넣어야 했다.

```
col  0 1 2 3 4 5 6   7    8
     └─ 전체 7×7 ─┘  여백  인벤토리 (행마다 한 슬롯)
```

7열 + 여백 1열 + 인벤토리 1열 = 9열로 `PUZZLE_BOARD_MAX_COLS` 안에 들어간다.
여백 열은 그리지 않으므로 눌리지 않고, 보드와 인벤토리가 붙어 보이지도 않는다.
인벤토리 슬롯은 행 수만큼 7개다 — 난이도 표의 최대 소요 슬롯이 5개이므로 충분하지만,
레벨의 인벤토리가 7개를 넘으면 **집을 수 없는 크리스탈이 생기므로 경고를 남긴다.**

좌표계가 둘이라는 점이 이 퍼즐의 함정이다. 기믹과 광선은 전체 7×7, 드래그 API 는 중앙 5×5 로컬이다.
배치 영역 밖(테두리·여백·인벤토리·격자 밖)으로 끌면 로컬 좌표 `(-1, -1)` 을 넘겨,
컨트롤러가 "영역 밖 드랍"으로 판정해 인벤토리로 돌려보내게 했다 (§3 3.3).

광선은 `BEAM_UPDATED` 의 구간을 방향 델타로 한 칸씩 걸어가며 옅게 칠한다.
칠하는 순서는 **바탕 → 광선 → 오브젝트 → 인벤토리**다. 광선을 오브젝트보다 먼저 칠해야
발사체·수신체가 광선에 가려지지 않는다.

## 2.5 슬라이드 / 카드 맞추기 — 격자 크기가 레벨마다 바뀐다

슬라이드는 §11 `iDivideNum` 이 3 또는 4, 카드 맞추기는 §8 `iTileArrayX/Y` 가 3×3 ~ 5×5 다.
스위치(항상 5×5)와 달리 `LEVEL_LOADED` 에서 `presenter.resetLayout()` 으로 격자를 갈아 끼운다.
`resetLayout()` 은 칸 내용을 전부 초기화하므로 곧바로 다시 칠해야 한다.

슬라이드의 조각 색은 **완성 위치**에서 뽑는다. 다 맞추면 좌상 → 우하 그라데이션이 매끄럽게
이어지고 어긋난 조각은 색이 튄다. 실제 이미지 텍스처가 들어오면 `getTileColor()` 하나만 바꾸면 된다.

카드 맞추기는 §6 의 상태 전이를 그대로 색으로 옮겼다 (검정 → 파랑 → 녹색, 폭탄은 붉은색).
활성화된 칸에만 오브젝트 이름 앞 세 글자를 적는다 — 뒷면에 적으면 기억력 퍼즐이 성립하지 않는다.

# 3. 연결 퍼즐의 칸 보간 — 유일한 규칙성 문제

설계 문서 §1.3 이 미리 짚어 둔 항목이다. 보드는 상하좌우로 **한 칸씩** 늘리는 것만 허용하는데
(§5 대각선 연결 불가), 빠른 스와이프는 중간 칸의 `onEnter` 를 건너뛴다.
칸 번호를 그대로 넘기면 경로가 끊긴 채 아무 반응이 없다.

`Flow_CoreAPI.onDrawMove()` 가 직전 칸에서 새 칸까지 **한 칸씩 걸어가며** `moveDraw` 를 부른다.
이동량이 큰 축을 먼저 소진하는데, 실제 손가락이 지나간 자취에 가장 가깝기 때문이다.
중간에 이을 수 없는 칸을 만나면 보드가 거절하므로 경로는 그 자리에서 멈춘다 — 잘못 이어지지 않는다.

러시아워와 레이저는 **절대 위치**를 넘기므로 칸을 건너뛰어도 문제가 없다. 보간이 필요한 것은 연결뿐이다.

## 4.3 배선 검증 (임시 하네스, 28건)

`*_CoreAPI` 자체는 `horizon/core` 를 import 해 Node 에서 실행할 수 없다. 그래서
**각 CoreAPI 가 프레젠터에 건 것과 같은 배선을 재현해** 실제 세션에 물리는 임시 하네스로
"칸 번호 → 세션 좌표" 변환이 통하는지 확인했다. 28건 전부 통과했다.

| 퍼즐 | 확인한 것 |
|---|---|
| 슬라이드 | 탭으로 조각이 실제로 움직인다 |
| 카드 맞추기 | 탭으로 타일이 열린다 |
| 색 채우기 | 링 18칸이 겹치지 않는다 / 링 칸 탭이 세션 터치로 전달되고 방향 반전을 예약한다 |
| 정렬 | 열 단위 드래그로 건전지가 옮겨진다 / 격자 밖 드랍이 리스폰 대기로 가고 2초 뒤 풀린다 |
| 연결 | 솔버 경로를 따라 그리면 완성된다 / **칸을 건너뛴 스와이프도 보간되어 완성된다** |
| 러시아워 | 힌트 이동대로 칸 단위 드래그가 오브젝트를 옮긴다 |
| 레이저 | 인벤토리 → 필드 드래그로 크리스탈이 놓인다 / 격자 밖 드랍이 인벤토리로 회수한다 |

**이 하네스는 저장소에 남기지 않았다.** 배선을 복제한 사본이라 CoreAPI 가 바뀌어도 조용히
통과해 버려 오히려 오해를 부른다. 배선을 고칠 때 같은 방식으로 다시 만들면 된다.

# 5. 남은 작업

1. **인월드 확인** (§4.4). 특히 드래그 중 `onEnter` 수신 여부.
2. **소유권 계층 재작성** — `Puzzle_LocalOwnership` → 리그 풀.
   CoreAPI 8종이 모두 싱글턴(`static instance`)과 전역 레지스트리를 쓰므로,
   플레이어별 인스턴스로 갈 때 이 두 지점을 함께 본다.
3. **리소스 교체.** 지금 칸 색과 한두 글자 라벨은 메시·텍스처가 없는 상태의 대용이다.
   교체 지점은 파일마다 함수 하나로 모아 두었다
   (`getTileColor` / `getBatteryColor` / `getCrystalLabel` 등).
4. **필드 테이블 사전 채움** — `퍼즐_구현_현황.md` §5.3. 러시아워·레이저는 CoreAPI 가 붙은
   지금부터 런타임 생성기의 프레임 정지가 실제 플레이에 드러난다.
