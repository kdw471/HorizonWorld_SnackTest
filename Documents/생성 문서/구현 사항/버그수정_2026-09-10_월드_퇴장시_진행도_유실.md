# 버그 수정 기록 - 월드를 나가면 Continue 진행도가 사라지는 문제

- **날짜**: 2026-09-10
- **증상**: 레벨을 여러 개 깨도 월드를 나갔다 다시 들어오면 모든 퍼즐의 Continue 가 잠긴다. 같은 세션 안에서는 정상 동작해서 잘 드러나지 않았다.
- **원인**: **Persistent Variables API 는 Local 스크립트에서 쓸 수 없다.** 진행도를 읽고 쓰는 `PuzzleUI_MainPanel` 이 Local 이었다.
- **수정 파일**: `Puzzle_ProgressServer.ts`(신규), `PuzzleUI_PersistentProgress.ts`, `PuzzleUI_Progress.ts`, `PuzzleUI_MainPanel.ts`, `Documents/Tests/PuzzleUI_Tests.ts`
- **에디터 작업 필요**: **있다.** `Puzzle_ProgressServer` 를 붙인 Default 엔티티를 하나 만들어야 실제로 저장된다 (`../가이드/에디터_퍼즐_셋업.md` §4.1)
- **관련 문서**: `../설계/Horizon_실행모드_제약과_규칙.md` §4 (이 제약을 포함한 Local 실행 규칙 전체)

---

## 1. 원인 - 실패해도 죽지 않는 코드가 증상을 감췄다

허브 패널은 진행도를 이렇게 읽었다.

```ts
// PuzzleUI_MainPanel.createProgressTracker() - 예전 코드
if (canUsePersistentStorage(this.world, player, key)) {
    return new PuzzleProgressTracker(new HorizonProgressStorage(this.world, player, key));
}
return new PuzzleProgressTracker(new MemoryProgressStorage());   // ← 언제나 이쪽
```

`PuzzleUI_MainPanel` 의 실행 모드는 **Local** 이다. 플레이어별로 자기 화면을 그려야 하므로
그래야 한다. 그런데 공식 문서가 **Persistent Variables API 는 Default 스크립트에서만
쓸 수 있다**고 못박고 있다 (`../설계/Horizon_실행모드_제약과_규칙.md` §4).

`PuzzleUI_PersistentProgress.ts` 의 읽기·쓰기는 전부 `try/catch` 로 감싸여 있었다. 그래서
호출이 실패해도 예외가 밖으로 나오지 않고 조용히 메모리 저장소로 떨어졌다.
**메모리 저장소는 그 세션 안에서는 완벽하게 동작한다** — 방금 깬 레벨이 그대로 Continue 에
반영되므로 플레이 중에는 아무 이상이 없다. 월드를 나가는 순간에만 드러난다.

> 방어적으로 감싼 것 자체는 옳았다. 변수 그룹이 없는 월드에서도 게임은 돌아야 하기
> 때문이다. **다만 "설정을 안 했다" 와 "구조적으로 불가능하다" 가 같은 로그로 수렴해서**
> 설정 문제로 오래 보였다.

---

## 2. 수정 - 영구 변수 호출만 서버로 옮긴다

순수 계층이 이미 `IPuzzleProgressStorage` 인터페이스 뒤에 저장소를 감추고 있었으므로,
**허브 모델과 화면 코드는 한 줄도 바꾸지 않았다.** 바뀐 것은 그 인터페이스의 구현뿐이다.

```
[Local] MainPanel  --REQUEST(브로드캐스트)-->  [Default] Puzzle_ProgressServer --> persistentStorage
[Local] MainPanel  <--LOADED(그 플레이어에게)-  [Default] Puzzle_ProgressServer
[Local] MainPanel  --SAVE(브로드캐스트)----->  [Default] Puzzle_ProgressServer
```

| 파일 | 무엇이 바뀌었나 |
|---|---|
| `Puzzle_ProgressServer.ts` **(신규)** | Default(서버)에서 도는 컴포넌트. 요청을 받아 읽어 주고, 저장 요청을 검증해서 쓴다 |
| `PuzzleUI_PersistentProgress.ts` | `NetworkEvent` 3종 + 로컬용 `RelayProgressStorage` 추가. `HorizonProgressStorage` 는 **서버 전용**으로 성격이 바뀌었다 |
| `PuzzleUI_Progress.ts` | `PuzzleProgressTracker.hydrate()` 추가. 순수 계층이라 `horizon/core` 의존은 그대로 없다 |
| `PuzzleUI_MainPanel.ts` | 요청·응답 배선과 5초 타임아웃 경고. 영구 변수 API 직접 호출 제거 |

### 2.1 왜 `NetworkEvent` 인가

퍼즐 8종이 쓰는 `*_GameEvents.ts` 는 `Utility_Events.ts` 의 자체 `EventPublisher` 다.
같은 JS 컨텍스트 안에서만 도는 구조라 **실행 모드 경계를 넘지 못한다.**
그래서 이 중계만 플랫폼 이벤트를 쓴다.

| 방향 | 쓰는 것 | 이유 |
|---|---|---|
| Local → 서버 | `sendNetworkBroadcastEvent` | 브로드캐스트는 **호스트(서버)가 받는다.** 패널이 서버 엔티티를 prop 으로 물고 있지 않아도 된다 |
| 서버 → Local | `sendNetworkEvent(player, ...)` | 그 플레이어에게만 간다. 로컬은 `connectNetworkEvent(this.entity.owner.get(), ...)` 로 자기 것만 듣는다 |

### 2.2 읽기가 비동기가 됐다

브리지를 건너 되돌아오므로 **생성자에서 값을 받을 수 없다.** 트래커는 빈 진행도로 시작하고,
응답이 오면 `hydrate()` 로 합친다. 허브는 그 전에도 정상적으로 그려진다 — 예전에도 메모리
저장소로 떨어지면 빈 진행도로 떴으므로 그 경로가 이미 있었다.

```ts
private onProgressLoaded(raw: string): void {
    this.clearProgressWaitTimeout();
    const tracker = this._model?.progress;
    if (tracker === undefined) { return; }
    if (!tracker.hydrate(parseProgressSnapshot(raw))) { return; }   // 바뀐 게 없으면 안 그린다
    this.applyCatalog();
    this.applyDetail();
}
```

### 2.3 기다리는 사이에 깬 판이 응답에 덮이면 안 된다

응답이 오기 전에도 게임은 시작할 수 있고, 그 사이에 한 판을 깨면 `recordCleared()` 가
저장 요청을 보낸다. 그 뒤에 **더 낮은 값을 담은 응답**이 도착할 수 있다.

`hydrate()` 는 퍼즐마다 **큰 쪽을 남기고**, 로컬이 앞서 있으면 병합 결과를 저장소에
되돌려 쓴다. 이것이 이 배선에서 가장 놓치기 쉬운 부분이라 테스트를 따로 뒀다.

### 2.4 서버는 클라이언트가 보낸 문자열을 그대로 쓰지 않는다

`parseProgressSnapshot()` 으로 한 번 거른 뒤 저장한다. 형식이 어긋난 값이나 0 이하의
레벨이 영구 변수에 들어가지 않는다.

## 3. 설정을 빠뜨렸을 때 어떻게 드러나나

**게임은 그대로 돈다.** 진행도만 남지 않고, 어느 단계가 빠졌는지 콘솔이 가른다.

| 로그 | 빠진 것 |
|---|---|
| `[PuzzleProgressServer] Ready. Variable key: "..."` | (정상) 서버 스크립트가 붙었다 |
| `[PuzzleProgressServer] Progress is stored in the persistent variable "..."` | (정상) 변수 그룹까지 읽힌다 |
| `[PuzzleProgressServer] Persistent variable "..." is not usable.` | 변수 그룹이 없다 |
| `[PuzzleHub] No reply from Puzzle_ProgressServer for "..."` (5초 뒤) | **서버 엔티티가 아예 없다** |
| `[PuzzleProgressServer] This entity is owned by a player.` | 그 엔티티를 `Puzzle_LocalOwnership.targets` 에 넣었다 |

마지막 줄이 특히 중요하다. 소유권이 넘어가면 그 스크립트도 Local 이 되어 **고치기 전과
똑같은 자리로 돌아간다.**

## 4. 검증

- 타입 체크 3종 (`--noEmit`, 에디터 제약 재현 `--target ES5 --lib ES2020`, 선언 파일 생성) — **오류 0건**
- Node 테스트 전체 — **1,345 PASS / 0 FAIL** (기존 1,334 + 지연 로드 11건)

새로 넣은 11건은 `Documents/Tests/PuzzleUI_Tests.ts` 의 `testProgressHydration()` 이다.
중계 저장소를 흉내 낸 가짜 저장소로 검증한다.

| 검증 | 내용 |
|---|---|
| 응답 전 상태 | 빈 진행도이고 저장소에 쓰지 않는다 |
| 응답 병합 | 합쳐지고 `true`(다시 그려야 함)를 돌려준다. Continue 레벨도 따라온다 |
| 되돌려 쓰지 않음 | 서버가 준 값을 그대로 서버에 다시 쓰지 않는다 |
| 같은 값 재수신 | `false` — 다시 그리지 않는다 |
| 뒤처진 응답 | 진행도를 되돌리지 않고, 로컬이 앞서므로 저장소에 다시 쓴다 |
| 경합 | 기다리는 사이의 클리어가 살아남고 병합 결과가 저장된다 |
| 빈 응답 / 깨진 문자열 | 아무것도 바꾸지 않고 `false` |

**인월드 검증은 아직이다.** 에디터에 `ProgressServer` 엔티티를 추가한 뒤,
레벨 하나를 깨고 → 월드를 나갔다 → 다시 들어와 Continue 가 남아 있는지 확인해야 최종 확인이 된다.
