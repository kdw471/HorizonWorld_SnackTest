# 작업기록 2026-09-21 — NoesisUI 전환 검증과 보드 패널 1단계

> 이 세션에서 만든 것: `NoesisDragLab_Panel` · `NoesisRushHour_Panel` · `NoesisProbe_Panel` ·
> `NoesisBoard_Panel` · `NoesisMoveLab_Panel` (전부 새 파일, 기존 파일은 손대지 않았다)
> 각 패널의 설명은 `../ScriptDesc/Noesis*.md` 에 있다.

## 한 줄

에디터가 권하던 NoesisUI 로 보드 표현 계층을 옮길 수 있는지 실기로 확인했고, **옮길 수 있다**는
결론과 함께 1단계(프레젠터 계약을 그대로 구독하는 Noesis 보드 패널)까지 만들었다.

## 왜 시작했나

에디터가 Custom UI 작업 중에 "성능을 위해 NoesisUI 를 쓰라" 는 경고를 띄운다. 그런데 기존 UI
스크립트를 NoesisUI gizmo 에 그대로 붙이면 동작하지 않았다. 원인은 단순했다 — **두 기즈모가 화면을
받아들이는 방식이 다르다.**

| | Custom UI | Noesis UI |
|---|---|---|
| 화면 정의 | TypeScript. `initializeUI()` 가 `View`/`Text`/`Pressable` 트리를 반환 | XAML 파일 (WPF 방식). 에셋으로 임포트 |
| 베이스 클래스 | `UIComponent` (`horizon/ui`) | 일반 `Component` + `NoesisGizmo` (`horizon/noesis`) |
| 데이터 연결 | `Binding.set()` — 호출마다 스크립트↔렌더러 브리지를 건넌다 | `gizmo.dataContext` 객체 하나 |
| 렌더링 | 직렬화된 트리를 런타임이 해석 (64kB 한도가 여기서 나온다) | NoesisGUI 네이티브 엔진이 XAML 을 직접 그린다 |
| 레이아웃 | Flexbox | Grid / StackPanel / Canvas / Viewbox |

성능 경고의 실체는 Custom UI 의 바인딩 갱신 비용이다. `UIComponent` 스크립트는 Noesis 가 읽지
않으므로 "붙여도 안 되는" 것이 정상이었다.

## 실기에서 확인된 사실

**이 표가 이 세션의 핵심 산출물이다.** 공식 문서 본문이 열리지 않아 대부분 직접 시험해서 얻었다.

| 항목 | 결과 | 어디서 |
|---|---|---|
| Local 실행 모드 + `Puzzle_LocalOwnership` 에서 동작 | 된다 | 러시아워 샘플 |
| 네이티브 드래그(`MouseDragElementBehavior`), `ConstrainToParentBounds` | 된다. **모바일에서 부드럽다** | DragLab B, 러시아워 |
| 낱개 키의 X/Y TwoWay (`P1X` …) | 된다 (모바일 포함) | 러시아워 |
| **배열 항목 안의 X/Y TwoWay** | **모바일에서 놓은 자리가 돌아오지 않는다** (PC 는 된다) | Probe T4 |
| `CommandParameter` + `ElementName` 으로 루트 크기 전달 | 된다 | 러시아워 |
| 배열 → `ItemsControl` / `DataTemplate` / `DataTrigger` / 항목 안의 함수 = `Command` | 된다 | DragLab A |
| 누른 채 옆 칸으로 밀면 **터치 Enter 이벤트가 온다** | 온다 | DragLab A |
| `PassEventArgsToCommand` 로 **포인터 좌표가 온다**, 스크립트가 Move 마다 위치를 써도 **네이티브만큼 부드럽다** | 그렇다 | MoveLab (09-22) |
| `dataContext` **속성만 바꿔도** 화면이 따라온다 (재대입 불필요) | 된다 | DragLab A, Probe |
| `dataContext` getter 는 **우리가 대입한 객체를 그대로** 돌려준다 | 그렇다 | Probe |
| `'#RRGGBB'` 문자열 → 색, `'Visible'/'Collapsed'` → Visibility | 된다 | Probe T1 |
| `ImageSource` → `Image.Source`, null → 그림 늦게 넣기 | 된다 (Local 에서도) | Probe T2 |
| 81칸 일괄 갱신 중에도 드래그가 부드럽다 | 그렇다 | Probe T3 |
| Viewbox 안에서의 드래그·좌표 환산 | 맞는다 | Probe T5 |
| **Noesis 는 Custom UI 위에 그려지고 입력도 가져간다** | 그렇다 | Probe T6 |
| **첫 대입 때 없던 키는 바인딩되지 않는다** | 그렇다 (`NoesisBindingModel_1` 오류) | 콘솔 |

### 여기서 나온 규칙

1. **쓸 키는 전부 첫 `dataContext` 대입에 넣는다.** 빈 값이라도 넣어 둔다.
2. **갱신은 바뀐 속성만.** 재대입하지 않는다.
3. **조각의 X/Y 는 낱개 키로.** 배열 항목 TwoWay 는 쓰지 않는다.
4. **서버 판별은 소유자가 아니라 `getLocalPlayer()` 로.** (Shared 모드 대비 — 아래)
5. **XAML 은 생성기(`Documents/Tools/build_noesis_*.js`)로 만든다.** 반복 덩어리가 많아 손으로 쓰면 어긋난다.
6. **XAML 과 스크립트는 같이 갱신한다.** 바인딩 키가 어긋나면 `[NOESIS] Binding failed` 가 난다.
7. **패널은 `setLocalEntityVisibility(true)` 로 시작한다.** 숨김 상태가 스크립트를 갈아 끼워도 남는다 (아래).

## 숨긴 gizmo 가 다음 스크립트까지 가린다

이 세션 후반에 **Noesis 패널이 전부, 예전 샘플까지 화면에 뜨지 않았다.** 원인은 XAML 도 스크립트도
아니었다.

`setLocalEntityVisibility(false)` 로 숨긴 gizmo 를 **런타임이 기기별로 기억한다.** 이 기억은 미리보기를
나갔다 들어와도, gizmo 에 붙은 스크립트를 다른 것으로 갈아 끼워도 남는다. `NoesisBoard_Panel` 은
`start()` 에서 한 번, 보드가 내려갈 때 또 한 번 자기를 숨긴다 (허브에 자리를 내주려고 일부러 그런다).
그 뒤 같은 gizmo 에 `NoesisMoveLab_Panel` · `NoesisDragLab_Panel` 을 차례로 붙였는데, 이 패널들은
가시성을 건드리지 않으므로 **숨은 채로 남았다.**

`Player.log` 가 이것을 그대로 보여준다.

| 시각(UTC) | 로그 | 읽는 법 |
|---|---|---|
| 08:23:47 | `[NOESIS] '…/PuzzleBoard.xaml' loaded` | 마지막으로 성공한 XAML 로드 |
| 08:23:50 | `Visibility state successfully changed to False for entity 100003` | **로그 전체의 마지막 가시성 변경.** 다시 True 가 되지 않는다 |
| 이후 | `Allocating Noesis ID Prefix: 8_ … 37_` | 스크립트는 멀쩡히 돌며 `dataContext` 를 계속 잡는다 |
| 이후 | XAML 로드 줄도, 파싱 오류도, 바인딩 오류도 **하나도 없다** | 로드를 실패한 게 아니라 **시도조차 하지 않았다** = 숨어 있다 |

XAML 로드가 실패한 것이라면 오류가 남는다. 아무 줄도 없는데 스크립트만 도는 것이 숨김의 표시다.

**고친 방식** — `NoesisProbe` · `NoesisDragLab` · `NoesisRushHour` · `NoesisMoveLab` 네 패널이 `start()`
에서 `setLocalEntityVisibility(true)` 를 먼저 부르게 했다. 패널마다 자기가 켜고 시작하므로 앞 스크립트가
무엇을 남겼든 상관이 없다. `NoesisBoard_Panel` 의 숨김은 설계대로라 그대로 둔다.

## Shared 실행 모드 (공식 문서)

`developers.meta.com/.../noesis-ui/shared-mode-noesis-scripts`

| 모드 | 스크립트가 도는 곳 | Noesis 에서 |
|---|---|---|
| Default | 마스터 클라이언트 한 곳 | **동작하지 않는다.** `dataContext` 를 설정해도 경고 로그만. (Custom UI 에서는 왕복 약 300ms) |
| Local | 엔티티 소유자의 기기 | 동작한다. 다만 플레이어별 복제와 소유권 이전이 필요하고 문서도 "까다롭다" 고 적는다 |
| **Shared** | **서버 포함 모든 클라이언트에서 동시에** | 권장. 복제·소유권 이전이 필요 없고 클라이언트마다 자기 `dataContext` 를 가진다 |

제약은 하나 — 엔티티가 하나뿐이라 위치·크기 같은 공통 속성은 플레이어별로 바꿀 수 없다. Screen
Overlay 패널에는 문제가 되지 않고, 보이기/숨기기는 `setLocalEntityVisibility()` 로 클라이언트별로 된다.

**이 프로젝트에 미치는 영향.** 기존 서버 가드(`entity.owner.get() === getServerPlayer()`)는 Shared 에서
소유자가 언제나 서버라 **모든 클라이언트를 막아 버린다.** 그래서 새 패널들은 전부
`getLocalPlayer().id === getServerPlayer().id` 로 바꿔 두었다 (Local 에서도 결과가 같다).

아직 모르는 것 둘 — ① Shared 스크립트가 같은 기기의 Local 스크립트와 **같은 JS 컨텍스트**를 쓰는가
(`PuzzleBoardStage` 싱글턴으로 CoreAPI 와 연결되므로 결정적이다) ② Noesis gizmo 가 아닌 엔티티에도
Shared 를 줄 수 있는가. ①이 되면 멀티플레이 구조(엔티티 풀링)가 통째로 단순해진다.

## 레이저 실기에서 고친 두 가지

### 1. 트레이 오브젝트가 너무 작았다

트레이를 한 줄로만 늘어놓았기 때문이다. 기존 Custom UI 는 `PuzzleUI_RelativeLayout.trayGrid()` 가
줄 수(최대 3)를 골라 슬롯이 가장 커지는 배치를 쓴다. 세로로 긴 화면에서 5칸을 한 줄에 놓으면 폭이
먼저 모자라 슬롯이 화면 폭의 9.8% 까지 줄었다.

같은 규칙을 `NoesisBoard_Panel.layoutTray()` 에 옮기고, 미니 격자가 없는 퍼즐은 그 열까지 트레이가
쓰게 했다. 3칸 × 2줄이 되어 17.8% 가 됐다.

### 2. 드롭이 안 되고 매번 원위치로 돌아갔다

**터치의 뗌 이벤트는 손가락 밑의 요소가 아니라 터치가 시작된 요소에서 올라온다.** Custom UI 판을
그대로 본떠 "보조 영역에서 올라온 뗌 = 판 밖에 놓았다" 로 읽었는데, 트레이는 보조 영역 안에 있어서
트레이에서 집은 부품은 **어디에 놓든** 뗌이 보조 영역에서 올라왔다.

고친 방식 — 뗌이 어느 요소에서 왔는지 보지 않는다. 뗌은 "끝났다" 신호로만 쓰고, 놓을 칸은 프레젠터가
Enter/Leave 기록(`_hoverCell` / `_lastInsideCell`)에서 정한다. "판 밖" 판정은 **누른 채 보조 영역에
들어왔을 때**로 옮겼다.

## 열려 있는 것

- **`NoesisMoveLab` 화면이 뜨지 않던 것은 XAML 문제가 아니었다** (아래 "숨긴 gizmo" 를 먼저 읽는다).
  `PassEventArgsToCommand` 와 `TranslateTransform` 바인딩이 지원되는지는 **아직 모른다** — 가려낸 적이
  없기 때문이다. 가리려고 만들어 둔 XAML 세 장(`MoveLabMini` → `MoveLabCanvas` → `MoveLab`)은
  그대로 쓸 수 있다. 이제 가시성을 켜고 순서대로 바꿔 끼우면 된다.
- **1단계를 나머지 7개 퍼즐로 확인**해야 한다 (특히 카드 맞추기 중복 누름, 색 채우기 `ClickMode=Press`,
  스위치 이탈 취소, 숨긴 gizmo 가 입력을 놓아주는지).
- **그림 틴트** — Noesis `Image` 에 multiply 틴트가 없다. 3단계에서 대안을 정한다.
- **Shared 모드 시험** (위 ①②).
- **새 Noesis 스크립트 5개에 주석이 남아 있다.** `ScriptDesc` 규칙대로 걷어내야 하는데,
  `strip_comments.js` 를 그대로 돌리면 손으로 쓴 `Noesis*.md` 를 덮어쓴다. 패널 구성이 정리되면
  문서를 보존한 채 코드 주석만 걷어낸다.

## 참고 — 빠른 월드는 어떻게 만들었을까

사용자가 지목한 `Block Puzzle` 월드(반응이 빠르고 모바일 네이티브 같다)는 제작 방식이 공개돼 있지
않다. 다만 플랫폼 구조상 느려지는 경로가 셋(서버 스크립트 왕복 ~300ms · 엔티티 네트워크 동기화 ·
Custom UI 의 `Binding.set` 브리지)인데, **Noesis + Local/Shared 는 셋 다 지나지 않는다.** 조각 끌기는
네이티브 드래그, 스냅·클리어 연출은 XAML Storyboard, 3D 씬은 거의 비우는 구성이면 일반 모바일
게임과 구조가 같아진다. 우리가 가져올 것은 **스냅·클리어 연출을 Storyboard 로 돌리는 것** (스크립트
비용 0) 이고, 2단계에서 러시아워 스냅부터 시험한다.
