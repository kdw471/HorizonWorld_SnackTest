## §1 제안 2 — 릴리즈 리페인트 코얼레싱 (적용 완료)

제안서의 (a)안(플래그 방식)을 택했다. (b)안(구독에서 리페인트 제거)은 드래그 없이도
같은 이벤트가 나는 경로를 전수 확인해야 해서 보류한 그대로다.

- `onDragEnd` 가 `session.endDrag()` 를 부르기 전에 `_isReleaseCoalescing` 플래그를 세운다.
- `endDrag()` 가 같은 이벤트 턴 안에서 띄우는 세션 이벤트의 구독은 플래그를 보고
  리페인트를 건너뛴다. 로그 등 리페인트 외의 일은 그대로 한다.
- `onDragEnd` 마지막의 1회가 유일한 리페인트가 된다.

| 퍼즐 | 대상 구독 | 릴리즈 전체 리페인트 |
|---|---|---|
| 러시아워 (`RushHour_CoreAPI.ts`) | `PIECE_MOVED`, `USB_DOCKED`, `USB_UNDOCKED` | 최대 3회 → 1회 |
| 레이저 (`Laser_CoreAPI.ts`) | `BEAM_UPDATED` | 2회 → 1회 |

레이저의 마무리 1회는 `session.lastTrace` 로 그린다 - `endDrag()` 안의 `refreshBeams()` 가
이벤트를 띄우기 전에 `lastTrace` 를 갱신해 두므로, 건너뛴 이벤트와 같은 광선이 그려진다.

## §2 제안 3 — 릴리즈에도 더티 필터 (러시아워만 적용)

릴리즈 확정에서 실제로 바뀔 수 있는 칸만 기록한다 (`collectReleaseDirtyCells`).

- 원래 자리 발자국 (실루엣이 꺼진다)
- 미리보기 자리 발자국 (확정 본체로 바뀐다) + 스냅 확정 자리 발자국 (같아야 하지만 별도 수집)
- 이동 축의 길 (PATH 강조가 꺼진다) - `forEachDragPathCell` 로
  `applyDragPathVisuals` 와 **같은 범위 계산을 공유**해 어긋나지 않게 했다.

더티 수집은 `endDrag()` **전에** 한다. 길 범위(`getMaxSteps`)가 이동 확정 뒤에는 달라지기
때문이다. 확정 자리 발자국만 `endDrag()` 뒤에 추가한다.

전체 리페인트로 되돌리는 예외:

- **결합/분리** (`USB_DOCKED`/`USB_UNDOCKED` 가 릴리즈 중 발화) - 점유 칸이 2↔3 으로 바뀐다.
  구독 핸들러가 `_didReleaseChangeWholeBoard` 를 세워 알린다.
- 오브젝트를 찾지 못한 경우 (라운드 전환 등으로 보드가 갈린 경우 포함)
- **레이저는 릴리즈 전체 리페인트 유지** - 광선 재계산은 어느 칸이든 바꿀 수 있다 (제안서 명시).

## §3 제안 1 — 드래그 스트림 실험 세팅 (`Puzzle_DragStreamProbe.ts` 신규)

검증할 질문: Screen Overlay(Custom UI 보드) 위의 터치가
`PlayerControls.onFocusedInteractionInput*` 스트림으로도 들어오는가.

### 에디터 세팅

1. 빈 엔티티에 `Puzzle_DragStreamProbe` 를 붙인다. 실행 모드 **Local**.
2. `Puzzle_LocalOwnership` 의 `targets` 에 그 엔티티를 추가한다.
3. Focused Interaction 모드 진입 경로를 하나 고른다.
   - 권장: 퍼즐 CoreAPI 의 `focusCamera` 를 켠다 (실전과 같은 조건)
   - 간편: 프로브의 `autoEnterSeconds` 에 5 등을 준다 (카메라 변경 없이 모드만 진입)
4. 모바일 기기에서 보드를 드래그하며 콘솔을 본다.

### 판독 기준

| 관찰 | 결론 |
|---|---|
| 보드 위 드래그 중 started/moved/ended 로그가 찍힌다 | 제안 1 진행 가능. ended 요약의 avgInterval 이 연속 추종의 입력 해상도 |
| started 만 오거나 아무 로그도 없다 | UI 가 터치를 소비한다. 제안 1 은 칸 단위 폴백 유지 필요 |
| 보드 밖 드래그에서만 로그가 온다 | 같은 결론. 보드 위/밖을 번갈아 그어 경계 확인 |

moved 로그는 250ms 간격으로만 찍되 개수는 전부 세어, ended 에서
`duration / moves / avgInterval` 요약을 남긴다. 실험이 끝나면 컴포넌트를 월드에서 뗀다.

## §3.5 제안 1 본 구현 — 미리 배선 완료, `continuousDrag` prop 으로 대기

실험이 긍정으로 끝나면 **에디터에서 prop 하나만 켜면** 적용되도록 하이브리드 입력을
미리 구현해 두었다. 기본은 꺼짐이라 켜기 전에는 동작이 완전히 기존과 같다.

### 구조 (4개 층)

| 층 | 파일 | 내용 |
|---|---|---|
| 순수 변환 | `PuzzleUI_RelativeLayout.ts` | `screenPointToGridPoint()` - 정규화 화면 좌표(0~1) → 연속 격자 좌표 (정수 = 칸 중심). 패널의 상대 배치(여백 % · 7:3 · 판 96%x94% · 격자 상자 중앙 정렬)를 그대로 복원한다. Node 테스트 8건 추가 |
| 지오메트리 통로 | `PuzzleBoardUI_Presenter.ts` (스테이지), `PuzzleBoardUI_Panel.ts` | 패널이 `resolveLayout()` 에서 확정한 배치+화면 비율을 `PuzzleBoardStage.setScreenGeometry()` 에 실어 둔다 - **패널이 실제로 그린 값 하나만** 진실 |
| 스트림 라우터 | `Puzzle_HorizonBridge.ts` | `PuzzleScreenDragStream` - `onFocusedInteractionInputMoved/Ended` 를 연속 격자 좌표로 바꿔 콜백. `enterPuzzleTouchStream()` / `exitPuzzleTouchStream()` - 카메라를 건드리지 않는 Focused Interaction 모드 진입/이탈 |
| 퍼즐 배선 | `RushHour_CoreAPI.ts`, `Laser_CoreAPI.ts` | `continuousDrag` prop (기본 꺼짐). 잡기는 칸 누름 그대로, 이동·뗌 처리를 `trackDragToLocal()` / `finalizeDrag()` 로 뽑아 칸 경로와 스트림 경로가 합류한다 |

### 폴백 규칙 — 스트림이 실제로 배달한 드래그만 넘겨받는다

Screen Overlay 가 터치를 소비하는 환경에서도 조작이 죽으면 안 된다. 그래서:

- 잡기 성공 시 라우터를 무장(`notifyDragBegan`)만 하고,
  **첫 moved 변환이 성공한 순간부터** `isDriving` 이 된다.
- `isDriving` 인 동안 칸 단위 `onCellMove`/`onCellUp` 은 무시된다 (같은 좌표 이중 주입 방지).
- 스트림이 한 번도 오지 않으면 끝까지 `isDriving === false` 라 기존 칸 단위 경로가
  그대로 동작한다. 그래서 **켜 둔 채 스트림이 안 와도 조작은 살아 있다.**

### 실험 결과 (2026-09-04 기기 확인) — 프로브는 소임을 다해 제거했다

1. **스트림 수신 확인됨** - Screen Overlay 위 터치가 Focused Interaction 스트림으로
   들어온다. `continuousDrag` 를 켜면 오브젝트가 손가락을 따라온다.
2. **`screenPosition` 은 아래가 0** - `Puzzle_HorizonBridge.ts` 의
   `SCREEN_POSITION_Y_IS_TOP_DOWN = false` 로 확정 (변환부가 `1 - y` 로 뒤집는다).

두 미지수가 모두 확정되어 `Puzzle_DragStreamProbe.ts` 는 **삭제**했다. 이후의 온오프
테스트는 `continuousDrag` prop 으로 충분하다. **에디터에 프로브를 붙인 엔티티가
남아 있다면 함께 제거한다** (스크립트가 사라져 참조가 깨진 채 남는다).

### §3.6 칸 안 소수 오프셋(직접 조작) — 시도했다가 **되돌렸다**

기기 확인에서 "조각이 보간되듯 뒤늦게 따라붙는다" 는 체감이 나왔다. 확인해 보니
**보간 코드는 없었다** - 칸 비주얼은 전부 즉시 반영되는 Binding 파생이고,
`Animation.timing` 은 시작 배너 페이드뿐이다. 체감의 정체는 둘의 합이었다.

1. **미리보기가 칸 단위로만 이동** - 연속 좌표를 받아도 반올림해 칸 리페인트로
   그리므로, 빠른 드래그에서 조각이 지나온 칸들을 한 박자 늦게 걸어서 따라간다.
2. **Custom UI 왕복 지연** (플랫폼) - 입력 → 스크립트 → Binding → 네이티브 렌더의
   기본 지연. 스크립트에서 줄일 수 없는 바닥이다.

1번을 없애려고 **반올림하고 남은 소수 위치만큼 발자국 칸을 `transform` 으로 미는**
직접 조작을 구현했다. 자리별 오프셋 Binding(81쌍), 프레임당 1회 플러시, 칸 1/8 양자화,
안 바뀐 축의 `set` 생략까지 단계적으로 눌렀지만 **모바일에서 드래그가 버벅였다.**

**결론: 이 접근은 이 플랫폼에서 성립하지 않는다. 전부 제거했다** (2026-09-04).

기기 A/B 로 확정한 근거 - 스위치 하나로 오프셋 발행만 끈 채 스트림은 유지했더니
버벅임이 사라졌다. 계측(`[DragStats]`)에서 스크립트가 보내는 양은 이미 충분히 적었다
(초당 입력 60회에 오프셋 발행 1~17회, 전체 리페인트는 잡는 순간 1회뿐). 즉 **양이
아니라 갱신 1건당 비용**이 문제였다.

왜 비쌌는지:

- `Binding.set` 하나가 스크립트→클라이언트 직렬화 + 패널 데이터 모델 갱신 +
  그 값에 묶인 노드의 네이티브 재렌더를 전부 태운다.
- 우리 오프셋 층은 칸의 그림 전부(텍스처 `Image`, 회전 걸린 `Text`, 절대 배치
  오버레이)를 감쌌다. 브라우저의 컴포지터 같은 빠른 경로가 없어 transform 변경이
  **텍스처 입힌 서브트리 재렌더**로 처리된 것으로 보인다.
- `AnimatedBinding`/`Animation` 이 따로 있다는 것 자체가 설계 의도를 말해 준다 -
  연속 움직임은 **클라이언트가 보간**하게 하고 스크립트는 목표값을 한 번만 보내라는 뜻이다.
  매 위치를 스크립트가 떠먹이는(per-value push) 방식은 정반대였다.

**남긴 상태:** 조각은 칸 단위로 움직인다. 스트림 입력(연속 좌표 판정·릴리즈 유실 해결)은
그대로라, 칸 전환이 입력 이벤트 해상도로 즉각 일어나고 버벅임이 없다.

**다시 시도한다면** 칸을 미는 대신 **경계를 넘는 순간에만 `AnimatedBinding` 으로
80~100ms ease-out 트윈 1회**를 거는 방식이어야 한다 (제안 4 스냅 트윈). 보간을
클라이언트가 실행하므로 브리지 통행은 경계 통과 횟수로 떨어진다.

### 적용 절차 (남은 것)

1. 나머지 드래그 퍼즐(정렬 `ColorSort_CoreAPI` · 연결 `Flow_CoreAPI`)에도 스트림 배선을
   복사한다 - 잡기 arm + move/up 가드 + `trackDragToLocal`/`finalizeDrag` 분리 + prop.
2. 부드러운 추종이 필요해지면 §3.6 마지막의 **경계 트윈**(제안 4)으로 접근한다 -
   칸을 미는 방식은 이미 기기에서 기각되었으므로 다시 시도하지 않는다.
