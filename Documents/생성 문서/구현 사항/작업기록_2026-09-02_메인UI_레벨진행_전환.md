# 0. 무엇을 했나

게임의 시작점을 **메인 UI 로 옮기고**, 난이도 선택을 **레벨 진행**으로 바꿨다.

```
이전   월드 진입 → autoStart 로 퍼즐이 바로 시작
       퍼즐 선택 → 난이도 버튼 1~6 중 하나 → 시작 (매번 처음부터)

이후   월드 진입 → 메인 UI (퍼즐 8종 격자 2열 × 4행)
       퍼즐 터치 → 그 퍼즐이 화면을 꽉 채움 → Start / Continue / Return (세로 배치)
                     Start    1레벨부터
                     Continue 마지막으로 클리어한 레벨의 다음부터
                     Return   메인 UI 로
```

## 0.1 레벨의 정의

**레벨 하나 = 퀘스트 라운드 하나 = 기획 판(field) 하나.**

난이도 오름차순으로 각 난이도의 판을 순서대로 이어 붙인 것이 그 퍼즐의 레벨 목록이다.

```
레이저 난이도 1 이 3판, 난이도 2 가 20판 이면
  L1..L3   = 난이도 1 의 0..2번 판
  L4..L23  = 난이도 2 의 0..19번 판
```

기존에는 한 퀘스트가 라운드를 2~3판 연달아 돌렸다. 레벨 모드는 **지정한 판 하나를
1라운드로** 연다. 판을 다 깨면 다음 레벨로 넘어가는 형태다.

## 0.2 실제 레벨 수

`buildPuzzleLevelTable()` 을 실제 데이터 테이블에 돌린 결과다.

| 퍼즐 | 레벨 | 난이도별 판 수 |
|---|---|---|
| PUZ_01 레이저 | 75 | 3 / 20 / 21 / 11 / 10 / 10 |
| PUZ_02 러시아워 | 53 | 3 / 10 / 10 / 10 / 10 / 10 |
| PUZ_03 정렬 | 60 | 10 / 10 / 10 / 10 / 10 / 10 |
| PUZ_04 색 채우기 | 164 | 13 / 19 / 27 / 13 / 28 / 64 |
| PUZ_05 연결 | 120 | 20 / 20 / 20 / 20 / 20 / 20 |
| PUZ_06 카드 맞추기 | 32 | 10 / **1** / 10 / **1** / 10 |
| PUZ_07 슬라이드 | 60 | 10 / 10 / 10 / 10 / 10 / 10 |
| PUZ_08 스위치 | 87 | 20 / 23 / 14 / 16 / 14 |
| **합계** | **651** | |

기획 CSV 649판 + 카드 맞추기 난이도 2·4 의 절차적 폴백 2레벨이다. 그 두 난이도는
CSV 행이 비어 있어(`PUZ_00` §5.2 기획 확인 대기) 판이 없으므로, 생성기가 만드는
레벨 하나로 친다. **CSV 가 채워지면 레벨 수가 자동으로 늘어난다** — 코드는 그대로다.

# 1. 새로 만든 파일

| 파일 | 계층 | 역할 |
|---|---|---|
| `PuzzleUI_Progress.ts` | 순수 | 퍼즐별 "마지막 클리어 레벨" 조회·기록, 저장소 인터페이스, 메모리 구현, JSON 직렬화 |
| `PuzzleUI_PersistentProgress.ts` | Horizon | 위 인터페이스를 플레이어 영구 변수에 얹는 구현 |

두 계층을 나눈 이유는 `PuzzleUI_Progress` 를 Node 테스트에서 그대로 돌리기 위해서다
(PUZ_00 §7.1). 진행도 규칙 — 뒤로 물리지 않기, 전부 깬 뒤의 Continue, 깨진 저장값 처리 —
가 전부 순수 계층에 있어 인월드 확인 없이 검증된다.

## 1.1 영구 저장은 "있으면 쓰고 없으면 메모리"

```
HubPanel.initializeUI()
   └ canUsePersistentStorage(world, player, key)
        ├ 쓸 수 있다 → HorizonProgressStorage  (월드를 나가도 유지)
        └ 못 쓴다   → MemoryProgressStorage    (세션 동안만)
```

에디터에서 변수 그룹을 만들지 않아도 게임이 돈다. 어느 쪽으로 붙었는지는 시작 시
콘솔에 찍히므로, "Continue 가 왜 매번 잠겨 있죠" 를 로그만 보고 답할 수 있다.

**퍼즐 8종의 진행도를 String 변수 하나에 JSON 으로 담는다** (`{"LASER":3,"SWITCH":1}`).
변수를 퍼즐마다 나누면 에디터 설정이 8배가 되고 퍼즐이 늘 때마다 설정을 고쳐야 한다.
8종 전부를 담아도 100바이트가 안 된다.

설정 절차는 `../가이드/에디터_퍼즐_셋업.md` §4.1 에 있다.

# 2. 세션 계층 변경 (8개 공통)

**로직은 그대로 두고 "판 하나를 1라운드로 여는 경로" 만 더했다.** 기존
`startQuest()` / `startQuestByDifficulty()` 의 동작은 한 줄도 바뀌지 않았다.

## 2.1 추가된 것

```ts
/** 레벨 하나만 플레이한다 - 메인 UI 의 Start / Continue 경로 */
public startLevel(difficulty: number, fieldOrdinal: number): boolean

/** startQuest / startLevel 의 공통 몸통 */
private beginQuest(quest: <퍼즐>MainTableEntry): boolean

/** 이번 플레이의 라운드 수. 레벨 모드면 1, 아니면 퀘스트 테이블 값 */
private getRoundCount(): number

/** 레벨 모드에서 이번에 쓸 판. 아니면 undefined 를 돌려 기존 무작위 선택으로 넘긴다 */
private resolveLevelField<T>(fields: T[]): T | undefined
```

상태 두 개(`_fieldOrdinal`, `_roundCountOverride`)가 늘었고, `startQuest()` 는 그 둘을
`undefined` 로 비운 뒤 `beginQuest()` 를 부른다. **레벨 모드는 `startLevel()` 로만 들어간다.**

## 2.2 판 선택 경로가 퍼즐마다 셋이었다

8개 세션이 판을 고르는 방식이 세 갈래여서, 각각에 레벨 분기를 넣었다.

| 패턴 | 퍼즐 | 기존 방식 | 레벨 모드 분기 |
|---|---|---|---|
| A | 레이저 · 러시아워 · 정렬 · 색 채우기 · 연결 | `loadLevel()` 에서 `getFieldsForDifficulty()` + `tables.buildLevel()` | 무작위 선택 앞에서 지정 판으로 즉시 반환 |
| B | 스위치 | `pickFieldIndex()` → 생성기의 `fieldIndex` | `pickFieldIndex()` 첫머리에서 지정 판의 `index` 반환 |
| C | 카드 맞추기 · 슬라이드 | 생성기가 내부에서 무작위 선택 | `generate()` 호출에 `fieldIndex` 를 넘김 |

세 패턴 모두 `resolveLevelField()` 라는 같은 헬퍼를 쓴다. **순번이 범위 밖이면
경고를 남기고 기존 무작위 선택으로 떨어진다** — 레벨 테이블이 같은 판 수에서 만들어지므로
실제로는 닿지 않는 방어 경로이고, 라운드를 실패시키는 것보다 낫다.

# 3. 허브 계층 변경

## 3.1 화면 상태

| 이전 | 지금 |
|---|---|
| `DIFFICULTY_SELECT` | `PUZZLE_DETAIL` |

난이도 버튼 최대 6개 + 시작 + 뒤로 (8개 버튼) → **Start / Continue / Return 세 개**로 줄었다.

## 3.2 핸들 인터페이스

| 이전 | 지금 |
|---|---|
| `getDifficulties(): number[]` | `getLevels(): PuzzleLevelRef[]` / `getLevelCount(): number` |
| — | `startLevel(level: number): boolean` (1-based) |
| `startQuestByDifficulty()` | 그대로 (퀘스트 트리거용 경로로 남겨 둠) |

레벨 번호 → (난이도, 판 순번) 변환은 **핸들 안에서 끝난다.** 모델은 레벨 번호만 다루고,
CoreAPI 는 (난이도, 판 순번) 만 받는다.

`probePuzzleDifficulties()` 는 지우지 않았다. `buildPuzzleLevelTable()` 이 같은 탐침을
쓰고 있고, 난이도 목록이 필요한 다른 용도가 생길 수 있다.

## 3.3 모델 액션

| 액션 | 하는 일 |
|---|---|
| `selectPuzzle(id)` | 메인 메뉴 → 상세 화면 |
| `startNewGame()` | 1레벨 시작 |
| `continueGame()` | 마지막 클리어 + 1 레벨 시작. 기록이 없으면 거절 |
| `returnToMenu()` | 상세 → 메인 메뉴 |
| `retry()` | 결과 화면에서 같은 레벨 재시작 |
| `playNextLevel()` | 결과 화면에서 다음 레벨 (이겼고 마지막이 아닐 때만) |
| `backToDetail()` | 결과 → 그 퍼즐의 상세 화면 |
| `quitToMenu()` | 인게임·일시정지·결과 → 메인 메뉴 |

`startNewGame` / `continueGame` / `retry` / `playNextLevel` 은 전부 private `startLevel(n)`
하나를 거친다. 구독 연결, 범위 검사, 동기 실패 처리가 그 한 곳에만 있다.

**진행도는 이겼을 때만 올린다.** 실패와 레벨 생성 실패는 진행도를 건드리지 않는다.

## 3.4 CoreAPI 8종

| 변경 | 내용 |
|---|---|
| `autoStart` 기본값 | `true` → **`false`**. 게임은 메인 UI 에서 시작한다 |
| controls | `startLevel` 추가 |
| 핸들 등록 | `probePuzzleDifficulties(...)` → `buildPuzzleLevelTable(...)` |
| public API | `startLevel(difficulty, fieldOrdinal)` 추가 |

> **기존 월드 주의** — `autoStart` 기본값이 바뀌어도 에디터에 저장된 값은 그대로다.
> 예전에 켜 둔 PuzzleController 는 직접 꺼야 한다.

# 4. UI 레이아웃

## 4.1 메인 메뉴 — 2열 × 4행

퍼즐 버튼 폭을 44% (+ 좌우 여백 2%) 로 두어 한 줄에 둘씩 들어가고, 카탈로그가 8종이므로
정확히 4행이 된다. 버튼마다 **클리어 진행도(`3 / 87`)** 를 한 줄 더 표시한다.

**표시 문자열은 전부 영어다** (§7).

## 4.2 상세 화면 — 세로 3버튼

```
        ┌───────────────────────┐
        │        Switch         │   ← 퍼즐 이름 (40pt)
        │  Turn every key green │   ← 부제
        │  Cleared 3 / 87 levels│   ← 진행도
        │                       │
        │  ┌─────────────────┐  │
        │  │      Start      │  │   1레벨부터
        │  ├─────────────────┤  │
        │  │ Continue · LV 4 │  │   기록 없으면 어둡게 + "No progress"
        │  ├─────────────────┤  │
        │  │     Return      │  │   메인 UI 로
        │  └─────────────────┘  │
        └───────────────────────┘
```

세 버튼의 폭(64%)·높이(11%)·간격(4%)을 같게 두었다. 엄지로 잘못 누르는 일을 줄이기
위해서고, PUZ_00 §8 의 최소 크기(폭 40% / 높이 8%)를 넘긴다.

Continue 는 잠겼을 때도 **누를 수는 있게** 두고 토스트로 이유를 알린다. 눌리지 않는
버튼은 고장으로 오인되기 쉽다.

## 4.3 결과 화면

이겼고 다음 레벨이 남았으면 **"Next Level"** 버튼이 하나 더 나온다 (`_hasNextLevel` 바인딩).
연속 플레이가 상세 화면을 거치지 않고 이어진다.

# 6. 남은 작업

1. **인월드 확인** — 2열×4행 격자와 상세 화면이 모바일 화면비에서 잘리지 않는지.
   특히 상세 화면 세 버튼의 세로 합(11%×3 + 간격 4%×3 = 45%)이 제목·부제·진행도와
   함께 들어가는지.
2. **영구 변수 그룹 생성** — 에디터에서 `PuzzleHub:progress` (String). 하기 전까지는
   진행도가 세션 한정이다 (`../가이드/에디터_퍼즐_셋업.md` §4.1).
3. **카드 맞추기 난이도 2·4·6 CSV** — 채워지면 레벨 수가 32 → 60 근처로 늘어난다.
   기획팀 확인 대기 항목이다 (`기획이슈_사양서_모순과_확인요청.md`).
4. **게임 플로우 계층** — 이번 작업은 "퍼즐 한 판" 의 시작·끝을 정리한 것이다.
   여러 퍼즐을 묶은 "게임 한 판" 은 아직 없다
   (`../설계/2026-09-02_퍼즐_시작흐름과_게임플로우_제안.md` §2).
5. **리그 풀** — 여전히 먼저 들어온 한 명만 플레이할 수 있다
   (`작업기록_2026-09-02_보드_CustomUI_전환.md` §6.2).

| 결과 제목 | 클리어! / 실패 | `Clear!` / `Failed` |
| 결과 상세 | … 남은 시간 0:31 | `… Time left 0:31` |
| 시스템 메뉴 | 일시정지 / 계속하기 / 레벨 재시작 / 메인 복귀 | `Paused` / `Resume` / `Restart Level` / `Return to Main` (2026-09-02 개편 — `작업기록_2026-09-02_재입장과_시스템메뉴.md`) |
| 결과 버튼 | 다음 레벨 / 다시 도전 / 메뉴로 | `Next Level` / `Retry` / `Menu` |
| 토스트 (미등록) | …퍼즐은 준비 중입니다. | `… is not available yet.` |
| 토스트 (시작 실패) | 퍼즐을 시작하지 못했습니다… | `Could not start the puzzle. Please try again.` |
| 토스트 (Continue) | 이어할 기록이 없습니다… | `No saved progress yet. Use Start to begin.` |

## 7.3 그 밖

`Switch_CoreAPI.ts` 의 보조 격자 라벨 `'스위치 영역'` → `'Switch Area'`.
다른 CoreAPI 의 칸 라벨은 원래 기호(`!` `?` `>` `<` `U`)라 손댈 것이 없었다.

`*_DataTables.ts` 의 `questName`(`'스위치 퍼즐 D1'` 등)은 **화면에도 콘솔에도 나가지
않으므로** 그대로 뒀다. 코드 주석과 `Documents/` 문서도 한글 그대로다.

## 7.4 규칙

> **이 프로젝트에서 콘솔과 화면에 나가는 문자열은 전부 영어로 쓴다.**
> 코드 주석과 문서는 한글 그대로 둔다.

# 8. 화면 겹침 — 한 번에 한 패널만 그린다

인월드 확인에서 **레벨을 클리어해도 결과 화면이 보이지 않는** 증상이 나왔다.

## 8.1 원인

BoardPanel 과 HubPanel 은 **서로 다른 Custom UI gizmo** 이고, 둘 다 Screen Overlay 로
화면을 꽉 채우는 불투명 배경을 그린다. **두 gizmo 사이의 z-order 는 코드가 정할 수 없다.**

초판은 퀘스트가 끝나도 보드를 남겨 두었다("결과 화면 뒤로 최종 판이 보인다"). 그래서
BoardPanel 이 위에 그려지는 환경에서는 결과 화면이 그 뒤로 숨고, **배경만이 아니라
Pressable 까지 가려져 Retry / Menu 를 누를 수도 없다.** 일시정지 오버레이도 같은 문제였다.

## 8.2 고친 방식

z-order 를 맞추려 들지 않고, **한 번에 한 패널만 그리게** 해서 순서에 의존하지 않도록 했다.

| 시점 | 보드 | 이유 |
|---|---|---|
| `onLevelLoaded` | `mount()` | 인게임 — 허브는 상단 바만 그린다 (PUZ_00 §8.5) |
| `pause()` | `unmount()` | 일시정지 오버레이에 자리를 내준다 |
| `resume()` | `mount()` | **세션이 실제로 재개됐을 때만** (`session.isActive` 확인) |
| `onQuestEnd` | `unmount()` | 결과 화면에 자리를 내준다 |
| `abort()` / `dispose()` | `unmount()` | 기존 정리 경로 (변경 없음) |

8종 CoreAPI 전부 같은 모양이다 (`unmount` 4곳 / `mount` 2곳).

`retry()` 와 `playNextLevel()` 은 다시 `startLevel()` 을 타므로 `onLevelLoaded` 에서
보드가 자동으로 다시 올라온다.

## 8.3 포기한 것

**"결과 화면 뒤로 최종 판이 보인다"** 는 연출을 버렸다. 결과 화면이 뜨는 순간 보드가 사라진다.
그 연출을 되살리려면 두 패널을 하나의 gizmo 로 합쳐 z-order 를 코드가 쥐어야 하는데,
`initializeUI()` 가 한 번만 불리는 제약 아래서 그 통합은 비용이 크다.

## 8.4 함께 넣은 진단 로그

`PuzzleBoardStage.mount()` 에서 **그릴 패널이 하나도 구독하고 있지 않으면** 경고를 남긴다.
BoardPanel gizmo 가 없거나 소유권이 안 넘어와 서버 인스턴스로 남은 경우를 둘 다 잡는다 —
둘 다 아무 오류 없이 조용히 빈 화면만 나와서 원인을 찾기 어려웠다.

```
[PuzzleBoardStage] A board was mounted but no panel is listening, so nothing will be drawn.
Add a Custom UI gizmo with PuzzleBoardUI_Panel (execution mode Local, Display Mode Screen Overlay)
and put that entity in Puzzle_LocalOwnership targets.
```
