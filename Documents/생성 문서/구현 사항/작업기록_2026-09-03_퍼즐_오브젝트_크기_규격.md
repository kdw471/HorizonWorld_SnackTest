## 1. 무엇이 작았나

세 가지가 겹쳐 있었다. 셋 다 **정사각형 한 변**(`PuzzleBoardGeometry.gridSide`)에서
비롯한다.

| | 예전 | 문제 |
|---|---|---|
| 판 | 정사각형. 한 변 = `min(쓸 수 있는 폭, 본 격자 영역의 높이)` | 가로 화면에서는 언제나 **세로가 한계**라, 폭 2500px 짜리 캔버스에서 판이 741px 였다. 좌우 1600px 이 그냥 비었다 |
| 칸 | 정사각 상자를 행·열로 `flex: 1` 분배 | 판이 정사각형이 아니면 칸이 눌리거나 늘어났다. 정렬 퍼즐(4행 8열)은 칸이 **가로 93 × 세로 185** 였다 |
| 트레이 부품 | 트레이 폭 ÷ 슬롯 수 (뒤에 격자 칸 크기까지 키움) | 레이저의 인벤토리는 7칸이라, 세로 캔버스에서는 부품 한 변이 **63px** 까지 내려갔다. 손가락보다 작다. 가로 캔버스에서는 142px 로 그럭저럭이었다 |

여기에 **아무도 쓰지 않는 세로 여백**이 하나 더 있었다. 보드 패널은 위쪽
`topInsetPercent` 14% 를 허브의 HUD 바 자리로 비워 두는데, 인게임에서는 보드 패널이
화면 전체를 불투명하게 덮어 **그 바가 보이지도 눌리지도 않는다**
(`버그수정_2026-09-03_인게임_일시정지_버튼_접근불가.md` — 그래서 보드 쪽에 `Menu` 버튼을
따로 달았다). 즉 화면 세로의 14% 가 인게임 내내 빈칸이었고, 그만큼 판이 작았다.

## 2. 새 규격

### 2.1 세로 배분 (`PuzzleBoardUI_Panel` 의 prop 기본값)

| prop | 예전 | 지금 |
|---|---|---|
| `topInsetPercent` | 14 | **8** |
| `boardAreaPercent` | 55 | **68** |
| `auxAreaPercent` | 28 | **24** |

셋의 합이 정확히 100 이다. 여기서 화면 비율 보정(`fitBoardAreaToCanvas`)과 기기 보정
(`fitBoardAreaToProfile`)이 순서대로 붙어, 모바일 가로 화면에서는 본 격자 영역이
**약 77%** 까지 올라간다.

> **에디터에서 이 prop 들을 직접 지정해 두었다면 그 값도 함께 내려야 한다.** 기본값은
> 에디터가 비워 둔 경우에만 쓰인다.

> 허브의 상단 바를 언젠가 보드 위로 올리게 되면 `topInsetPercent` 를
> `HUD_BAR_HEIGHT_PERCENT`(10%) + 상단 안전 여백 이상으로 다시 키워야 한다.

### 2.2 보드 메인 패널 — 직사각형

```
boardPanelWidth  = min(쓸 수 있는 폭 × 기기 가로 사용률, 캔버스 폭 × 90%)
boardPanelHeight = 본 격자 영역의 높이 − boardGap
```

- **가로 90%** 가 요구 사항 그대로다 (`BOARD_PANEL_WIDTH_PERCENT`).
- 화면 가운데에 놓인다. 패널에 자기 바탕색(`COLOR_BOARD_PANEL`)을 준 이유는, 정사각 판
  (러시아워 9×9)이 직사각 패널 안에서 가운데로 모이면서 좌우가 남기 때문이다. 그 남는
  자리가 화면 배경과 같은 색이면 "어디까지가 판인지" 가 보이지 않는다.
- `boardGap` 은 패널과 보조 레이아웃 사이의 틈이고, **본 격자 영역 안쪽에서** 뗀다.
  예전에는 보조 레이아웃에 `marginTop` 을 붙였는데, 세로 비율 셋의 합에는 그 여백이
  들어 있지 않아 합이 100% 일 때 보조 레이아웃이 딱 그만큼 화면 밖으로 밀려났다.

### 2.3 칸 — 언제나 정사각형

```
cellSide = floor(min(boardPanelWidth / 열, boardPanelHeight / 행))
격자 크기 = cellSide × 열  ×  cellSide × 행
```

`PuzzleUI_Layout.computeGridPixels()` 하나가 정한다. 행·열은 레벨마다 다르므로 패널은
이 값을 Binding(`_gridWidth` / `_gridHeight` / `_cellSide`)으로 나르고,
`applyView()` 에서 한 번 채운다.

**가로로 긴 판일수록 칸이 커진다** — 남는 가로를 칸이 가져가기 때문이다. 8종 판 규격에
적용하면 이렇게 갈린다.

아래는 19.5:9 가로 화면(캔버스 2557×1180, 보드 패널 2301×801)에서의 칸 한 변이다.

| 퍼즐 | 판 | 예전 | 지금 |
|---|---|---|---|
| 정렬 | 4행 8열 | 가로 92 × 세로 185 | **200 × 200** |
| 색 채우기 | 5행 6열 | 가로 123 × 세로 148 | **160 × 160** |
| 스위치 | 5×5 | 148 | **160** |
| 레이저·연결 | 7×7 | 105 | **114** |
| 러시아워 | 9×9 | 82 | **89** |
| 슬라이드·카드 맞추기 | 판마다 다르다 | — | 위와 같은 규칙 |

정사각 판은 세로가 한계라 **세로 배분에서 늘어난 만큼**(약 +9%) 커지고, 가로로 긴 판은
남는 가로까지 가져가 크게 바뀐다.

칸 글자 크기와 집은 조각을 띄우는 거리도 전부 `cellSide` 에서 파생한다.

### 2.4 트레이 부품 — 화면 아래 절반의 20% 이상 + 슬라이드바

```
아래 한계 = 캔버스 높이 × 50% × 20%
선호 크기 = min(트레이 높이, 트레이 폭 ÷ 3)
itemSlotSide = min(트레이 폭, 트레이 높이, max(아래 한계, 선호 크기))
```

**크기를 먼저 정하고, 다 들어가지 않으면 넘겨 본다.** 예전처럼 슬롯 수로 폭을 나누면
슬롯이 많은 퍼즐(레이저 7칸)에서 부품이 손가락보다 작아진다.

20% 는 **상한이 아니라 하한**이다. 상한으로 두면 트레이가 넉넉한 가로 화면에서 부품이
오히려 지금(142px)보다 작아진다(118px). 트레이 상자가 허락하는 만큼 키우되 이 크기
밑으로는 내려가지 않게 했다. `÷ 3` 은 그 반대쪽 안전장치다 — 슬롯을 트레이 높이까지
키우면 좁은 화면에서 한 번에 하나씩만 보여 일곱 개를 보려고 여섯 번을 넘겨야 한다.

한 페이지에 몇 개를 놓을지는 `computeTrayPageSize()` 가 정한다.

- 전부 한 줄에 들어가면 **화살표를 그리지 않고** 그 폭까지 슬롯이 쓴다.
- 들어가지 않으면 좌우에 `<` `>` 버튼이 붙고, 그 폭을 뺀 나머지로 페이지를 나눈다.
- 감아 돌지 않는다. 끝 페이지에서는 화살표가 흐려진다 — 어디까지 봤는지를 잃지 않기 위해서다.

화살표 라벨을 부등호로 둔 이유는 **폰트에 없는 글리프(◀ ▶)가 기기에 따라 빈 네모로
떨어지기** 때문이다. 방향만 보이면 되므로 ASCII 로 충분하다.

패널 쪽에서는 `_itemIndices` 에 **지금 페이지의 슬롯 번호만** 넣는다. 슬롯 노드와 내용
Binding 은 절대 슬롯 번호로 캐시되어 있으므로, 목록의 내용만 바꾸면 페이지가 넘어간다.
끌던 부품을 화살표 위에서 떼는 경우도 리셋 버튼과 같은 규칙으로 마감한다 — 여기는 판
밖이 확실하므로 부품이 인벤토리로 돌아간다.

## 3. 바꾼 파일

| 파일 | 내용 |
|---|---|
| `PuzzleUI_Layout.ts` | `boardPanelWidth/Height`·`boardGap`·`trayArrowWidth` 를 `PuzzleBoardGeometry` 에 추가. 새 순수 함수 `computeGridPixels()` · `computeTrayPageSize()` · `computeTrayPageCount()`. 상수 `BOARD_PANEL_WIDTH_PERCENT` · `TRAY_SLOT_LOWER_HALF_RATIO` |
| `PuzzleBoardUI_Panel.ts` | 세로 배분 기본값 변경, 보드 메인 패널(`createBoardPanel()`) 신설, 격자 크기를 Binding 으로, 트레이 슬라이드바(`createTrayArrow()` / `applyItemPage()`), 보조 레이아웃의 `marginTop` 제거 |
| `PuzzleUI_MainPanel.ts` | 주석만. 상단 바가 인게임에서 보이지 않는다는 사실과 `topInsetPercent` 의 관계를 적었다 |
| `PuzzleUI_Tests.ts` | 보드 패널·정사각 칸·트레이 페이지 검증 추가 (`testBoardPanelGrid` / `testTrayPaging`) |

`*_CoreAPI` 8종은 **하나도 건드리지 않았다.** 퍼즐은 행·열 수만 알려 주고 크기는 전부
표현 계층이 정하기 때문이다.

## 4. 검증

```
node ./node_modules/typescript/bin/tsc --noEmit --skipLibCheck                    → 에러 0
node ./node_modules/typescript/bin/tsc --noEmit --skipLibCheck --target ES5 ...   → 에러 0
메인 UI 허브  220 PASS / 0 FAIL   (예전 177 → 새 검증 43개 추가)
전체         1,322 PASS / 0 FAIL
```

새로 넣은 검증은 이렇다.

- 보드 패널이 화면 폭과 배정된 높이를 넘지 않는다 / 보조 레이아웃과의 틈이 있다
- 8종 판 규격 전부에서 **칸이 정사각형**이고 격자가 패널 안에 들어간다
- 행이 적은 판이 칸을 더 크게 쓴다 (예전 정사각 상자에서는 반대로 납작해졌다)
- 슬롯이 화면 아래 절반의 20% **밑으로 내려가지 않고** 트레이 상자를 넘지도 않는다
- 한 페이지의 슬롯이 **화살표까지 합쳐** 트레이 폭 안에 들어간다
- 페이지를 모으면 슬롯 전부가 나온다 / 넘겨야 하는 경우에도 한 페이지에 둘 이상 보인다
- 가로 화면에서는 레이저의 7칸이 한 줄에 다 들어간다 (화살표가 뜨지 않는다)

> `*_CoreAPI` 8종은 Node 에서 돌지 않으므로 테스트가 아니라 타입 체크로만 검증된다
> (`가이드/타입체크와_테스트_실행.md` §3). 이번 작업은 CoreAPI 를 건드리지 않았다.

## 5. 인월드에서 확인할 것

숫자는 전부 화면 비율에서 나오므로, 실기에서는 아래를 눈으로 본다.

1. 판이 화면 가로의 90% 를 차지하고 가운데 있는가.
2. 정렬 퍼즐(4행 8열)의 케이스가 정사각형인가 — 예전에는 세로로 길쭉했다.
3. 레이저의 부품이 판의 칸보다 크게 보이는가 (가로 화면 기준 부품 138 vs 판 칸 114).
   7칸이 한 줄에 들어가는가, 아니면 `<` `>` 가 떠 있는가 — 가로 화면이면 한 줄에 들어가고
   세로에 가까운 화면에서만 화살표가 뜬다.
4. **판이 위로 올라오면서 허브의 레벨·남은 초 표시와 겹치지 않는가.** 지금은 보드가 그
   바를 덮고 있어 문제가 없지만, 상단 바를 보드 위로 올리는 변경이 들어가면 여기가 먼저
   깨진다.
