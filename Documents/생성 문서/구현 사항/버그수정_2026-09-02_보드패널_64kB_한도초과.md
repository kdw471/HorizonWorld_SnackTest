# 버그수정 — 보드 패널이 64kB 한도를 넘어 아예 만들어지지 않던 문제

> 대상 파일: `PuzzleBoardUI_Panel.ts`
> 관련 문서: `작업기록_2026-09-02_보드_CustomUI_전환.md` (이 패널이 왜 생겼는지),
> `작업기록_2026-09-02_기기별_화면_규격.md` (칸 구조를 이렇게 나눈 이유),
> `작업기록_2026-09-02_드래그_조작_시각_피드백.md` (겹쳐 놓은 층들의 역할)

---

## 1. 증상

에디터 콘솔에 이것만 뜨고 보드가 전혀 그려지지 않았다.

```
Failed to instantiate script component definition `PuzzleBoardUIPanel`:
Component definition 'PuzzleBoardUIPanel' was unable to initialize an instance
attached to the object: Error: The UI (86236B) exceeds the maximum allowed size of 64kB.
```

**컴포넌트 인스턴스 자체가 만들어지지 않는다.** 화면이 비는 것이 아니라 패널이 없는
상태이므로, `PuzzleBoardStage` 에는 `A board was mounted but no panel is listening`
경고가 남는다.

---

## 2. 원인 — `initializeUI()` 의 반환 트리는 통째로 직렬화된다

`initializeUI()` 는 한 번만 불리고, 돌려준 `UINode` 트리는 통째로 직렬화되어 패널에 실린다.
그 크기에 **64kB 한도**가 걸려 있고, 넘으면 컴포넌트가 만들어지지 않는다.

예전 구조는 최대 격자(9×9)의 칸 81개를 `initializeUI()` 에서 전부 만들어 두고, 실제 격자
밖은 `display: none` 으로 숨기는 방식이었다. 칸 하나가 노드 6개다.

```
Pressable (입력 판정 - 크기를 바꾸는 스타일을 걸지 않는다)
 ├ 얼굴 View (배경색·확대·그림자)
 │   └ Text (라벨, 무늬 방향만큼 회전)
 ├ 무늬 테두리 View   (position: absolute)
 ├ 강조 테두리 View   (position: absolute)
 └ 집기 고리 View     (position: absolute)
```

이 6개가 **81벌 복제**되어 트리에 들어갔다. 실측한 비중은 이렇다.

| 구역 | 노드 수 | 직렬화 비중 |
|---|---|---|
| 본 격자 (`createGrid`) | 497 | **88%** |
| 보조 레이아웃 (트레이 8 · 미니격자 3×3 · 리셋) | 78 | 12% |
| 나머지 (상단 여백 · 제목) | 3 | ~0% |
| 합계 | 578 | 86,236 B |

---

## 3. 검토했지만 택하지 않은 길

### 3.1 격자를 9×9 보다 줄인다 — 불가능

러시아워가 **도착 포인트를 올려 놓는 보이지 않는 테두리 링까지 합쳐 9×9** 를 쓴다
(`RushHour_Definitions.RUSH_HOUR_FULL_GRID_SIZE`, 플레이 공간은 중앙 7×7).
7×7 로 줄이면 USB 가 어디로 나가는지가 화면에서 사라진다.

### 3.2 패널을 여러 Custom UI gizmo 로 쪼갠다 — 조작이 깨진다

64kB 는 패널 단위 한도라, 격자를 3개 gizmo 로 나누면 각각은 한도 아래로 내려간다.
그러나 **Custom UI 는 gizmo 마다 입력 표면이 따로다.** A 패널에서 시작한 드래그가 B 패널
칸의 `onEnter` 를 받지 못하면 판을 가로지르는 드래그가 죽는다 — 레이저·연결·정렬·러시아워의
기본 조작이 전부 여기에 걸린다. 보조 레이아웃만 떼어내도 같은 문제다. 트레이 슬롯에서 시작한
드래그가 그대로 격자 칸으로 이어지는 것이 레이저의 기본 조작이기 때문이다.

### 3.3 연출을 깎는다 — 하지 않아도 됐다

집기 고리 제거, 그림자 제거, 무늬 테두리와 강조 테두리 합치기로 칸당 6 → 4 노드까지는
줄일 수 있고 그러면 약 53kB 가 된다. 아래 방법으로 연출을 하나도 건드리지 않고 해결되므로
쓰지 않았다.

---

## 4. 해결 — 격자를 `DynamicList` 로 그린다

`horizon/ui` 의 `DynamicList` 는 `renderItem` 을 **런타임에** 부른다. 그래서 직렬화되는
트리에는 **템플릿 한 벌만** 들어간다.

```ts
DynamicList<number>({
    data: this._rowIndices,                       // Binding<number[]>
    renderItem: (row: number) => DynamicList<number>({
        data: this._colIndices,
        renderItem: (col: number) =>
            this.createGridCell(this._cellBindings[row * PUZZLE_BOARD_MAX_COLS + col], row, col),
        style: { flex: 1, width: '100%', flexDirection: 'row' },
    }),
    style: { width: gridSide, height: gridSide, flexDirection: 'column' },
})
```

핵심은 **목록이 나르는 것이 자리 번호뿐**이라는 점이다.

- 칸의 **내용**은 예전과 같이 미리 만들어 둔 `_cellBindings[슬롯]` 이 나른다.
  칸 하나가 바뀔 때 목록을 다시 그리지 않고 그 칸의 Binding 만 갱신하므로,
  **드래그 중의 갱신 비용은 예전과 같다.**
- 목록의 **길이가 곧 격자의 크기**다. 그래서 행·칸을 `display: none` 으로 숨기던
  파생 Binding 이 전부 없어졌다.
- 자리 번호 ↔ 칸 번호 변환 규칙(`toSlotIndex()` / `toCellIndex()`)은 그대로다.
  `_cellBindings` 는 여전히 고정 9열 기준으로 색인한다.

같은 방식을 **오브젝트 트레이**(`_itemIndices`)와 **정보 미니 격자**
(`_sideRowIndices` / `_sideColIndices`)에도 적용했다.

### 4.1 순서 주의 — 내용을 먼저 채우고 목록을 늘린다

`applyView()` 에서 `_rowIndices` / `_colIndices` 를 **칸 Binding 을 다 채운 뒤에** 세운다.
반대로 하면 새 격자가 앞 레벨의 칸 내용을 한 프레임 보여 준다.

### 4.2 함께 바뀐 것

| 항목 | 전 | 후 |
|---|---|---|
| `_cellBindings` 생성 위치 | `createGrid()` 안에서 push | 필드 초기화(`createSlotBindings`) |
| 행/칸의 `display` 파생 | 슬롯마다 있음 | 없음 (목록 길이가 대신한다) |
| 미니 격자 칸 | `createSide()` 안의 인라인 View | `createSideCell()` 로 분리 |

연출 코드(얼굴·무늬 테두리·강조 테두리·집기 고리·그림자·확대)는 **한 줄도 바뀌지 않았다.**

## 5. 검증

직렬화 크기는 `horizon/core` · `horizon/ui` 를 스텁으로 바꿔 `initializeUI()` 의 반환
트리를 JSON 으로 재는 방식으로 측정했다. 하네스 값은 에디터가 보고한 86,236 B 에
맞춰 환산했다.

| 패널 | 전 | 후 | 한도 |
|---|---|---|---|
| `PuzzleBoardUIPanel` | 86,236 B | 약 1,500 B | 65,536 B |
| `PuzzleUI_MainPanel` | — | 약 7,100 B | 65,536 B |

메인 UI 패널은 카탈로그 슬롯이 8개뿐이라 한도에서 멀다. 그대로 두었다.

- `tsc --noEmit --skipLibCheck` — 에러 0건
- `tsc --noEmit --skipLibCheck --target ES5 --lib ES2020` (에디터 제약 재현) — 에러 0건
- 전체 테스트 1,241 PASS / 0 FAIL (변화 없음)

> 테스트는 순수 계층과 프레젠터만 덮는다. 패널은 `horizon/ui` 에 의존해 Node 에서 돌지
> 않으므로, **인월드에서 다음 세 가지를 눈으로 확인해야 한다.**
> 1. 격자 크기가 다른 퍼즐을 오갈 때(예: 슬라이드 3×3 ↔ 4×4, 러시아워 9×9) 격자가 제대로 갈리는지
> 2. 판을 가로지르는 드래그가 예전처럼 이어지는지
> 3. 레벨이 바뀔 때 앞 레벨의 칸이 한 프레임 비치지 않는지

---

## 6. 앞으로 칸에 무엇을 더할 때

`DynamicList` 를 쓰는 지금은 칸 하나에 층을 더해도 직렬화 크기가 그만큼 늘지 않는다
(템플릿 한 벌만 실린다). 다만 **런타임에는 81벌이 실제로 만들어지므로** 프레임 비용은
예전과 같이 늘어난다. 크기 한도가 아니라 성능으로 판단한다.
