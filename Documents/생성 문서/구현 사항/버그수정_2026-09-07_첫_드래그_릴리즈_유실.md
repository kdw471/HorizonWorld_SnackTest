# 버그 수정 기록 - 퍼즐 시작 후 **첫 드래그만** 손을 떼도 놓이지 않는 문제

- **날짜**: 2026-09-07
- **증상**: 레이저 퍼즐을 시작하고 **처음** 오브젝트를 드래그하면 터치를 떼는 즉시 드롭되지 않는다. 그 다음 터치에서야 놓인다. 두 번째 드래그부터는 정상.
- **수정 파일**: `Puzzle_HorizonBridge.ts`(`PuzzleScreenDragStream`), `Laser_CoreAPI.ts`, `RushHour_CoreAPI.ts`, `ColorSort_CoreAPI.ts`, `Flow_CoreAPI.ts`
- **영향 범위**: 연속 드래그 스트림(`continuousDrag`)을 쓰는 퍼즐 4종 전부. 레이저에서 가장 잘 드러났을 뿐 같은 구멍이었다.
- **관련 문서**: `작업기록_2026-09-04_릴리즈_리페인트_통합과_드래그_스트림_실험.md`(스트림 도입)

---

## 1. 원인 - 뗌을 알려 주는 두 경로가 **서로에게 미루고 있었다**

드래그의 뗌은 두 곳에서 올 수 있다.

| 경로 | 출처 | 신뢰도 |
|---|---|---|
| 칸 단위 | Custom UI `Pressable` 의 `onRelease` | 모바일에서 **유실될 수 있다** (이미 알려진 문제 - `pointerDown()` 의 회복 규칙) |
| 스트림 | Focused Interaction 의 `onFocusedInteractionInputEnded` | 유실되지 않지만 **모드가 활성일 때만** 흐른다 |

그런데 두 경로가 각각 상대에게 마감을 미루고 있었다.

```ts
// 칸 단위 - 스트림이 배달 중이면 통째로 버린다
private onDragEnd(cell: number): void {
    if (this._dragStream?.isDriving === true) {
        return;                       // ← 스트림이 확정하겠지
    }
    ...
}

// 스트림 - 한 번도 배달하지 않았으면 그냥 돌아간다
private handleEnded(...): void {
    ...
    if (wasDriving === false) {
        return;                       // ← 칸 단위 폴백이 확정하겠지
    }
    ...
}
```

평소에는 둘 중 하나가 반드시 도착하므로 문제가 없다. **그런데 퍼즐이 막 시작한 직후의
첫 터치가 정확히 두 조건을 동시에 깬다.**

```
startLevel()
  └ enterInteraction() -> enterFocusedInteractionMode()      모드가 자리를 잡는 중
     ...
     GameStart 배너 유지 0.45s -> 페이드 시작에 입력 개방
        └ 유저의 첫 터치
             Pressable.onPress   O   잡기는 된다 (조각이 손가락을 따라온다)
             stream inputMoved   X   모드가 아직 흐르지 않아 isDriving = false
             Pressable.onRelease X   모드 전환에 삼켜진다
             stream inputEnded   O   이때쯤엔 모드가 살아 있다 -> 그러나 wasDriving=false 라 무시
                                     => 아무도 드래그를 닫지 않는다
```

그래서 손을 떼도 조각이 놓이지 않고, **다음 터치의 `pointerDown` 회복 규칙**(열려 있던
누름을 마지막 칸에 놓아 마감)이 돌 때에야 뒤늦게 놓였다. 두 번째 드래그부터는 모드가
완전히 활성이라 스트림이 배달하고(`isDriving = true`) `onStreamEnd` 가 확실히 마감한다 -
"그 후부터는 잘된다" 가 이것이다.

## 2. 수정

### 2-1. 스트림은 배달 여부와 무관하게 "터치가 끝났다" 를 알린다

`PuzzleDragStreamHandlers` 에 `onStreamRelease?` 를 더했다. `handleEnded` 는 이제
`wasDriving` 이 거짓이어도 조용히 돌아가지 않는다.

```ts
if (wasDriving) {
    this._handlers.onStreamEnd(point ?? { row: NaN, col: NaN });
}
// **배달 여부와 무관하게** 이 터치는 끝났다 - 열려 있는 누름을 닫으라고 알린다
if (this._handlers.onStreamRelease !== undefined) {
    this._handlers.onStreamRelease();
}
```

각 CoreAPI 는 이것을 **프레젠터의 `pointerUp()`** 으로 받는다. 평소 릴리즈와 완전히 같은
경로(`onCellUp`)를 타므로 별도 확정 로직이 없고, 이미 닫혀 있으면 프레젠터가 무시한다.

```ts
private onStreamRelease(): void {
    this._presenter.pointerUp();
}
```

### 2-2. 칸 단위 릴리즈도 더 이상 버리지 않는다 - **먼저 도착한 쪽이 이긴다**

`isDriving` 을 보고 통째로 버리던 것을 없애고, **드래그가 열려 있는지**만 본다.

```ts
private onDragEnd(cell: number): void {
    if (this._dragCrystalId === undefined) {
        return;                                   // 뒤늦게 온 쪽은 여기서 조용히 지나간다
    }
    // 스트림이 배달 중이었다면 마지막 자리는 스트림이 이미 더 정확히 반영해 두었다 -
    // 칸 중심 좌표로 덮어쓰지 않고 확정만 한다.
    if (this._dragStream?.isDriving !== true) {
        this.trackDragTo(cell);
    }
    this.finalizeDrag();
}
```

두 가지를 동시에 지킨다.

- **정확도** - 스트림이 배달 중이었다면 좌표는 건드리지 않는다. 연속 좌표로 따라오던
  조각이 마지막에 칸 중심으로 튀지 않는다.
- **확정성** - 어느 쪽이 먼저 오든 그쪽이 확정한다. 스트림의 뗌이 유실돼도(반대 방향의
  구멍) 드래그가 열린 채 남지 않는다.

4종의 "드래그가 열려 있는지" 판정은 각자 이미 쓰던 상태를 그대로 쓴다.

| 퍼즐 | 판정 |
|---|---|
| 레이저 | `_dragCrystalId === undefined` |
| 러시아워 | `_previewPieceId === undefined` |
| 정렬 | `_dragFromCase === undefined` |
| 연결 | `session.dragController?.isDrawing !== true` |

네 퍼즐의 `onStreamDragEnd` 는 **이미** 같은 판정으로 가드하고 있었으므로, 양쪽이 대칭이
되어 어떤 순서로 들어와도 두 번 확정되지 않는다.

## 3. 검증

- 타입 체크 2종(정식 / 에디터 제약 ES5) 통과.
- Node 테스트 스위트 전체 통과 (`가이드/타입체크와_테스트_실행.md` §3).

`PuzzleScreenDragStream` 은 `horizon/core` 의 `PlayerControls` 브로드캐스트에 직접 붙어
있어 Node 하네스로 재현할 수 없다. 그래서 **이 수정의 회귀는 자동 테스트가 잡지 못한다** -
인월드에서 다음 순서로 확인한다.

1. 월드 입장 -> 메인 메뉴 -> 레이저 -> Start
2. `GameStart` 배너가 사라지는 즉시 크리스탈 하나를 끌어 놓는다
3. **손을 떼는 즉시** 놓이는지 본다 (예전에는 다음 터치에서야 놓였다)
4. 러시아워·정렬·연결에서도 첫 드래그를 같은 방식으로 확인한다

# 2차 수정 — 1차 수정이 닿지 않았던 이유 (같은 날 재보고)

> **증상 그대로 재발.** "첫 드래그만 손을 떼도 놓이지 않고 한 번 더 터치해야 놓인다."
> 1차 수정(`onStreamRelease`)이 **실행되지 않는 경로**가 셋 남아 있었다.

## A. 안전망이 `_isArmed` 뒤에 갇혀 있었다 — 진짜 구멍

1차에서는 `wasDriving` 조건만 걷어내고 그 **위의 `_isArmed` 조기 반환은 그대로 두었다.**

```ts
private handleEnded(info): void {
    this._lastStartInfo = undefined;
    if (this._isArmed === false) {
        return;                        // ← 안전망까지 통째로 건너뛴다
    }
    ...
```

`_isArmed` 를 세우는 것은 칸 `Pressable` 의 down(`notifyDragBegan()`)이고, `handleEnded` 는
플랫폼 브로드캐스트다. **둘의 순서는 보장되지 않는다** — 이것은 같은 파일의 `_lastStartInfo`
주석이 이미 적어 둔 사실이다(`started` 와 down 의 순서 무보장). 잡기보다 이 뗌이 먼저
처리되면 무장이 아직 서 있지 않아, 1차에서 넣은 `onStreamRelease` 가 한 번도 불리지 않는다.

**수정** — 무장·배달 여부와 **무관하게** 닫는다. 열려 있는 누름이 없으면 프레젠터가
무시하므로(`PuzzleBoardPresenter.pointerUp`) 관계없는 터치에서 불려도 아무 일이 없다.

## B. `continuousDrag` 가 꺼져 있으면 안전망이 **아예 만들어지지 않았다**

`_dragStream` 은 `if (this.props.continuousDrag)` 안에서만 생성됐고, `enterInteraction()` 도
같은 조건에서만 Focused Interaction 모드에 들어갔다. 즉 prop 하나가 꺼지면
**`inputEnded` 자체가 흐르지 않아** 1차 수정이 통째로 죽는다.

여기에 **에디터의 저장된 값** 문제가 겹친다. 이 prop 의 기본값은 원래 `false` 였고
2026-09-05 에 `true` 로 바뀌었는데, Horizon 은 엔티티에 prop 값을 **저장**하므로 코드의
기본값을 바꿔도 **이미 배치된 엔티티는 예전 값(false)을 그대로 들고 있을 수 있다.**
그러면 인월드에서는 1차 수정이 있으나 마나였다.

**수정** — 역할을 갈랐다.

| | 이동을 스트림이 몰까 | 뗌 안전망 |
|---|---|---|
| 전 | `continuousDrag` 가 둘 다 정함 | prop 이 꺼지면 없음 |
| 후 | `PuzzleDragStreamOptions.drivesMoves` (= `continuousDrag`) | **언제나 있음** |

- `PuzzleScreenDragStream` 에 `drivesMoves` 옵션을 더했다. 꺼지면 `isDriving` 은 끝까지
  false 라 이동·뗌 확정은 전부 칸 단위 경로가 맡고, **`onStreamRelease` 만 계속 흐른다.**
- 4종 CoreAPI 는 스트림을 **prop 과 무관하게 언제나 만들고**, `enterInteraction()` 도
  카메라를 쓰지 않는 경우 **언제나** `enterPuzzleTouchStream()` 으로 모드에 들어간다.

## C. 트레이에서 집는 순간 가장 무거운 리페인트가 돌았다 (레이저)

`onDragBegin`(판에서 집기)은 같은 날 전환 더티 필터로 바꿨는데
**`onInventoryPick`(트레이에서 집기)만 `applyBoardVisuals()` 전체 리페인트로 남아 있었다.**
레이저의 첫 드래그는 거의 항상 트레이에서 시작하므로, 손가락이 닿는 바로 그 순간에
바탕 49칸 + 광선 + 기믹을 전부 훑는 리페인트가 돈 셈이다. 집는 순간 실제로 바뀌는 것은
**그 슬롯 하나(실루엣)** 뿐이므로 트레이만 다시 칠하도록 맞췄다.

## D. 유실을 눈에 보이게 만들었다 — 인월드 진단 로그

이 증상은 Node 하네스로 재현할 수 없다. 그래서 다음 두 줄을 남긴다.

| 로그 | 뜻 |
|---|---|
| `[PuzzleScreenDragStream] Focused Interaction input is live (first event: ...)` | 스트림이 실제로 흐른다. **이 줄이 없으면** 모드 진입이 실패한 것이고 뗌 안전망도 동작하지 않는다 |
| `[PuzzleBoardPresenter] A cell/item press arrived while the previous press was still open, so the previous release was lost (count N)` | 뗌을 다섯 경로(칸·격자 상자·보조 영역·전면 캐처·스트림) 어디서도 받지 못했다. **이 줄이 뜨는 그 순간이 곧 "한 번 더 터치해야 놓이는" 순간이다** |

## 검증

- 타입 체크 3종(정식 / ES5 다운레벨 / 선언 파일 생성) 통과.
- Node 테스트 전체 1,405 PASS / 0 FAIL.
- 인월드 확인 순서는 위 §3 과 같다. 이번에는 **콘솔의 두 줄**을 함께 본다.
  1. 레이저 시작 직후 `Focused Interaction input is live` 가 뜨는가 → 안 뜨면 B 가 원인이다.
  2. 첫 드래그를 떼고 다음 터치에서 `the previous release was lost` 가 뜨는가 →
     뜨면 뗌이 여전히 다섯 경로 모두에서 유실된 것이고, 안 뜨면 이번 수정으로 닫힌 것이다.
