## 1. 문제 제기 — "색 채우기의 STOP 을 모든 퍼즐이 알 필요는 없다"

보드 패널 한 파일이 8개 퍼즐의 화면을 전부 그리고 있었다. 그런데 화면 조각 셋은
**그것을 규격에 적은 퍼즐만** 쓴다.

| 조각 | 쓰는 퍼즐 | 규격 |
|---|---|---|
| 오브젝트 트레이 | 레이저 | `PuzzleBoardLayoutSpec.itemCount` |
| 정보 미니 격자 | 스위치 | `PuzzleBoardLayoutSpec.side` |
| 큰 액션 버튼 | 색 채우기 | `PuzzleBoardLayoutSpec.actionLabel` |

### 1.1 먼저 확인한 것 — 코드 결합은 이미 없었다

`createReleaseCatcher()` 같은 것은 패널 클래스의 `private` 메서드라 다른 파일에서 참조
자체가 불가능하다. 각 `*_CoreAPI` 가 보드 UI 에서 가져가는 것은 색 타입과 헬퍼뿐이다
(스위치는 `PuzzleBoardColor` · `PuzzleTextureKey` · `boardColor` · `textureKey` 네 개).

### 1.2 진짜 문제 — 안 쓰는 조각이 **트리에 올라가 있었다**

선택 조각을 `UINode.if`(트리에서 뺌)가 아니라 **`display: 'none'`(트리에 두고 숨김)** 으로
처리하고 있었다. 숨긴 노드는 그려지지만 않을 뿐 트리에 남아 Binding 을 들고 있다.

| 안 쓰는데 마운트되던 것 | 노드 |
|---|---|
| 오브젝트 트레이 (슬롯 8 + 화살표 2 + 상자) | 62 |
| 액션 버튼 | 2 |

62 중 56은 **같은 날 트레이 버그를 고치면서 늘어난 것**이다
(`버그수정_2026-09-04_보조레이아웃_오브젝트_미표시.md` — 슬롯 8개를 트리로 되돌렸다).
트레이를 쓰지 않는 7개 퍼즐이 그것을 그대로 짊어지고 있었다.

## 2. 해결 1 — 선언한 퍼즐만 마운트한다

```ts
children: [
    this.createActionButton(),                    // 안에서 UINode.if(this._hasAction, ...)
    UINode.if(this._hasItems, tray.createNode()),
    UINode.if(this._hasSide, side.createNode()),
    this.createResetButton(),                     // 모든 퍼즐이 쓴다
],
```

`initializeUI()` 는 월드 시작에 **한 번만** 돌고 그때는 어떤 퍼즐이 올라올지 모른다.
그래서 트리에는 넷이 다 들어가되, **마운트 여부를 런타임 Binding 이 정한다.** Custom UI
에서 "퍼즐이 자기 UI 를 들고 온다" 에 가장 가까운 방법이 이것이다.

### 2.1 왜 퍼즐마다 Custom UI gizmo 를 나누지 않았는가

검토했지만 득보다 실이 컸다.

- **런타임 객체가 오히려 늘어난다.** gizmo 는 월드에 있으면 `initializeUI()` 가 각각 한 번씩
  돈다. 8개로 나누면 지금 안 쓰는 퍼즐의 트리와 Binding 까지 8벌이 상시 존재한다.
- **에디터 셋업이 8배**가 되고, 화면 오버레이 gizmo 끼리는 **코드로 z-order 를 정할 수 없다**
  (보드 ↔ 허브 패널에서 이미 겪어 `unmount` 로 우회 중인 문제다).
- 64kB 트리 한도는 나눌 이유였지만, 격자를 `DynamicList` 로 돌린 뒤로는 여유가 크다.
- 레이아웃·입력 코드 1,400줄을 8벌 복제하거나 공통 베이스로 빼야 하는데, 후자면 결국
  같은 파일을 다시 공유하는 셈이라 얻는 것이 트리 크기뿐이다.

## 3. 해결 2 — 화면 조각을 파일로 나눈다

```
PuzzleBoardUI_Panel   틀과 배선 - 수명주기·프레젠터 연결·화면 크롬(제목·Menu·Reset·배너)
PuzzleBoardUI_Grid    본 격자              BoardGridRenderer
PuzzleBoardUI_Tray    오브젝트 트레이       BoardTrayRenderer
PuzzleBoardUI_Side    정보 미니 격자        BoardSideRenderer
PuzzleBoardUI_Parts   셋이 나눠 쓰는 어휘    색·조작 강조·칸 위에 겹치는 층 다섯
```

**렌더러가 자기 상태(Binding)를 소유한다.** 패널에는 창구 몇 개만 노출한다 -
`applyView()` · `applyCell()`/`applyItem()` · `setPressed()` · `reset()` · `createNode()`.
그래서 패널의 `applyView()` 는 규격을 해석해 셋에게 나눠 주는 20줄이 됐다.

패널에 남은 Binding 은 **셋 중 어느 것에도 속하지 않는 것**뿐이다 - 보드가 올라와 있는지,
제목, 배너, 액션 버튼, 텍스처 세대.

### 3.1 `BoardMetrics` — 픽셀 환산을 넘겨받는 창구

렌더러는 `UIComponent` 의 메서드가 아니라서 `this.px()` 같은 환산기를 쓸 수 없다.
그래서 패널이 자기 환산기를 한 덩어리로 묶어 넘긴다.

```ts
private createMetrics(): BoardMetrics {
    return {
        px: (v) => this.px(v),
        units: (f) => this.units(f),
        ...
        layout: () => this._layout,
        textureEpoch: this._textureEpoch,
        tintTexturesWithFill: () => this.props.tintTexturesWithFill === true,
    };
}
```

**값이 아니라 함수로 넘긴다.** 배율과 배치는 `resolveLayout()` 이 정하고, 글자 크기는
런타임 파생(`Binding.derive`) 안에서도 다시 계산되므로 복사해 두면 낡는다.

### 3.2 렌더러는 `initializeUI()` 에서 만든다

생성자가 `this.props`(칸 간격)를 읽는데, 클래스 필드 초기화 시점에는 아직 props 가 없어
컴포넌트가 통째로 만들어지지 않는다 (`_pixelRatio` 주석에 적힌 것과 같은 함정).
그래서 셋은 `| undefined` 필드이고 접근은 전부 `?.` 다 - 서버 인스턴스는 트리를 만들지
않으므로 실제로 `undefined` 로 남는다.

### 3.3 옮기면서 갈라 놓은 것 하나 — 트레이의 뗌

트레이 슬롯과 화살표는 **뗌 처리가 다르다.** 하나로 묶었다가 되돌렸다.

| 어디서 뗐나 | 무엇을 부르나 | 왜 |
|---|---|---|
| 슬롯 | `pointerUp()` 만 | 슬롯에서 집어 칸 위에서 뗀 뗌이 슬롯으로 올라오는 경우가 있다. 여기서 "판 밖" 으로 단정하면 칸 위에서 뗐는데 부품이 인벤토리로 돌아간다 |
| 화살표 | `pointerLeaveBoard()` + `pointerUp()` | 여기는 판 밖이 확실하다 (리셋 버튼과 같은 처리) |
