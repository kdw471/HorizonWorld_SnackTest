## 1. 드래그 앤 드롭 — 손을 떼도 놓이지 않고 "한 번 더" 눌러야 놓였다

> "터치를 떼는 타이밍을 감지 못해서 손을 떼는 즉시 오브젝트가 해당 위치에 스냅되는 것이
> 아니라, 한번 더 터치를 해야 스냅되는 이슈"

### 1.1 증상이 원인을 가리켰다

**"한 번 더 눌러야 놓인다"** 는 표현이 결정적이었다. 지난 수정에서 넣어 둔 회복 규칙
(`pointerDown()` 이 붙잡힌 누름을 먼저 마감한다) 때문에, 두 번째 터치의 **누름**에서
앞 드래그가 뒤늦게 확정되고 있었던 것이다. 즉 **첫 번째 터치의 뗌이 아예 오지 않았다.**

```
1차 터치   press(A) → enter(B) → [손 뗌]           ← 아무 이벤트도 오지 않는다
2차 터치   press(C) → 회복 규칙이 앞 드래그를 B 에 확정   ← 여기서 비로소 스냅
```

### 1.2 원인 — `propagateClick: false` 가 조상까지 막고 있었다

`Pressable` 은 손가락이 **누른 요소 밖으로 나가면** 그 요소에 뗌을 보내지 않는다.
그래서 조상이 대신 받아야 하는데, 격자 칸과 트레이 슬롯에 `propagateClick: false` 가
걸려 있었다. 이 값은 **전파를 통째로 끊으므로**, 칸도 조상도 뗌을 받지 못했다.

```
이전                                    지금
Pressable 격자 상자   ✗ 못 받음          Pressable 격자 상자   ✅ 받는다
  └ Pressable 칸 A   ✗ 손가락이 떠남       └ Pressable 칸 A   ✗ 손가락이 떠남
      propagateClick:false ← 여기서 끊김        (전파 허용)
```

칸에서 `propagateClick: false` 를 뺐다. 조상(격자 상자·전면 캐처)은 **손가락이 벗어날 수
없는 크기**라 뗌을 확실히 받는다. 여러 경로로 올라와도 `pointerUp()` 은 한 번만 일한다
(첫 호출에서 누름을 비우므로 나머지는 무시된다).

버튼(리셋·메뉴·트레이 화살표)은 `propagateClick: false` 를 그대로 둔다 - 그쪽은 눌림이
조상으로 새면 안 된다.

### 1.3 남겨 둔 안전망

회복 규칙(`pointerDown()`/`itemDown()` 이 붙잡힌 누름을 먼저 마감)은 **그대로 둔다.**
전파가 어떤 이유로든 끊기는 기기가 있으면 최악의 경우가 "다음 터치에서 확정" 으로
머무르고, 판이 영영 굳지는 않는다.

## 2. 인터랙션 반응 — 게임 루프 점검과 잔여 랙

> "게임 루프가 철저하게 프레임 업데이트 시간 간격으로 실행되고 있는지 확인해주고,
> 전반적인 터치, 드래그 등 인터랙션의 미세한 랙들이 어디서 오는지 검토"

### 2.1 루프는 정상이다

| 확인한 것 | 결과 |
|---|---|
| 프레임 구동인가 | ✅ `connectPuzzleUpdate()` 가 `World.onUpdate` 에 걸고 `deltaTime` 을 그대로 넘긴다 |
| 고정 간격을 섞어 쓰는가 | ✅ 아니다. 8개 세션이 전부 `deltaSeconds` 로만 시간을 깎는다 |
| 시간 이벤트가 매 프레임 나가는가 | ✅ 아니다. `publishRemainingTime()` 이 **초 단위로 스로틀**한다 |
| 칸 갱신이 매번 재렌더를 부르는가 | ✅ 아니다. `setCell()` 이 값이 실제로 바뀐 칸만 이벤트로 낸다 |
| 드래그 한 칸마다 판을 통째로 다시 그리는가 | ✅ 레이저·러시아워·정렬은 `trackDragTo()` 로 실제 변화가 있을 때만, 연결은 경로 이벤트가 왔을 때만 |

즉 **구조적으로는 이미 프레임 간격을 따르고 있었다.**

### 2.2 실제로 찾은 랙 두 군데 — 드래그 도중의 `console.log`

Horizon 의 `console.log` 는 드래그 빈도로 부르면 눈에 띄게 끊긴다. 두 곳이 그 빈도였다.

| 자리 | 얼마나 자주 | 조치 |
|---|---|---|
| 연결 퍼즐 `PATH_COMPLETED` / `PATH_BROKEN` | 선을 긋는 동안 두 이벤트가 번갈아 **수십 번** | 로그 삭제 |
| 레이저 `SKULL_HIT` | 광선이 드래그 **한 칸마다** 다시 계산되므로, 해골을 지나는 배치에서는 이동마다 | 로그 삭제 |

둘 다 화면이 이미 같은 정보를 실시간으로 보여 준다(전구 색과 테두리, 수신체의 Fault 색).
레벨 로드·퀘스트 종료·데드락처럼 **드물게 한 번** 나오는 로그는 그대로 남겼다.

> 1번의 "떼도 안 놓임" 자체도 **랙처럼 보이는 증상**이었다. 조각이 손가락을 따라오다가
> 확정만 늦어지므로, 체감으로는 "반응이 한 박자 느리다" 로 읽힌다.

## 3. 레이저 — 반사 부품에 그림 입히기

> "반사 부품들에 대해 이미지를 적용할 수 있게 구현되어 있는지 확인하고,
> `resources/textures/LaserProp.png` 의 이미지를 잘라서 적용해줘"

### 3.1 적용할 수 있게는 되어 있었지만 부품을 가르지 못했다

텍스처 구조는 이미 있었다(`작업기록_2026-09-02_퍼즐_요소_텍스처_파라미터화.md`).
그런데 레이저의 prop 이 `crystalTexture` **하나**뿐이라, 삼각·팔각·십자·T자가 전부 같은
그림을 쓸 수밖에 없었다. 발사체와 수신체도 `gimmickTexture` 하나로 묶여 있었다.

### 3.2 시트를 부품별로 잘랐다

`LaserProp.png` 는 3×3 배치의 스프라이트 시트다. 내용 경계를 픽셀로 찾아
**캡션(#201 같은 글자)을 잘라 내고** 부품만 남겨, 배경 흰색을 투명으로 바꾼 뒤
512×512 정사각형으로 저장했다.

```
resources/textures/laser/
    LaserProp_Emitter.png          #201 붉은 장치   -> 발사체
    LaserProp_Receiver.png         #202 초록 장치   -> 수신체
    LaserProp_CrystalOctagon.png   #203 팔각       -> OCTAGON
    LaserProp_CrystalTriangle.png  삼각뿔          -> TRIANGLE
    LaserProp_CrystalCross.png     십자            -> CROSS
    LaserProp_CrystalTee.png       T자             -> TEE
    LaserProp_Relay.png            T자 변형        -> 중계체
    LaserProp_Skull.png            해골            -> 해골
```

배경을 투명으로 만든 것이 중요하다. 흰 사각형이 남으면 칸 색을 통째로 덮어
**놓을 수 있는 자리와 테두리 구분이 사라진다.**

FLOWER(꽃)는 시트에 그림이 없다. prop 은 만들어 두었고, 비워 두면 색으로 그려진다.

### 3.3 prop 을 부품별로 늘렸다

| prop | 부품 |
|---|---|
| `crystalTriangleTexture` / `crystalOctagonTexture` / `crystalCrossTexture` / `crystalTeeTexture` / `crystalFlowerTexture` | 크리스탈 종류별 (§4.1) |
| `emitterTexture` / `receiverTexture` | 발사체 / 수신체 |
| `relayTexture` / `skullTexture` | 중계체 / 해골 |
| `crystalTexture` | 종류별 그림이 없을 때의 기본 |
| `fixedCrystalTexture` | 고정 크리스탈 전용. 없으면 종류별 그림으로 떨어진다 |

그림 선택은 **색 선택 옆에 나란히** 두었다(`getCrystalTexture()` / `getGimmickTexture()`).
판 위·트레이·끌고 있는 중 어디서나 같은 그림이 나온다 - 집기 전에 무엇인지 알 수 있어야 한다.

**방향 표시는 그림과 별개로 계속 얹힌다.** 같은 T자라도 어느 변이 막혔는지는 무늬 테두리와
글자 회전이 알려 준다(`EBoardCellGlyph`). 그림 한 장으로 네 방향을 다 그리지 않아도 된다.

## 4. 정렬 — 판이 가로 가운데로 오지 않았다

> "보드판이 중앙에 위치하지 않아, 가로방향의 중앙에 위치하도록 수정"

### 4.1 원인 — 쓰지 않는 케이스가 오른쪽에 몰려 있었다

테이블은 케이스를 언제나 8개 만들고 **앞에서부터** 활성으로 표시한다(`createCases`).
격자는 8열로 고정해 두고 남는 열을 `isVisible: false` 로 숨겼는데, 숨긴 열이 전부
오른쪽에 몰리므로 **보이는 판이 왼쪽으로 치우쳤다.**

```
활성 6개일 때
이전   [1][2][3][4][5][6][ ][ ]   ← 오른쪽 두 칸이 빈자리, 판이 왼쪽으로
지금      [1][2][3][4][5][6]      ← 격자를 6열로 만들어 가운데 정렬
```

### 4.2 고친 방법 — 격자를 활성 케이스 수만큼만 만든다

레벨을 열 때 활성 케이스를 세어, 열 수가 달라졌으면 `resetLayout()` 으로 격자를 다시 잡는다.
격자는 보드 영역 안에서 이미 가운데 정렬이므로 **남는 자리가 좌우로 똑같이 나뉜다.**
칸 번호 ↔ 케이스 index 변환도 그 열 수를 쓰도록 인스턴스 메서드로 옮겼다
(모듈 함수는 8을 상수로 물고 있어 쓸 수 없다).

## 5. 연결 — 시작과 끝 지점을 구분할 수 있게

> "이 퍼즐은 시작점과 끝지점에 대한 식별이 너무 어려워, 시작과 끝 지점을 잘 알 수 있게
> 구별점을 만들어줘"

### 5.1 색만으로는 짝을 찾을 수 없었다

전구는 색으로만 구분됐다. 색약이거나 화면이 작으면 빨강과 주황, 파랑과 남색이 붙어 보인다.
게다가 **전구와 "그리다 만 선의 머리" 가 같은 테두리**를 써서, 선 끝이 전구처럼 보였다.

### 5.2 세 가지를 더했다

1. **짝 글자** — 같은 색 두 전구가 같은 글자를 단다 (`A` ... `A`). 색이 아니라 글자라
   어떤 조건에서도 읽힌다. 글자는 **판에 나온 순서**로 붙여, 쓰지 않는 색 때문에
   글자가 건너뛰지 않게 했다 (빨강·파랑만 쓰는 판도 A·B 로 이어진다).
2. **출발 표시** — 출발 지점에는 `*` 가 하나 더 붙는다 (`A*` ↔ `A`).
   데이터에 이미 `ENodeRole.START / END` 가 있었는데 화면에 드러나지 않고 있었다.
3. **테두리를 전구에게 돌려줬다** — 그리는 중인 머리에서 테두리를 뺐다. 머리는
   떠오르고 빛나는 연출(`GRABBED`)로 충분히 구분되고, 이제 **테두리 = 전구**가 된다.

선이 지나간 칸에는 글자를 달지 않는다. 달면 판이 글자로 뒤덮여 오히려 읽기 어렵다.
글자색은 어둡게 두어 노랑·연두 전구 위에서도 읽힌다.

출발/도착에 서로 다른 그림을 넣고 싶으면 `nodeStartTexture` / `nodeEndTexture` prop 을 쓴다.
비워 두면 공통 `nodeTexture` 로 떨어진다.
