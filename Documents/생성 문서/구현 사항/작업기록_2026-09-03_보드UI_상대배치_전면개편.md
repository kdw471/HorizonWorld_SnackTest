> 신고: "로그는 맞는데 실제로 그려지는 건 판이 화면의 40% 밖에 안 된다. 참고 HTML 처럼 나오게 처음부터 다시 짜 달라"

## 1. 측정으로 확정한 것

`showLayoutProbe` 스크린샷(iPhone, 실제 1179x2556)에서 전부 확인했다.

| 표식 | 스타일 | 결과 |
|---|---|---|
| 7:3 분할 | `flex: 7` / `flex: 3` | 경계가 화면 세로의 **69.5%** ✅ |
| **A** | `height:'100%'` + `aspectRatio:1` + `maxWidth:'100%'` | 923x923 **정사각형**, 영역 안에 정확히 들어옴 ✅ |
| **B** | `height:'60%'` + `aspectRatio:1` | 363x363 정사각형 ✅ |
| **C** | `width:'20%'` | 187 = 영역 폭의 정확히 1/5 ✅ |
| A 안의 4×4 | 행 `flex:1` + 칸 `flex:1` | 16칸 모두 231x231 ✅ |
| **D** | `width: 100` 고정 | 화면에 **실측 약 100 픽셀** |

**D 가 원인을 확정했다.** 패널 좌표 1 단위 = 디바이스 실픽셀 1 인데,
`player.screenWidth/screenHeight` 는 **긴 변을 1280 으로 정규화한** 값을 준다 —
1179x2556 폰이 590x1280 으로 읽혔다. 즉 읽기값으로 계산한 픽셀은 실제의 **절반**으로
그려진다. 보드가 화면의 40% 밖에 못 쓰던 이유가 이것이다.

**A 가 설계를 확정했다.** `maxWidth` 가 `aspectRatio` 를 제대로 눌러 CSS 의
`min(가로, 세로)` 와 같이 동작하므로, 화면 방향에 따른 분기 없이 정사각형을 만들 수 있다.

## 2. 새 구조

```
루트 (세로 흐름, 100% x 100%)
├─ 위 여백    height: topInsetPercent%      ← 상태바·노치·호라이즌 버튼 + 퍼즐 제목
├─ 본 격자    flex: 7                       ← 그 안에 정사각형 보드
│   └─ 보드   height:94% + aspectRatio:1 + maxWidth:96%
│        └─ 격자 상자  width/height = 판 비율 %
│             └─ 행 flex:1 → 칸 flex:1
├─ 보조      flex: 3                        ← 트레이 · 미니격자 · Reset
└─ 아래 여백  height: bottomInsetPercent%    ← 홈 인디케이터 + Menu 버튼
```

### 요령 1 — 정사각형은 `aspectRatio` + `maxWidth` 한 줄

세로를 꽉 채우되 가로가 모자라면 가로에 맞춘다. 세로 화면이면 `boardWidthPercent` 가,
가로 화면이면 `boardHeightPercent` 가 자동으로 이긴다.

### 요령 2 — 정사각형 부모 안에서는 `width:'x%'` 와 `height:'x%'` 가 같은 길이

칸은 판 모양과 무관하게 **언제나 정사각형**이어야 하는데, `aspectRatio` 는 `Bindable` 이
아니라 레벨마다 바꿀 수 없다. 대신 격자 상자를

```
width  = 100 × colCount / max(rowCount, colCount) %
height = 100 × rowCount / max(rowCount, colCount) %
```

로 준다 (`computeGridBox`). 부모가 정사각형이므로 두 퍼센트가 같은 길이 단위가 되고,
그 안에서 행·칸을 `flex: 1` 로 나누면 칸이 정확히 정사각형으로 떨어진다.
4행 8열이면 100%x50%, 9행 3열이면 33.3%x100% 다. 둘 다 `Bindable` 이라 레벨마다 갈아 끼운다.

### 픽셀이 남는 곳 — 글자와 테두리뿐

`fontSize`/`borderWidth`/`borderRadius` 는 `horizon/ui` 에 상대 단위가 없어 숫자여야 한다.
그 숫자만 `screenPixelRatio` prop(실측 2)을 거쳐 환산한다. **배치는 이 값을 쓰지 않으므로**,
배율이 틀린 기기에서도 판과 트레이는 정확히 그려지고 글자만 조금 크거나 작아진다.

예전에는 화면 좌표로 띄웠는데 그 좌표가 화면 픽셀과 달라 판 위로 올라와 칸을 가렸다.
지금은 **아래 여백 띠 안의 흐름 배치**라 어떤 화면에서도 판을 가리지 않는다.

## 5. 개편 직후 잡은 버그 — 필드 초기화에서 `this.props` 를 읽으면 안 된다

에디터에 올리자마자 컴포넌트가 아예 만들어지지 않았다.

```
Failed to instantiate script component definition `PuzzleBoardUIPanel`:
TypeError: Cannot read properties of undefined (reading 'screenPixelRatio')
```

원인은 클래스 **필드 초기화 순서**다.

```ts
private readonly _cellFontSize = this._cellSide.derive((side) => this.cellFontSize(side));
```

`derive` 는 초기값을 만들려고 콜백을 **그 자리에서 한 번 부른다.** 그 콜백이
`cellFontSize()` → `pxScale` → `screenUnitsHeight` → `this.props.screenPixelRatio` 를 탔는데,
필드 초기화 시점에는 `this.props` 가 아직 `undefined` 다. 개편 전에는 같은 경로가
`this._canvas`(필드)만 봤기 때문에 드러나지 않았다.

**고친 방법**: 배율을 필드(`_pixelRatio`)에 담고 기본값은 상수
(`DEFAULT_SCREEN_PIXEL_RATIO`, prop 기본값과 같은 2)에서 가져온다. prop 은
`resolveLayout()` 에서 **한 번만** 읽어 그 필드에 넣는다. 같은 함정을 두 번 밟지 않도록
`cellGapValue` 도 `this.props` 가 없을 때 상수로 떨어지게 해 두었다.

> **규칙**: 클래스 필드 초기화(그리고 거기서 불리는 어떤 것도)에서 `this.props` 를 읽지
> 않는다. prop 이 필요하면 `preStart()`/`initializeUI()` 에서 읽어 필드에 담는다.
> 이것을 어기면 컴포넌트가 **부분적으로 깨지는 것이 아니라 아예 만들어지지 않는다.**

## 6. 남은 것

- **실기 확인.** 계산과 테스트는 끝났지만 실제 화면은 아직 못 봤다. `showLayoutProbe` 를
  끄고 퍼즐을 한 판 띄워 확인한다.
- **허브 패널(`PuzzleUI_MainPanel`)의 단위 문제는 뒤이어 고쳤다** —
  `버그수정_2026-09-03_허브UI_글자크기와_상세화면_정렬.md`. 다만 고친 것은 **단위와 정렬**이고,
  배치를 보드처럼 퍼센트·flex 로 다시 짠 것은 아니다. 절대 배치 7곳은 그대로 남아 있다.
- `PuzzleUI_Layout.ts` 의 픽셀 계산 함수들(`computeBoardGeometry`, `computeGridPixels`,
  `computeSafeAreaPixels`, `verticalPixels`...)은 **허브 패널이 아직 쓰고 있어 남겨 두었다.**
  허브까지 옮기면 함께 지운다.
