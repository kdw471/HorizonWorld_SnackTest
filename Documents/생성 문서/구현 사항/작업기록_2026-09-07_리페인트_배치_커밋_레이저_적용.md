## §1 검토 - 제안과 API 의 한계

### 1.1 출발점

원 제안은 "한 프레임 안의 결과를 캐싱했다가 프레임이 끝날 때 **브리지 호출 1회 · `UpdateBinding::Send` 1회**
로 서버 값을 갱신하자" 였다. 방향은 맞지만 목표치 "1회" 는 `horizon/ui` 에서 도달할 수 없다.

- `horizon/ui` 에는 배치·트랜잭션 API 가 없다. `types/horizon_ui.d.ts` 의 `Binding` 은 `set()` · `reset()` · `derive()` 뿐이고,
  전송 단위는 언제나 **바인딩 키 하나**다.
- `UpdateBinding::Send` 는 브리지 호출과 별개의 두 번째 비용이 아니라, 바인딩 set 이 타는 브리지 호출 그 자체다.
  Perfetto 에서 `ScriptingRuntime::Bridge` 와 `CustomUI::UpdateBinding::Send` 가 똑같이 462회인 이유다.
- 칸의 색·글자·투명도·테두리는 각각 `Bindable` prop 이라 각각 키가 필요하다. 칸 전체를 `Binding` 하나에 담아도
  prop 마다 `derive()` 가 붙고, 파생 바인딩은 저마다 별도 키로 등록되어 별도 Send 가 나간다.
  따라서 이론적 하한은 "값이 실제로 바뀐 prop 의 수" 이지 1 이 아니다.

### 1.2 무엇이 가능한가

곱셈의 두 인수(21 × 22) 가운데 **곱해지는 수 21** 은 프레젠터 안에서 없앨 수 있다.

- `PuzzleBoardPresenter.setCell()` 은 `applyCellPatch()` 로 값 변화를 확인한 뒤 **즉시** `CELL_CHANGED` 를 낸다.
  패널은 그 즉시 `Binding.set()` 을 부른다.
- `Laser_CoreAPI.applyBoardVisuals()` 는 바탕 49칸을 리셋한 뒤 광선·기믹·크리스탈을 겹쳐 그린다.
  최종값이 그대로인 기믹·광선 칸도 "바탕으로 리셋 → 원래대로" 두 번 나간다. 실제로 바뀐 칸은 한두 개인데 21번이 나갔다.
- 배치 중에는 publish 만 미루고, 패스 끝에 시작 시점과 최종값을 비교해 달라진 칸만 알리면
  덧칠 로직(앞 프레임의 광선·실루엣을 지우는 데 필요하다)은 그대로 둔 채 새는 것만 막을 수 있다.

### 1.3 "프레임 종료 시점" 이 아니라 "페인트 패스 종료 시점" 인 이유

실제 프레임 끝(`World.onUpdate` 나 `async.setTimeout(…, 0)`)으로 미루지 않고, 페인터가 끝나는 지점에서 동기적으로 flush 한다.

- 한 이벤트 턴 안의 set 은 이미 렌더 한 번으로 합쳐진다 (트레이스의 `CustomUIStateService::Update` 1회).
  비용은 set 마다 건너는 브리지이므로 동기 flush 만으로 같은 절감을 얻는다.
- 프레임 끝으로 미루면 최대 1프레임(약 14 ms)의 표시 지연이 생겨 "거의 즉시 피드백" 규칙과 충돌한다.
- 프레젠터에 `horizon/core` 타이머 의존이 들어가 순수 계층 원칙(PUZ_00 §7.1)이 깨지고,
  `Pressable` 콜백과 `onUpdate` 의 같은 프레임 내 순서가 보장되지 않는다.

### 1.4 사전 확인 사항

| 확인 | 결과 |
|---|---|
| `setCell()` / `setItem()` 반환값을 쓰는 호출자 | 8개 CoreAPI · 드래그 컨트롤러 어디에도 없다. 배치 중 반환 의미가 "스냅샷이 바뀜" 으로 달라져도 영향 없음 |
| `applyCellPatch()` 의 객체 취급 | 바뀔 때 새 객체를 만들고 이전 객체를 건드리지 않는다. 첫 패치 직전의 객체 참조가 그대로 baseline 이 되므로 복사 불필요 |
| 최종 비교 함수 | `isSameCellView()` / `isSameItemView()` 가 `PuzzleBoardUI_Definitions` 에 이미 있다 |
| 레이저의 재진입 | `_isReleaseCoalescing` 이 릴리즈 턴의 `BEAM_UPDATED` 를 막고 있어 현재 중첩은 없다. 그래도 카운터 방식으로 방어 |
| 다른 퍼즐의 덧칠 구조 | 러시아워 `applyGridVisuals()` 가 81칸 바탕 리셋 → 길 → 말 순서로 같은 구조. ColorSort·Flow 는 칸당 한 번만 최종값을 쓰는 단일 패스, 나머지 4개는 칸 단위 지정 갱신이라 얻는 것이 없다 |

## §2 구현

### 2.1 `PuzzleBoardUI_Presenter.ts` - 배치 API

```ts
presenter.runBatch(() => { /* 페인트 패스 */ });   // 권장 - try/finally 로 반드시 닫힌다
presenter.beginBatch(); … presenter.endBatch();       // 직접 열고 닫을 때
presenter.isBatching                                  // 진단용
```

동작 규칙:

- `_batchDepth > 0` 이면 `setCell()` · `setSideCell()` · `setItem()` 은 스냅샷만 갱신하고 이벤트를 내지 않는다.
  `applyCellPatch()` 의 "같은 값이면 객체를 만들지 않고 빠져나가기" 는 그대로라 GC 압박도 그대로 낮다.
- 배치 안에서 어떤 자리가 **처음** 바뀔 때 그 직전의 스냅샷 객체를 `_cellBaselines[index]` 에 넣고 `_touchedCells` 에 번호를 적는다.
  두 번째 이후의 패치는 baseline 을 건드리지 않는다.
- 가장 바깥 배치가 닫히면(`flushBatch`) 건드린 자리마다 baseline 과 현재값을 `isSameCellView` 로 비교해 다를 때만
  `CELL_CHANGED` 를 낸다. 순서는 **건드린 순서**다. 보조 격자(`SIDE_CELL_CHANGED`)와 트레이(`ITEM_CHANGED`)도 같은 규칙이다.
- `runBatch()` 는 `try/finally` 로 닫는다. 페인터가 예외를 내면 깊이가 걸린 채 남아 **이후의 모든 UI 갱신이 조용히 멈추기** 때문이다.
  그때까지의 변경은 정상적으로 알린다.
- 중첩은 카운터로 센다. 안쪽이 닫혀도 바깥이 열려 있으면 미룬다.
- 짝 없는 `endBatch()` 는 영어 경고를 남기고 무시한다.
- `resetLayout()` 은 배치 버퍼를 버린다. 옛 뷰를 가리키던 baseline 은 의미가 없고, `LAYOUT_CHANGED` 가 새 뷰를 통째로 그리게 하므로
  그 뒤에 오는 `setCell` 만 새 버퍼에 기록되면 된다.
- baseline 배열은 규격 크기로 한 번만 잡는다 (`resetBatchBuffers` - 생성자와 `resetLayout` 에서). 드래그 중 할당이 없다 (방법론 §4.4).
- `PRESS_CHANGED` 는 이미 비교 후 발행이라 건드리지 않았다.

### 2.2 `Laser_CoreAPI.ts` - 적용

`applyBoardVisuals()` 본문(바탕 → 광선 → 기믹 → 크리스탈 → 드래그 → 인벤토리)을 `this._presenter.runBatch(() => { … })` 로 감쌌다.
호출 지점 6곳(레벨 로드 · 집기 · 드래그 전환 · 릴리즈 · 리셋 · `BEAM_UPDATED`)은 손대지 않았고,
더티 필터(`_repaintFilter`)와 릴리즈 코얼레싱(`_isReleaseCoalescing`)도 그대로다.
배치는 그 둘과 직교한다 - 더티 필터는 "어느 칸을 기록할지", 코얼레싱은 "패스를 몇 번 돌릴지", 배치는 "한 패스 안에서 무엇을 내보낼지" 를 정한다.

### 2.3 `PuzzleBoardUI_Tests.ts` - `testPresenterBatch` 14건

| 검사 | 기대 |
|---|---|
| 배치 밖의 갱신 | 즉시 알린다 |
| 배치 중 | 이벤트가 나가지 않는다 |
| A → B → A | 이벤트 0회, 스냅샷은 최종값 |
| A → B → C | 최종값으로 1회 |
| 여러 칸 | 바뀐 칸마다 1회, 건드린 순서대로 |
| 중첩 | 가장 바깥이 닫힐 때 알린다 |
| 페인터 예외 | 배치가 닫히고(`isBatching === false`) 그때까지의 변경은 알린다. 이후 갱신은 즉시 |
| 짝 없는 `endBatch` | 무시된다. 이후 갱신은 즉시 |
| 배치 중 `resetLayout` | 옛 칸은 버리고 새 칸만 알린다 (`LAYOUT_CHANGED` 1회) |
| 트레이 슬롯 · 보조 격자 | 달라진 것만 1회 |

테스트 작성 중 잡힌 것 하나: 콜백 안에서 대입하는 `let lastCell: T | undefined = undefined` 는 TS 가 제어 흐름 분석으로
`never` 로 좁혀 버린다 (클로저 안의 대입은 보지 않는다). `{ cell: T | undefined }` 홀더 객체로 바꿨다.

## §4 인월드 테스트에서 볼 것 (미실시)

기대값 (Send 횟수 / 프레임, 칸당 22키 기준):

| 프레임 | 적용 전 | 기대 |
|---|---|---|
| 집기 (판 위 크리스탈) | 462 | 약 22 (실루엣이 되는 원래 칸 1) |
| 집기 (트레이에서) | 462 | 약 47 (트레이 슬롯 약 25 + 미리보기 칸 0~1) |
| 드래그 이동 | 44 | **44 그대로** - 더티 필터가 이미 두 칸으로 줄여 놓았고 두 칸 다 실제로 바뀐다 |
| 드롭 | 462 | (광선이 바뀐 칸 + 놓은 칸 + 트레이 슬롯) × 22 |

절차:

1. Perfetto 로 드롭·집기 프레임을 잡아 `CustomUI::UpdateBinding::Send` 횟수를 센다 (가이드 분석 §3.4 마커표).
2. 22 의 배수인지 본다. 배수가 맞으면 "파생은 값과 무관하게 전부 나간다" 는 전제(가이드 분석 §5 각주)가 확정된다.
3. 손을 뗀 뒤 광선·기믹·실루엣이 정확히 지워지는지 본다. 덧칠 로직은 손대지 않았지만 이벤트 순서가
   "건드린 순서" 로 바뀌었으므로, **화면 결과가 같은지** 가 이번 테스트의 핵심이다.
