## §1 샘플과 우리 경로의 비교

| 항목 | 브라우저 샘플 | 우리 (수정 전) | 판정 |
|---|---|---|---|
| 이동 입력 | `pointermove` 연속 좌표 + `setPointerCapture` (요소 밖으로 나가도 그 요소가 계속 받는다) | 러시아워·레이저만 `continuousDrag` prop(기본 **꺼짐**)으로 Focused Interaction 스트림. 연결·정렬은 칸 `Pressable` 의 `onEnter` 만 - 칸 경계에서만 반응 | **차이** |
| 잡기 기준점 | `pointerdown` 의 `clientX/Y` - **실제 손가락 위치** | 칸 `Pressable` 이 알려 준 **칸 중심(정수)**. 뒤이은 스트림 좌표는 연속이라 칸 가장자리를 잡으면 첫 move 만으로 반 칸을 넘겨 한 칸 튄다 | **차이** |
| 위치 계산 | `initial + round(delta / cell)` - 잡은 오프셋 유지 | 러시아워 동일(`beginValue + delta`). 레이저는 절대 좌표(1×1 이라 무방) | 같음 |
| 충돌 한계 | 매 move 마다 다른 블록을 훑어 min/max (싸다) | 잡을 때 한 번 `recomputeRange`, 이후 클램프만 | 같음(더 낫다) |
| 잡는 순간 피드백 | `classList.add('grabbing')` - 그 요소만 | 러시아워 **81칸 전체 리페인트**, 레이저 **49칸+광선+기믹+트레이 전체**. 첫 피드백이 가장 무거운 리페인트 뒤에 나왔다 | **차이** |
| 놓기 | 마지막 move 가 정한 자리에 그대로 (재계산 없음) | 스트림 ended 좌표를 마지막으로 한 번 반영해 스냅 | 같음 |
| 렌더 | DOM style 직접 설정 | 바뀐 칸의 Binding 만 갱신 (더티 필터) | 같음 |

**샘플이 매끄러운 이유는 "연속 좌표 + 실제 터치 기준점 + 가벼운 잡기" 세 가지가 전부 갖춰져
있기 때문이고, 우리 경로에 빠진 것도 정확히 그 셋이었다.** 계산량은 이미 우리가 더 가볍다.

## §2 적용한 것

### 2.1 잡기 기준점을 실제 터치 지점으로 (샘플의 `startX/startY`)

- `Puzzle_HorizonBridge.PuzzleScreenDragStream`
  - `onFocusedInteractionInputStarted` 도 구독한다. 가장 최근 started 좌표를 들고 있다가
    잡기(`notifyDragBegan`)와 만나면 새 콜백 **`onStreamStart(point)`** 로 CoreAPI 에 전한다.
  - started 와 칸 `Pressable` 의 down 은 순서가 보장되지 않는다. 그래서 "가장 최근 값" 규칙이다 -
    잡기가 먼저면 잡을 때 직전 값을 쓰고 뒤따라온 started 가 덮어쓰며, started 가 먼저면
    잡을 때 이미 이번 터치의 값이다. started 가 아예 오지 않으면 **첫 moved** 가 기준점을 대신한다.
  - `setGridSize(rows, cols)` 추가 - 판마다 열 수가 바뀌는 정렬 퍼즐용.
- `RushHour_DragController.rebaseTouchOrigin(row, col)` / `RushHour_Session.rebaseDragOrigin`
  - `_touchOriginRow/Col` 만 옮긴다. 오브젝트 시작값(`_beginValue`)과 이동 범위는 그대로.
  - **아직 움직이기 전에만** 받는다 (`_currentValue === _beginValue`). 움직인 뒤 기준점을 옮기면
    오브젝트가 튀므로 거절한다. NaN 도 거절.
- `RushHour_CoreAPI.onStreamDragStart` 가 위를 잇는다. 레이저는 절대 좌표 방식이라 해당 없음.
- 테스트 5건 추가 (`RushHour_Tests.testDragInteraction`): 보정 전/후, 움직인 뒤 거절, NaN 거절,
  드래그 중 아님 거절.

### 2.2 잡는 순간의 리페인트를 바뀌는 칸으로 좁힘 (샘플의 `grabbing` 클래스)

| 퍼즐 | 수정 전 | 수정 후 |
|---|---|---|
| 러시아워 | 81칸 전체 | 발자국(GRABBED) + 이 축의 길(PATH) - `applyDragFocusedVisuals()`, 릴리즈 더티 수집(`collectReleaseDirtyCells`)과 같은 범위 |
| 러시아워 1×1 축 확정 | 81칸 전체 | 원래 자리 + 이전/새 미리보기 자리 + 길 |
| 레이저 (판에서 집기) | 49칸+광선+기믹+트레이 | 크리스탈이 있던 그 칸 하나 - `applyDragTransitionVisuals(undefined, undefined)` |
| 정렬 | 케이스 전체 | 출발 케이스 한 열 - `applyCaseVisual(fromCase)` |

### 2.3 연결·정렬에도 스트림 배선, 넷 다 기본 켬

- `Flow_CoreAPI` / `ColorSort_CoreAPI` 에 `continuousDrag` prop · 스트림 · `enterPuzzleTouchStream`
  진입/이탈 · `onStream*` 핸들러를 러시아워와 같은 구조로 넣었다. 칸 단위 경로는 폴백으로 남는다.
  - 연결: 반올림한 칸이 바뀔 때만 `trackDrawTo` (기존 보간 로직 그대로). 격자 밖은 무시.
  - 정렬: **열만 반올림**해 케이스로 본다. 세로는 격자 위아래 한 칸까지 너그럽다 - 건전지를 들어
    올려 케이스 위 허공에서 놓는 자연스러운 손짓에 "영역 밖 드랍"(2초 잠금)을 물리지 않기 위해서다.
    열 수가 바뀌면 `resizeGridToActiveCases` 가 스트림에도 `setGridSize` 로 알린다.
- `continuousDrag` 의 **기본값을 넷 모두 `true`** 로 바꿨다. 기기 실험이 끝났고 목표 조작감이
  곧 규격이므로 이제는 끄는 쪽이 예외다. 에디터에서 이미 값을 명시한 엔티티는 그 값이 유지된다 -
  **기존 러시아워·레이저 엔티티에 `false` 가 박혀 있으면 직접 켜야 한다.**

## §3 하지 않은 것과 이유

- **칸 안 소수 오프셋으로 조각을 미는 직접 조작** - 09-04 기록 §3.6 에서 기기에서 기각됐다.
  샘플도 사실 `Math.round` 로 칸 단위 배치를 한다 - 매끄러움은 픽셀 추종이 아니라 위의 세 가지에서
  온다. 다시 시도하지 않는다.
- 레이저의 델타 방식 전환 - 1×1 크리스탈은 손가락 아래 칸이 곧 목표라 절대 좌표가 맞다.

## §3.5 샘플 대비 자체 검토에서 고친 것

- **앞 터치의 시작점이 다음 잡기에 새는 문제** - 스트림이 `_lastStartInfo` 를 지우지 않아,
  이번 터치의 started 가 안 오거나 늦으면 앞 터치의 좌표가 기준점이 되어 조각이 엉뚱하게 튈 수
  있었다. `handleEnded` 에서 지운다 (샘플의 `startX` 가 `pointerdown` 마다 새로 잡히는 것과 같다).
- **결합된 USB 를 잡을 때 슬롯 칸이 안 지워지는 문제** - 좁힌 잡기 리페인트가 발자국(2칸)만
  다뤄, 3칸째(슬롯)가 직전 그림으로 남았다. `getGoalOccupiedCellsInFullGrid` 를 더티에 더한다.
- 검토했으나 그대로 둔 것: 스트림이 driving 인 드래그는 칸 단위 `onCellUp` 이 마감하지 않는다 -
  Focused Interaction 의 `inputEnded` 는 유실되지 않는다는 전제(09-04 실험) 위에 서 있다.
  퀘스트 종료 뒤 Focused Interaction 모드 해제는 허브의 `disconnectQuest -> abort()` 가 맡는다
  (연결·정렬도 이제 같은 경로).
