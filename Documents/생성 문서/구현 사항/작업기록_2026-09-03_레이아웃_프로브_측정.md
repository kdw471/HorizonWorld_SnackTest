# 작업기록 2026-09-03 — 레이아웃 프로브: 상대 배치가 실기에서 어떻게 그려지는지 재기

> 신고: "로직 수정 후에도 보드가 화면의 40% 밖에 안 된다. 로그는 맞게 나오는데 화면은 다르다" (스크린샷)
> 관련 문서: `작업기록_2026-09-03_캔버스_실해상도_전환.md`, `작업기록_2026-09-03_보드_정사각형_규격.md`
> 이 문서는 **고치는 기록이 아니라 재는 기록**이다. 배치를 상대 배치로 다시 짜기 전에
> 그 전제를 실기 스크린샷 한 장으로 확정하는 것이 목적이다.

---

## 1. 지금까지의 가정이 틀렸다는 증거

`showLayoutDebug` 로그 두 개를 대조하면 나온다.

```
이전: screen 590x1280 | canvas 590x1280 portrait Mobile | board 531x723 | cell 75 | area 8/64/28
이후: screen 590x1280 | canvas 590x590  portrait Mobile | box 590 full 590x1280
      | board 531@30 (margin 30) | cell 75 | aux 165@579
```

숫자 자체는 전부 계산대로다. 짧은 변 590 기준으로 여백 5% = 30, 보드 90% = 531,
틈 3% = 18 이라 `auxTop` 이 30+531+18 = 579, 보조 레이아웃이 28% = 165. 전부 맞는다.

**그런데 `panelHeight` 를 1280 에서 590 으로 절반 이하로 줄였는데 화면에 그려지는 크기가
전혀 변하지 않았다.** 보드는 여전히 화면 폭의 40% 대다. `PuzzleUICanvas` 머리말에 적어 둔
가정 — *"`panelHeight` 가 정사각 레이아웃 상자의 좌표 해상도를 정한다"* — 은 이것으로
반증되었다. 그 가정이 맞았다면 축척이 두 배로 뛰었어야 한다.

반대로 **상대 배치는 정상 동작한다.** 두 가지가 증거다.

- 루트 View 의 `width: '100%', height: '100%'` 배경은 화면을 정확히 꽉 채운다.
- 격자 안쪽 행·칸은 이미 `flex: 1` 인데, 스크린샷에서 고르게 나뉘어 있다.

즉 **`%`·`flex` 는 믿을 수 있고, `screenWidth/screenHeight` 에서 뽑은 절대 픽셀은 믿을 수
없다.** 그런데 `PuzzleUI_Layout.ts` 885줄 전체가 후자 위에 서 있다. 최근 수정들이 전부
"픽셀 매핑 규칙 추측 → 실기 확인 → 다시 추측" 이었던 이유가 이것이다.

## 2. 지금 서 있는 가설 — 읽기값의 **단위**가 바뀌었다

`작업기록_2026-09-03_캔버스_실해상도_전환.md` 는 같은 폰을 **1179x2556** 으로 읽었다고
기록하고 있다. 그런데 이번 로그의 읽기값은 **590x1280**, 거의 정확히 그 절반이다.

여기서 나오는 가설: **Screen Overlay 는 실제 디바이스 픽셀(≈1180 폭)로 그리는데,
`player.screenWidth/screenHeight` 는 그 절반인 논리 포인트를 돌려주고 있다.**

이 가설은 관측과 맞아떨어진다. 보드 영역은 `left: 0, width: '100%'` 에 가운데 정렬이므로,
좌표계 가로가 1180 이라면 531 짜리 보드의 왼쪽 끝은 (1180−531)/2 = 324, 즉 **화면 폭의
27% 지점**이고 오른쪽 끝이 73% 다. 스크린샷의 보드 위치가 정확히 그렇다.

다만 이것은 아직 **가설**이다. 프로브의 표식 **D** 가 이 값을 직접 재서 확정한다.

## 3. 프로브가 재는 것

`PuzzleUI_LayoutProbe.ts` 를 추가했다. 상대 배치만으로 그린 측정용 화면이고, 입력을 받는
노드가 하나도 없다.

| 표식 | 스타일 | 통과 조건 |
|---|---|---|
| 위/아래 두 색 영역 | `flex: 7` / `flex: 3` | 경계가 화면 세로 70% 지점 (왼쪽 눈금 7칸째 끝) |
| **A** (노랑) | `height: '100%'` + `aspectRatio: 1` + `maxWidth: '100%'` | **정사각형**이고 위 영역 **안에** 들어온다 |
| **B** (초록) | `height: '60%'` + `aspectRatio: 1` | 정사각형 |
| **C** (분홍) | `width: '20%'` | 아래 영역 가로의 정확히 1/5 |
| **D** (흰색) | `width: 100, height: 100` 고정 | **화면 폭 대비 몇 % 인지 재면 좌표계 크기가 나온다** |
| A 안의 4×4 | 행 `flex: 1` + 칸 `flex: 1` | 16칸이 모두 같은 정사각형 |
| 왼쪽 세로 눈금 | 10칸 `flex: 1` | 10등분 — 위 항목의 위치를 읽는 자 |

**D 가 핵심이다.** D 가 화면 폭의 x% 를 차지하면 좌표계 가로 = 100 ÷ x × 100 이다.
8.5% 면 ≈1180 (§2 가설 확정), 17% 면 ≈590 (읽기값이 맞고 다른 원인), 그 밖이면 제3의 규칙이다.

## 4. 결과를 어떻게 쓰는가

| 관측 | 결론 | 다음 작업 |
|---|---|---|
| A 가 정사각형 + 영역 안 | `maxWidth` 가 `aspectRatio` 를 제대로 누른다 | 보드를 `height:'100%' + aspectRatio:1 + maxWidth:'100%'` 한 줄로. 화면 비율 분기 불필요 |
| A 가 좌우로 삐져나감, B 는 정사각형 | `aspectRatio` 는 되고 `maxWidth` 조합만 안 된다 | **화면 비율**(절대 픽셀 아님)로 `width:'100%'` / `height:'100%'` 를 분기 |
| A·B 둘 다 정사각형이 아님 | 좌표계가 화면에 **비균일하게** 늘어난다 | `aspectRatio` 를 쓸 수 없다. 정사각형은 비율 계산으로 직접 만든다 |
| 7:3 경계가 70% 가 아님 | `flex` 비율을 못 믿는다 | 상대 배치 재작성 자체를 재검토 |
| C 가 1/5 이 아님 | 퍼센트 폭을 못 믿는다 | 위와 같다 |

A·B·C·7:3 이 모두 통과하면 재작성은 사실상 기계적인 작업이 된다. 입력이 **칸마다
`Pressable`** 이라 포인터 좌표 계산을 하지 않기 때문이다 — 배치를 픽셀에서 퍼센트로
바꿔도 드래그·놓기 로직은 손댈 곳이 없다.

## 5. 켜는 법

에디터에서 **보드 패널(`PuzzleBoardUIPanel`) 의 `showLayoutProbe` 를 켠다.**
게임 화면 대신 프로브만 뜬다 — 다른 노드가 섞이면 측정이 흐려지기 때문이다.
화면 아래에는 `showLayoutDebug` 와 같은 실측값 한 줄이 함께 뜨므로, 스크린샷 하나에
"코드가 믿는 숫자" 와 "실제로 그려진 모습" 이 같이 담긴다. 재고 나면 다시 끈다.

## 7. 재작성 범위 (계획 — 실제 결과와 다른 두 곳은 아래에 적어 두었다)

참고 구조는 `../../SampleHtml/index.html` 이다. CSS 의 `flex: 7 / 3`,
`aspect-ratio: 1`, `repeat(N, 1fr)` 가 `horizon/ui` 에 거의 1:1 로 옮겨진다.

| 구분 | 대상 |
|---|---|
| 버린다 | `PuzzleUI_Layout.ts` 의 픽셀 계산 축 — `computeBoardGeometry`, `computeBoardSquare`, `computeGridPixels`, `computeSafeAreaPixels`, `fitBoardAreaToCanvas/Profile`, `verticalPixels`, `PuzzleUICanvas.fullWidth/fullHeight` **(실제로는 보드 패널에서만 떼어 냈다.** 허브 패널이 아직 쓰고 있어 모듈 자체는 남겼다 — 허브를 옮길 때 함께 지운다) |
| 그대로 둔다 | 프레젠터·모델·세션·퍼즐 로직 전부, `DynamicList` 슬롯 구조(64kB 한도), 텍스처, 색, **입력·드래그 전부** |
| 고친다 | `PuzzleBoardUI_Panel.ts` 의 `position:'absolute'` 13곳, `PuzzleUI_MainPanel.ts` 의 7곳 |

`horizon/ui` 에 없어서 대체가 필요한 CSS 는 둘뿐이다.

- `gap` — 없다. 칸의 `padding` 으로 (지금의 `inset` 방식 그대로)
- `font-size` 의 상대 단위 — 없다. 기준 해상도 하나를 정해 그 비율로 환산한다
  (실제로는 `screenPixelRatio` prop 이 그 기준이 되었다)

**`padding` 퍼센트에 대한 예외 하나.** Yoga 는 네 방향 여백의 퍼센트를 모두 부모의 *가로*
로 계산한다 (`버그수정_2026-09-02_UI가_화면을_꽉_채우지_않음.md` §8 에 기록된 함정).
그런데 칸과 트레이 슬롯은 **정사각형**이라 가로 기준이 곧 세로 기준이다. 그래서 이 두
곳에서는 퍼센트 여백이 오히려 정확하고, 실제 개편에서도 그렇게 썼다. 정사각형이 아닌
상자에는 여전히 쓰면 안 된다.
