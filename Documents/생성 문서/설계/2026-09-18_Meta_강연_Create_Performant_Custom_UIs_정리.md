# Meta 강연 "Create Performant Custom UIs in Horizon Worlds" 정리

> 대상: Custom UI 의 내부 동작(브리지·RPC·UI 스레드)을 알고 성능 규칙의 **이유**를 이해하려는 사람
> 원문: [Create Performant Custom UIs in Horizon Worlds](https://www.youtube.com/watch?v=Dss5RErTFwg) (YouTube, 약 60분. 발표 Yen, 오프닝 Linda. Meta Custom UI 팀이 파트너 스튜디오 대상으로 한 기술 강연. 2026-09-18 자동 생성 영어 자막으로 정리)
> 관련 문서: `2026-09-07_Horizon_CPU_TypeScript_최적화_가이드_분석.md` (공식 문서의 수치 기준선), `Horizon_실행모드_제약과_규칙.md` (Local 모드 제약과 64 kB 한도), `../구현 사항/버그수정_2026-09-02_보드패널_64kB_한도초과.md` (한도를 실제로 맞은 기록)

**한 줄 요약.** Custom UI 는 TypeScript → Unity(C#) → 클라이언트 JS(React VR) 세 계층을 브리지와 RPC 로 오가며 그려지고, UI 스레드의 리렌더 한 번은 메인 프레임보다 **약 4배 느린 30~50 ms** 다. 그래서 강연이 내리는 규칙은 다섯 가지다. **바인딩 갱신은 4~5 프레임당 1회 이하, 콜백은 2~4 프레임당 1회 이하, 동시에 보이는 패널은 10개 이하, 월드 전체 바인딩은 1,000~1,500개 이하, 바인딩으로 애니메이션을 만들지 않는다.** 바인딩 하나가 바뀌면 그 바인딩을 쓰지 않는 패널까지 **보이는 패널 전부가 리렌더 알림을 받는다**는 점이 가장 중요한 내부 사실이다.

> 강연 시점 주의. 강연은 ScrollView 가 "이번 분기 신규", DynamicList 와 애니메이션 API 가 "계획·알파" 라고 말한다. 우리 프로젝트는 이미 `DynamicList` 를 쓰고 있으므로 강연은 그보다 앞선 시점의 것이다. 수치는 강연 시점의 경험칙이며, 현재 공식 문서의 기준선(set ≤ 10/frame, 0.5 ms)과 다른 곳은 §7 에서 대조한다.

## §2 기억해야 할 수치 (강연 기준)

| 항목 | 값 | 근거 |
|---|---|---|
| 바인딩 갱신 빈도 | 평균 **4~5 프레임당 1회 이하** | 리렌더가 프레임보다 4배 느려 큐가 쌓인다 |
| 콜백 빈도 | **2~4 프레임당 1회 이하** | 콜백 하나가 서버 왕복 RPC 한 번 |
| 동시에 보이는 패널 | **10개 이하** (하드 리밋 없음) | 리렌더 시간이 보이는 패널 수에 비례 |
| 월드 전체 바인딩 총수 | **1,000~1,500개 이하** (플레이어별 복제분 포함) | 초기화 시 전부 RPC 로 전송, 63 kB 한도 |
| RPC 크기 한도 | **63 kB** | 데이터 모델·바인딩 초기 전송이 넘기 쉽다 |
| UI 리렌더 1회 | **30~50 ms** | React 프레임워크 고유 비용 |
| 메인 스레드 프레임 | 72 FPS, 약 13~14 ms | 비교 기준 |
| 바인딩 초기화 | 약 20 ms 급 (트레이스) | 갱신은 트레이스에서 보이지 않을 만큼 작다 |
| 커스텀 애니메이션 지속 | **2초 이내** (발표자는 "2초도 많다") | 4배 느리므로 스레드가 5~6초 어긋난다 |
| 이미지 URL 조회 | 월드 초기화 시 **프레임당 50장** | 너무 많으면 백엔드 실패, 너무 적으면 프레임 낭비 |
| 콜백 왕복 체감 지연 | 약 10 ms 급 | 원격 실행 시 호버 색 변경에서 보임 |
| 내부 렌더 개선 | 렌더 시간 96% 단축 | 제작자 조치 없이 적용됨 |

## §3 1부 · 제작 측 요점

### 3.1 기즈모 UI 전용 설정

- **VR**: 상호작용(손에서 나가는 레이캐스트) 켜기·끄기, 상호작용 거리(기본 3 m). 끄면 버튼이 전부 동작하지 않는다.
- **웹·모바일**: 가까이 가면 뜨는 카메라 포커스 프롬프트(E 키 등)를 켜기·끄기, 프롬프트 표시 거리(기본 2.5). 끄면 카메라가 패널로 줌인하지 않는다.
- **Mipmap**: 작은 글자가 픽셀화되는 현상을 완화한다. 스크린샷보다 실기에서 차이가 크다.

### 3.2 TypeScript API 와 컴포넌트

- 기즈모는 스크립트 없이는 아무것도 하지 않는다. `UIComponent` 를 상속한 클래스의 `initializeUI()` 반환값이 곧 UI 다.
- 컴포넌트는 강연 시점 5종: View, Text, Image, Pressable, ScrollView. 계획으로 언급한 것은 **DynamicList**(배열 길이를 미리 모르는 자식 렌더)와 **Image Background**(absolute 포지션 없이 배경 처리).
- 스타일은 표준 CSS 문법. 렌더링 스택은 React VR(React Native 계열).

### 3.3 스크립팅 기반을 택한 이유와 보완책

- WYSIWYG 편집기보다 스크립팅이 유연성·정밀도·확장성에서 낫다고 판단했다. 게임플레이가 이미 TypeScript 라 UI 와 로직이 같은 언어로 붙는다.
- 스크립팅이 부담스러운 제작자를 위해 **Figma Exporter**(Figma 프로토타입을 TS 코드로)와 **UI Inspector**(2D 에디터 안의 Chrome DevTools 격)를 계획 중이라고 밝혔다.

### 3.4 Binding 이 하이브리드인 이유

React 는 컴포넌트를 함수로 취급해 props 를 넣으면 결과가 나온다. 객체처럼 속성을 뒤집을 수 없다. Horizon 은 여기에 **Binding** 을 얹어 "나중에 바꿀 수 있는 자리표시자" 를 두는 절충을 택했다. 콜백은 버튼 컴포넌트에 TS 함수를 넘기는 방식이다. 사용자 정의 컴포넌트(예: `MyButton`)로 재사용이 쉽다.

### 3.5 멀티플레이어 Binding 과 Local 모드

- **멀티플레이어 Binding**: 같은 기즈모에서 `set` 할 때 대상 플레이어를 지정해 플레이어마다 다른 값을 보인다. 호버 색상처럼 차이가 작을 때 알맞다.
- **Local 모드**: 기본은 서버에서 TS 가 돌고 클라이언트가 그린다. Local 모드는 클라이언트에서 TS 를 돌려 네트워킹 지연을 없앤다. 제약은 둘이다. 로컬 플레이어에게만 보이고, 멀티플레이어 Binding 이 꺼진다.

### 3.6 플레이어별 UI 를 만드는 두 방식

| 방식 | 알맞은 경우 | 예 |
|---|---|---|
| 기즈모 하나 + 멀티플레이어 Binding | 플레이어 간 내용 차이가 작을 때 | 호버 색상 |
| 기즈모를 플레이어 수만큼 복제, 각각 한 명에게만 표시 | 내용이 크게 다르거나 즉각 반응이 필요해 Local 모드가 필요할 때 | 탭별 통계 메뉴, HUD 의 체력바·카운트다운 |

우리 프로젝트는 두 번째 방식이다. 보드·허브 패널이 Local 이고 플레이어별로 소유권을 넘긴다 (`Horizon_실행모드_제약과_규칙.md`).

### 3.7 예고된 기능

- **UI 애니메이션 API**: React Native 애니메이션 라이브러리를 TS 로 노출. 회전·위치·색 등을 체이닝. 강연 시점 스튜디오 2곳과 알파, 수 주 내 출시 예정.
- **스크린 오버레이**: 데스크톱·모바일에서 HUD 를 띄우는 기능. VR 은 기즈모를 플레이어에 부착하면 되지만 크로스 스크린은 카메라가 뒤에 있어 부착이 어색하다. 카메라 포커스 없이 누를 수 있는 버튼 같은 새 상호작용 모델도 함께 개발 중.

## §4 2부 · 아키텍처: 왜 느린가

### 4.1 세 계층과 브리지

```
TypeScript (제작자 API)
   │ 브리지
Unity / C# Horizon 서비스 (런타임·네트워킹)
   │ RPC (몇 프레임 지연, 63 kB 한도)
클라이언트 JS VM → React VR → 패널 렌더
```

- 브리지는 "적당히 비싸다". 목표는 셋이다. **브리지 호출을 줄이고, 네트워킹 횟수를 줄이고, 가능한 한 하류(JS)에서 처리한다.**
- 흔히 브리지라 하면 TS↔Unity 만 떠올리지만 C#↔JS 사이에도 통신이 있다.

### 4.2 콜백 왕복

호버·클릭은 JS 에서 발생한다. 이것이 RPC 로 서버에 가고, 서버가 TS 콜백을 부르고, 콜백이 바인딩을 갱신하고, 그 갱신이 다시 RPC 로 클라이언트에 온 뒤에야 React VR 이 그린다. 왕복 하나가 약 10 ms 급 시각 지연이다.

| 해결책 | 내용 | 상태 |
|---|---|---|
| 1. 콜백 빈도 제한 | 2~4 프레임당 1회 이하. 발표자도 "사용자 입력이라 통제가 어렵다" 고 인정 | 지금 가능 |
| 2. Local 모드 | 왕복이 한 클라이언트 안에서 끝난다 | 지금 가능 |
| 3. Local Event Binding | 기본색·호버색 등을 한 객체로 미리 JS 에 넘겨 TS 개입 없이 처리 | 계획 |

### 4.3 데이터 모델과 Binding 구현

- UI 는 거대한 JSON **데이터 모델**로 직렬화된다. Binding 은 값 대신 **ID** 로 들어간다. 기즈모의 수명 동안 데이터 모델을 바꾸지 않기 위해서다.
- C# 은 데이터 모델과 바인딩을 두 서비스로 따로 보낸다. 클라이언트 JS 는 데이터 모델을 역직렬화하고 바인딩 ID 를 실제 값으로 치환해 React VR 에 넘긴다.
- 그래서 **초기화는 매우 무겁다**. 수십 kB 데이터 모델 + 수백~수천 개 바인딩을 브리지와 RPC 로 보낸다. 둘 다 63 kB 를 넘기 쉽다. **이후 갱신은 값만 보내므로 가볍다.**
- 대응 둘. (1) 의미 없는 컴포넌트·스타일을 지운다. 자식이 하나뿐인 Image 를 View 로 감싸고 `justifyContent: 'flex-start'` 를 주는 것은 몇 바이트지만 "천 개의 종이 베임" 이 된다. (2) 바인딩은 필요할 때만 만든다. "나중에 바꿀지 모르니" 만들어 두지 않는다.

### 4.4 UI 스레드의 세 가지 나쁜 소식

UI 는 Unity 메인 스레드와 **별개의 스레드**에서 그린다. 좋은 소식은 UI 가 막혀도 월드 FPS 는 유지된다는 것이다. 나쁜 소식은 셋이다.

1. **리렌더가 4배 느리다.** 메인은 13~14 ms 에 한 프레임인데 UI 리렌더는 30~50 ms 다.
2. **바인딩 하나가 바뀌면 보이는 패널 전부가 알림을 받는다.** 바인딩은 컴포넌트 밖 어디서나 만들 수 있고 여러 패널이 공유할 수 있다. 그 대가로 어떤 바인딩이 바뀌든 모든 패널의 모든 컴포넌트에 알림이 간다. 각 컴포넌트가 "나는 이 바인딩을 안 쓴다" 고 거절하지만, 알림을 보내는 것 자체가 시간이다. 리렌더 시간은 **보이는 패널 수에 선형**이다.
3. **1st party UI 와 같은 JS 스레드를 쓴다.** PUI 와 2D 에디터 UI 가 같은 스레드다. Custom UI 가 스레드를 막으면 시뮬레이션 정지 버튼조차 안 눌린다. 스튜디오들이 실제로 겪었다.

### 4.5 대응 규칙

| 문제 | 규칙 | 단서 |
|---|---|---|
| 보이는 패널이 많다 | 동시에 보이는 패널 10개 이하. 기즈모는 수백 개 있어도 되지만 안 쓸 때는 숨긴다 | 숨기기는 공짜, **다시 보이기는 비용**. 자주 토글할 패널은 켜 둔 채가 낫다 |
| 바인딩으로 애니메이션 | 하지 않는다. 갱신은 평균 4~5 프레임당 1회 이하 | 짧은 구간 몰아서 갱신하면 스레드가 곧 따라잡는다. 평균이 넘으면 큐가 계속 길어진다 |
| 부득이한 커스텀 애니메이션 | 2초 이내. 출시 예정 애니메이션 API 를 쓴다 | API 는 명령 하나로 애니메이션 전체를 JS 에 넘겨 브리지 비용이 없다 |
| 1st party UI 보호 | Meta 가 바인딩 갱신 상한(세이프가드)을 검토 중 | 임계값은 미정. 우선 상한선, 다음 반기에 스레드 분리 검토 |

### 4.6 실시간 지표 4종

에디터의 실시간 지표 툴에 Custom UI 항목이 있다. **보이는 패널 수, 바인딩 총수, 바인딩 총 데이터 크기, 프레임당 바인딩 갱신 횟수.** 위 규칙 넷을 그대로 재는 계기판이다.

### 4.7 이미지

- 이미지는 텍스처 에셋이다. 월드 초기화 때 렌더 가능 URL 을 프레임당 50장씩 조회해 React VR 에 네트워크 이미지로 넘긴다. PUI 의 월드 목록도 같은 방식이라 수백 장은 문제없다.
- 결과는 캐시된다. 패널 가시성을 껐다 켜도 다시 받지 않는다.
- 다만 아이콘에 5 MB 파일을 쓰는 사례가 있었다. 다운로드가 길어지고 메모리를 먹어 간접적으로 FPS 를 해친다.

## §5 Q&A 요점

| 질문 | 답 |
|---|---|
| Local Event Binding 은 어떻게 쓰나 | 바인딩을 만들 때 기본색·호버색 같은 상태별 값을 한 객체에 담아 넘긴다. 이후 TS 는 관여하지 않는다 (아직 미출시) |
| 바인딩 수 제한은 UI 인스턴스마다인가 | **월드 전체 합산**이다. 10명이 각자 UI 를 복제해 쓰면 10벌이 다 들어간다 |
| 200장 텍스처는 메모리에 계속 있나 | 그럴 것으로 본다. React VR 캐시 무효화 세부는 확인 필요 |
| UI 를 삭제하면 메모리가 정리되나 | 아니다 |
| UI 스레드가 리렌더 완료를 TS 에 알려주나 | 없다. 그러려면 브리지 호출이 더 늘어난다. 대신 같은 바인딩을 매 프레임 갱신하면 내부에서 **배칭**하는 방안을 고려 중 (마지막 값만 의미 있으므로) |
| 캐시가 무한이라 메모리가 터지지 않나 | 시스템이 죽지는 않을 것. 메모리가 차면 캐시를 무효화할 것으로 추정 |
| 1st party 와 Custom UI 스레드를 왜 안 나누나 | 근본 해법이지만 작업량이 크다. 분리하더라도 상한선은 필요하므로 상한선을 먼저 넣고 다음 반기에 분리를 검토 |
| Local 바인딩 갱신도 모든 UI 를 리렌더하나 | **로컬 스코프만** 리렌더한다. 또 하나의 최적화 수단 |
| 안 쓰는 바인딩이 바뀌어도 리렌더되나 | 그렇다. 패널이 어떤 바인딩을 쓰는지 알긴 하지만 알림은 모든 컴포넌트에 간다. 개선 아이디어가 있다 |

## §6 우리 프로젝트에 대는 점검

| 강연 규칙 | 우리 현황 | 판단 |
|---|---|---|
| Local 모드로 왕복 제거 | 보드·허브 패널이 Local. 영구 변수만 `Puzzle_ProgressServer`(Default)로 분리 | 충족. Local 바인딩은 로컬 스코프만 리렌더하므로 §4.4-2 의 부담도 줄어든다 |
| 데이터 모델 63 kB | 보드 패널이 86 kB 로 한도를 맞았고 `DynamicList` 로 칸 81벌 복제를 없앴다 | 해결. 강연이 말한 "의미 없는 래퍼 View 제거" 는 추가 여지 |
| 바인딩 총수 1,000~1,500 | 칸당 파생 키 22개 × 칸 수라 보드 하나가 이미 수백 개. **플레이어별 복제분이 합산**된다 | 동시 접속 수 결정 시 다시 센다. 실시간 지표로 실측 필요 |
| 갱신 4~5 프레임당 1회 | 레이저 드롭 프레임에서 set 462회/frame (Perfetto). `runBatch` 배치 커밋으로 줄이는 중 | 미충족. 공식 문서 기준(≤ 10/frame)보다 강연 기준이 더 엄격하다 (§7) |
| 콜백 2~4 프레임당 1회 | 드래그 중 칸 `Pressable` 의 enter/exit 가 프레임마다 올 수 있다 | 스트림 방식(`screenPosition`)으로 옮기는 실험이 이 항목의 대응이다 |
| 보이는 패널 10개 이하 | 플레이어 1명 기준 보드 + 허브 + DragLab 정도 | 충족. 단 선택 조각을 `UINode.if` 로 마운트를 가르는 현재 방식이 강연의 "숨기기" 와 같은 효과 |
| 가시성 토글 비용 | 트레이 페이지를 `display` 로 넘긴다 | 강연과 일치. 패널 단위 visible 토글은 피한다 |
| 바인딩 애니메이션 금지 | 드래그 중 반복 애니메이션은 이미 제거 | 충족 |
| 대용량 이미지 | 레이저 스프라이트 시트를 부품별로 분할 | 파일 크기는 에셋 등록 시 확인 |

## §7 공식 문서 수치와의 대조

`2026-09-07_Horizon_CPU_TypeScript_최적화_가이드_분석.md` 의 공식 기준선과 강연의 경험칙이 다른 곳이 있다.

| 항목 | 공식 문서 | 강연 | 해석 |
|---|---|---|---|
| 바인딩 set | 로컬 ≤ 10회/frame, 서버 ≤ 20회/frame(전원 합) | 평균 4~5 프레임당 1회 | 공식은 "한 프레임에 몰아도 되는 상한", 강연은 "지속 평균". 둘 다 지키려면 **평균은 낮게, 순간 최대는 10회 이하** |
| 콜백 | ≤ 1회/2 frame | 2~4 프레임당 1회 | 같은 취지. 강연이 조금 더 보수적 |
| 가시성 토글 | 렌더 텍스처(~40 MB) 해제·재할당이라 켠 채로 둔다 | 끄기는 공짜, 켜기는 비용 | 같은 결론 |
| RPC 한도 | 64 kB | 63 kB | 같은 한도의 반올림 차이 |
| 패널 수 · 바인딩 총수 | 언급 없음 | 10개 · 1,000~1,500개 | 강연에만 있는 기준. 실시간 지표로 잰다 |
| 리렌더 비용 | 언급 없음 | 30~50 ms, 4배 느림 | 강연에만 있는 내부 사실. "왜 set 을 줄여야 하는가" 의 근거 |

강연이 공식 문서보다 앞선 시점이라 수치는 문서를 우선하되, **"모든 패널이 알림을 받는다"** 와 **"리렌더가 4배 느리다"** 는 문서에 없는 구조적 설명이라 규칙의 이유로 기억해 둔다.
