# 멀티플레이 플랫폼에서 싱글플레이 구현 방안 (2026-09-02)

> 퍼즐은 1인용인데, **참여한 플레이어마다 각자의 보드판을 띄워 주는 것이 지금 구조로 가능한가?**
> 형제 문서: `2026-09-02_퍼즐_시작흐름과_게임플로우_제안.md` (게임 플로우 계층)

# 0. 결론

**로직 계층은 이미 멀티 준비가 되어 있고, 막고 있는 것은 "표현 + 소유권" 한 겹뿐이다.**

다만 지금 상태 그대로 배포하면 **가장 먼저 들어온 플레이어 한 명만** 퍼즐을 할 수 있다.
구조를 갈아엎을 필요는 없고, 소유권 계층 하나를 다시 짜고 표현 방식을 정하면 된다.

**표현 방식 결정은 나머지 7개 `*_CoreAPI` 를 쓰기 전에 해야 한다.** 3D 오브젝트 방식으로
7종을 더 쓴 뒤에 바꾸면 같은 작업을 7배로 다시 하게 된다 (§4).

# 1. 이미 되어 있는 것

## 1.1 로직이 전부 인스턴스 기반이다

`Session` / `Board` / `Generator` / `Tables` 어디에도 모듈 전역 가변 상태가 없다.
`constructSystems()` (`Switch_CoreAPI.ts:141`) 가 매번 `new` 로 조립한다.

```ts
this.tables  = new SwitchPuzzleTables();
this.events  = new SwitchPuzzleEvents();
this.session = new SwitchSession(this.events, this.tables, new SwitchLevelGenerator(this.tables), { seed });
```

N 명분 세션을 동시에 굴리는 데 **로직상 걸림돌이 없다.** 이것은 PUZ_00 §7.1 "로직과 표현의
분리" 를 지킨 부수 효과다. 규칙 판정이 컴포넌트가 아니라 순수 객체 안에 있으므로
인스턴스를 몇 개 만들든 서로 간섭하지 않는다.

## 1.2 Horizon 의 실행 모델이 이미 플레이어별 격리를 준다

Local 스크립트는 **소유자 클라이언트의 독립된 JS 컨텍스트**에서 돈다.
서버는 서버대로, 각 플레이어는 각자의 컨텍스트를 갖는다.

따라서 아래 전역 상태들은 **플레이어 간에는 서로 섞이지 않는다.**

| 전역 | 위치 | 멀티 영향 |
|---|---|---|
| `PuzzleHubRegistry.instance` 싱글턴 | `PuzzleUI_Registry.ts:167` | 없음 — 클라이언트마다 별도 인스턴스 |
| `_cameraRetryTimeoutIds` 모듈 배열 | `Puzzle_HorizonBridge.ts:355` | 없음 — 단, 한 클라 안에서 8개 퍼즐이 공유하는 문제는 그대로 |
| `onTouchStart/Move/End` 퍼블리셔 | `Basics_Input_Screen.ts` | 없음 — 로컬 브로드캐스트 이벤트 원천 |
| `SwitchCoreAPI.instance` static | `Switch_CoreAPI.ts` | 없음 |

형제 문서 §2.5(c) 가 지적한 카메라 타이머 문제는 **"한 클라이언트 안에서 8개 퍼즐이
동시에 살아 있을 때"** 의 문제다. 멀티플레이 때문에 새로 생기는 문제가 아니므로
우선순위는 그대로 두면 된다.

## 1.3 카메라·포커스·터치는 전부 클라이언트 로컬이다

`LocalCamera`, `enterFocusedInteractionMode()`, `PlayerControls.onFocusedInteractionInput*`
모두 소유 플레이어에게만 적용된다. A 가 보드에 카메라를 고정해도 B 의 시야에는 영향이 없다.
`enterPuzzleInteraction()` / `exitPuzzleInteraction()` (`Puzzle_HorizonBridge.ts:344`) 는
플레이어별로 독립적으로 동작한다.

## 1.4 터치→격자 변환이 물리 레이캐스트가 아니라 순수 평면 수학이다

`PuzzleBoardMapper.getGridFromRay()` (`Puzzle_HorizonBridge.ts:99~119`) 는
ray-plane 교차를 직접 계산한다. 콜라이더를 쏘지 않는다.

```
intersectPlane(rayOrigin, rayDirection)
  denominator = rayDirection · normal
  distance    = (center - rayOrigin) · normal / denominator
  hit         = rayOrigin + rayDirection * distance
```

읽는 것은 `boardCentre` 의 position/right/up/forward 넷뿐이고, 그것도 `refreshFrom()` 으로
레벨 로드 시 한 번만 캐시한다.

**이 성질이 §3.1 리그 풀 설계에서 결정적인 이점이 된다.** 물리 레이캐스트로 짰다면
플레이어별 보드를 서로 멀리 떨어뜨려 놓아야 했겠지만, 평면 수학이므로 **같은 자리에
겹쳐 놓아도 서로의 입력을 가로채지 않는다.**

# 2. 막고 있는 것 — 세 가지

## 2.1 소유권을 첫 플레이어에게만 넘긴다

`Puzzle_LocalOwnership.ts:31,51` 의 `firstPlayerOnly` 가 기본 `true` 다.
파일 상단 주석에도 "단일 플레이어 퍼즐을 전제로, 먼저 들어온 플레이어가 소유자가 된다" 고
명시돼 있다.

```ts
private onPlayerEnterWorld(player: Player): void {
    if (this.props.firstPlayerOnly && this._assignedPlayer !== undefined) {
        return;                       // ← 두 번째 플레이어부터는 아무 일도 일어나지 않는다
    }
    this.assignTo(player);
}
```

**이 플래그를 `false` 로 바꾸면 더 나빠진다.** Horizon 의 엔티티 소유권은 **배타적**이라
나중에 들어온 B 에게 넘어가는 순간 A 의 컴포넌트는 `dispose()` 되고, A 는 진행 중이던 판을
통째로 잃는다. `dispose()` 안에서 `releaseInteraction()` 이 도는 것이 그나마 다행이지만
(카메라에 갇히지는 않는다) 게임은 끝난다.

**플래그 문제가 아니라 구조 문제다.** 플레이어 수만큼의 엔티티 세트가 필요하다.

## 2.2 보드 3D 오브젝트가 월드에 딱 한 세트뿐이다

`boardCentre` / `keyCapRoot` 가 단일 `PropTypes.Entity` 다 (`Switch_CoreAPI.ts:56,65`).
그리고 그 자식 25개에 아래 세 속성을 쓴다.

| 호출 | 위치 |
|---|---|
| `entity.position.set(...)` | `Switch_CoreAPI.ts:321` |
| `entity.visible.set(...)` | `Switch_CoreAPI.ts:324` |
| `mesh.style.tintColor.set(...)` | `Switch_CoreAPI.ts:370` |

**이 세 속성은 전부 네트워크 동기화된다.** 두 명이 같은 키캡 세트를 조작하면
A 가 누른 키가 B 의 화면에서도 초록으로 변한다. 서로 다른 판을 받았다면
(각자 다른 `fieldIndex`) 화면이 아예 깨진다.

## 2.3 플레이어별 가시성 분리가 없다

`setVisibilityForPlayers()` 호출이 코드베이스 전체에 한 군데도 없다.
보드를 여러 세트 배치하더라도 남의 보드가 그대로 보인다.

# 3. 해법

## 3.1 A안 — 리그 풀(rig pool). 지금 구조를 그대로 살리는 정공법

Horizon 의 표준 패턴이다. **"퍼즐 1세트 = 리그"** 를 최대 동접 인원수만큼 미리 배치하고,
입장한 플레이어에게 하나씩 빌려준다.

```
Rig_0 ┬ PuzzleController      (CoreAPI 8종)
      ├ InputScreenListener
      ├ PuzzleUI_MainPanel
      ├ BoardCentre
      └ KeyCapRoot (자식 25)
Rig_1 ┬ ... (동일 구성)
Rig_2 ┬ ...
```

`Puzzle_LocalOwnership` 을 `Puzzle_PlayerRigPool` 로 확장한다.

```
OnPlayerEnterWorld(player)
  ├ 비어 있는 리그 하나 확보 (없으면 대기열 / 정원 안내)
  ├ 리그 엔티티 전부 owner.set(player)
  └ 리그의 보드 오브젝트 setVisibilityForPlayers([player], VisibleTo)
       ★ 이것을 빠뜨리면 남의 판이 보인다

OnPlayerExitWorld(player)
  ├ requestEnd(PLAYER_LEFT)          ← 형제 문서 §2.3 규칙 4 와 같은 지점
  ├ 리그 상태 리셋 (키 캡 색·위치 초기화, 세션 abort)
  └ owner.set(serverPlayer) → 풀에 반납
```

### 리그를 같은 자리에 겹쳐 놓을 수 있다

§1.4 의 성질 덕분이다. 각 클라이언트는 **자기 리그의 `boardCentre` 기저만** 읽고
ray-plane 교차를 계산하므로, 다른 리그의 오브젝트가 물리적으로 겹쳐 있어도
입력이 섞이지 않는다. 가시성만 분리하면 카메라 배치(`cameraDistance` 자동 배치)도
리그마다 따로 잡을 필요가 없다.

### 약점 — 엔티티 수

스위치만 키 캡 25개다. 8개 퍼즐을 전부 붙이면 리그 하나에 수백 엔티티가 되고,
거기에 동접 인원을 곱한다. 현실적으로 **동시 플레이 4~8명 상한**을 두고 시작해야 한다.

## 3.2 B안 — 보드를 Custom UI 로 그린다 (권장)

8개 퍼즐이 **전부 2D 격자**다. 3D 키 캡 대신 Custom UI 패널로 그리면 §2 의 세 가지가
전부 사라진다.

- Local 소유 Custom UI 는 **그 플레이어에게만 렌더된다** → 가시성 분리가 공짜
- 복제할 3D 엔티티가 없다 → 리그당 엔티티 1~2개
- `LEVEL_LOADED` / `KEY_PRESSED` 핸들러가 `entity.position.set()` 대신 UI 바인딩을
  갱신하는 형태로 바뀔 뿐, **Session 계층은 한 줄도 건드리지 않는다**
- 이미 `PuzzleUI_MainPanel.ts` 가 정확히 이 방식(Local + Screen Overlay)으로 돌고 있어
  검증된 경로다

대신 "월드 안에 실물 퍼즐 판이 서 있는" 공간감은 포기하게 된다.

## 3.3 권장 조합 — 월드스페이스 Custom UI 리그

**리그 = 컨트롤러 엔티티 + 월드스페이스 Custom UI 패널 1개.**

판은 3D 공간에 서 있되 내용물은 UI 라 플레이어별로 다르게 보인다. 리그당 엔티티가
손에 꼽을 정도라 8~16명도 감당되고, 소유권 관리도 단순해진다.

| 항목 | A안 (3D 리그) | B안 (Screen Overlay) | 권장 (월드스페이스 UI 리그) |
|---|---|---|---|
| 리그당 엔티티 | 수백 | 1~2 | 2~3 |
| 현실적 동접 | 4~8 | 제한 거의 없음 | 8~16 |
| 공간감 | 있음 | 없음 | 있음 |
| Session 수정 | 없음 | 없음 | 없음 |
| CoreAPI 표현부 | 그대로 | 다시 씀 | 다시 씀 |
| 남은 7종 작업량 | 큼 | 중간 | 중간 |

# 4. 진행 순서 제안

| 순서 | 작업 | 이유 |
|---|---|---|
| 0 | **표현 방식 결정 (3D 리그 / Custom UI)** | 나머지 7개 CoreAPI 를 쓰기 **전에**. 뒤로 미루면 7배로 물린다 |
| 1 | `Puzzle_LocalOwnership` → `Puzzle_PlayerRigPool` 재작성 | 배타적 소유권 배분 + 반납 + 정원 초과 처리 |
| 2 | 리그 가시성 분리 (`setVisibilityForPlayers`) | 3D 리그를 택했을 때만 필요 |
| 3 | 형제 문서 §2.6 순서 진행 | GameFlow 의 `PLAYER_LEFT` 종료 경로가 리그 반납과 짝을 이룬다 |

형제 문서 §2.3 규칙 4("안전망을 서버에 둔다") 가 이미 `onPlayerExitWorld` 를 종료 지점으로
잡고 있으므로, 리그 반납을 같은 자리에 얹으면 자연스럽게 맞물린다.

# 5. 검증 시 확인할 것

인월드에서 2명 이상으로 테스트할 때 아래 순서로 좁히면 원인을 빨리 찾을 수 있다.

1. 두 번째 플레이어의 콘솔에 `[SwitchCoreAPI] Started on the local client.` 가 찍히는가
   → 안 찍히면 소유권 배분 문제 (§2.1)
2. 두 사람의 키 캡 색이 같이 변하는가
   → 변하면 리그 분리가 안 된 것 (§2.2)
3. 상대의 보드가 보이는가
   → 보이면 가시성 분리 누락 (§2.3)
4. 한 사람이 나갔을 때 그 리그가 반납되고 다음 입장자가 쓸 수 있는가
   → 안 되면 `onPlayerExitWorld` 정리 경로 문제
