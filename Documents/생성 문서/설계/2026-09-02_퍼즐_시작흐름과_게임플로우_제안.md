# 1. 퍼즐의 시작 함수와 호출 흐름

## 1.1 계층 구조

8개 퍼즐 모두 동일한 계층을 쓴다. `horizon/core` / `horizon/ui` 를 아는 것은 어댑터·패널뿐이다 (PUZ_00 §7.1 로직과 표현의 분리).

```
FieldData(자동생성)  →  DataTables  →  LevelGenerator  →  Board / InputController
                            ↑                                       ↑
                         Session (라운드·시간·승패 상태머신, 순수 로직)
                            ↑
                        *_CoreAPI (Horizon Component, Local)
                       ↙                                ↘
   PuzzleBoardPresenter (순수)                   PuzzleHubRegistry
            ↕ 스테이지                                    ↕
   PuzzleBoardUIPanel (Custom UI, Local)        PuzzleUI_Model → PuzzleUI_MainPanel
```

| 계층 | 파일 | 프레임워크 의존 |
|---|---|---|
| 데이터 | `*_FieldData.ts` (자동 생성), `*_DataTables.ts` | 없음 |
| 생성 | `*_LevelGenerator.ts`, `*_Solver.ts` | 없음 |
| 규칙 | `*_Board.ts`, `*_InputController.ts`, `*_DragController.ts` | 없음 |
| 상태머신 | `*_Session.ts`, `*_GameEvents.ts` | 없음 |
| **보드 표현 (신규)** | `PuzzleBoardUI_Definitions.ts`, `PuzzleBoardUI_Presenter.ts` | 없음 |
| **보드 렌더 (신규)** | `PuzzleBoardUI_Panel.ts` | `horizon/ui` |
| 어댑터 | `*_CoreAPI.ts`, `Puzzle_HorizonBridge.ts`, `Puzzle_LocalOwnership.ts` | `horizon/core` |
| 허브 UI | `PuzzleUI_Registry/Definitions/Model` (무의존), `PuzzleUI_MainPanel` (있음) | 혼합 |
| 진행도 | `PuzzleUI_Progress.ts` (무의존), `PuzzleUI_PersistentProgress.ts` | 혼합 |

**`PuzzleBoardUI_*` 4개는 퍼즐을 모른다.** 격자와 칸 색만 다루므로 8종이 그대로 재사용한다. 이것이 나머지 7개 CoreAPI 작성 비용을 크게 낮춘다.

## 1.2 시작 진입점 — 3단 계단

"시작 함수" 는 계층마다 이름이 다르고, 실제로는 아래 셋이 순서대로 불린다.

| 계층 | 함수 | 비고 |
|---|---|---|
| Horizon 컴포넌트 | `<퍼즐>CoreAPI.start()` → `constructSystems()` | 시스템 조립. 아직 퍼즐이 돌지 않는다 |
| 허브 | `PuzzleHubModel.startLevel(n)` → `handle.startLevel(n)` | 레벨 번호 → (난이도, 판 순번) |
| 퀘스트 시작 | `CoreAPI.startLevel(difficulty, fieldOrdinal)` | Start / Continue / 재도전 / 다음 레벨의 공통 경로 |
| 순수 로직 | `Session.startLevel()` → `beginQuest()` → `startRound()` | 지정한 판을 1라운드로 |

단독 구동(`autoStart`)만 예외로 `CoreAPI.startQuestByDifficulty()` →
`Session.startQuest()` → `beginQuest()` 를 타고, 난이도 전체를 라운드 여러 판으로 돌린다.

### 8개 퍼즐 Session 의 공통 API

전 퍼즐이 아래 시그니처를 동일하게 갖는다. 그래서 퍼즐별 어댑터 없이 `createPuzzleHandle()` 팩토리 하나로 전부 감쌀 수 있다 (구조적 타이핑, `PuzzleUI_Registry.ts`).

```
startLevel(difficulty: number, fieldOrdinal: number): boolean   ← 레벨 하나 (1라운드 고정)
startQuest(questId: string): boolean                            ← 퀘스트 전체
startQuestByDifficulty(difficulty: number): boolean
startRound(): boolean
update(deltaSeconds: number): void
pause() / resume() / abort(): void
getRemainingTimeSeconds(): number
getRoundProgress(): { current, total, cleared }
```

**Custom UI 전환은 이 계층을 한 줄도 건드리지 않았고**, 레벨 진행 전환에서는
`startLevel()` 이 더해졌을 뿐 기존 두 경로의 동작은 그대로다.

| 퍼즐 | Session 파일 | `startQuest` | `startRound` | 생성자 추가 의존 |
|---|---|---|---|---|
| PUZ_01 레이저 | `Laser_Session.ts` | 146 | 175 | `tracer`, `solver` |
| PUZ_02 러시아워 | `RushHour_Session.ts` | 132 | 165 | `solver` |
| PUZ_03 정렬 | `ColorSort_Session.ts` | 120 | 148 | `solver` |
| PUZ_04 색 채우기 | `ColorFill_Session.ts` | 118 | 146 | — |
| PUZ_05 연결 | `Flow_Session.ts` | 132 | 160 | `solver` |
| PUZ_06 카드 맞추기 | `CardMatch_Session.ts` | 109 | 136 | — |
| PUZ_07 슬라이드 | `SlidePuzzle_Session.ts` | 118 | 145 | — |
| PUZ_08 스위치 | `Switch_Session.ts` | 125 | 171 | — |

공통 생성자 형태는 `(events, tables, generator, [solver...], options)` 이다.

## 1.3 게임 로직이 시작되기까지의 전체 호출 흐름

### ① 월드 부팅 — 소유권 이전

`*_CoreAPI` 와 Custom UI 패널은 플레이어별로 따로 돌아야 하므로 실행 모드가 `Local` 이고, Horizon 의 Local 스크립트는 **엔티티에 플레이어 소유자가 지정되어야 실행된다.** 소유자가 서버인 채로 두면 CoreAPI 는 조용히 끝나고 패널은 빈 화면만 그린다.

```
[서버] PuzzleLocalOwnership.start()
   └ OnPlayerEnterWorld(player)
        └ targets[].owner.set(player)      ← PuzzleController + BoardPanel (+ HubPanel)
             │
[클라] ──────┼──▶ SwitchCoreAPI.start()          ┐ 순서는 보장되지 않는다
             └──▶ PuzzleBoardUIPanel.initializeUI() ┘ (§②-b 스테이지가 흡수한다)
```

3D 보드 시절과 달리 **`InputListener`(`Basics_Input_Screen`) 엔티티는 targets 에 넣지 않는다.** 터치가 UI 에서 나오기 때문이다. 대신 **BoardPanel 이 새로 들어간다.**

정상 순서는 콘솔 로그로 확인한다.

1. `[SwitchCoreAPI] Server instance. Waiting for ownership transfer.`
2. `[PuzzleLocalOwnership] Transferred ownership of 2 entities to the player.`
3. `[SwitchCoreAPI] Started on the local client. Ownership transfer OK.`

1번은 정상 셋업에서도 한 번 뜬다. **3번이 이어서 뜨는지가 판단 기준이다.**

### ②-a constructSystems() — 시스템 조립 (`Switch_CoreAPI.ts:147`)

```
new SwitchPuzzleTables()        // 모듈 로드 시점에 Switch_FieldData.ts 상수가 이미 정적 평가됨
new SwitchPuzzleEvents()
new SwitchSession(events, tables, new SwitchLevelGenerator(tables), { seed })
createPresenter()               // ★ 신규 - 예전의 PuzzleBoardMapper + PuzzleTouchRouter 자리
subscribeToSessionEvents()      // LEVEL_LOADED / KEY_PRESSED / AREA_TOGGLED / ... / QUEST_CLEAR
connectPuzzleUpdate()           // World.onUpdate → session.update(dt)   ★ 빠뜨리면 시간이 안 흐른다
PuzzleHubRegistry.register(createPuzzleHandle(...))   // 메인 UI 가 이 퍼즐을 목록에 띄운다
SWITCH_READY.publish(this)
autoStart ? startQuestByDifficulty(props.difficulty) : (대기)
```

`createPresenter()` (`Switch_CoreAPI.ts:189`) 가 하는 일은 격자 규격과 입력 콜백을 묶는 것뿐이다.

```ts
new PuzzleBoardPresenter(
    { title, rowCount: 5, colCount: 5, side: { rowCount: 3, colCount: 3, label } },
    {
        onCellDown: (cell) => { this.session.touchDown(cell); },
        onCellMove: (cell) => { this.session.touchMove(cell); },   // 보드 밖이면 -1
        onCellUp:   ()     => { this.session.touchUp(); },
    },
);
```

**이 시점까지는 아직 게임 로직이 아니다.** 세션은 `IDLE`, 프레젠터는 입력이 꺼져 있고(`_isInputEnabled = false`) 스테이지에 올라가 있지도 않다.

#### 사라진 배선

| 3D 보드 시절 | 지금 |
|---|---|
| `new PuzzleBoardMapper({ rowCount, colCount, cellSpacing })` | 없음. 좌표 변환이 필요 없다 |
| `new PuzzleTouchRouter(mapper, handlers)` | `PuzzleBoardPresenter` 가 같은 역할(단일 터치 강제 포함) |
| `collectChildEntities(keyCapRoot, ...)` | 없음. 3D 자식 엔티티가 없다 |
| `onTouchStart/Move/End` 구독 | 없음. `Pressable` 콜백이 대신한다 |

`Puzzle_HorizonBridge.ts` 는 **삭제하지 않았다.** `connectPuzzleUpdate()` 는 계속 쓰고, `enterPuzzleInteraction()` 은 `focusCamera` 경로에서만 쓴다.

### ②-b BoardPanel 초기화 — 스테이지 연결

패널과 컨트롤러는 다른 엔티티이므로 **초기화 순서가 보장되지 않는다.** 이를 `PuzzleBoardStage` 싱글턴이 흡수한다.

```
PuzzleBoardUIPanel.initializeUI()        [PuzzleBoardUI_Panel.ts:118]
   ├ owner === serverPlayer ? → View({}) 빈 화면 반환
   ├ 최대 격자(9×9 = 81) 만큼 Pressable 슬롯을 미리 만든다
   │    ★ initializeUI() 는 한 번만 불리고 UINode 를 갈아 끼우는 API 가 없다
   │      실제 격자 밖 슬롯은 display: none 으로 숨긴다
   └ connectStage()                       [:152]
        ├ stage.MOUNTED  → attachPresenter(presenter)
        ├ stage.UNMOUNTED → detachPresenter()
        └ stage.current 를 즉시 읽어 따라잡는다   ← 패널이 늦게 떠도 이미 올라온 보드를 그린다
```

**슬롯 번호와 칸 번호가 다르다.**

```
슬롯 번호 = row * 9(고정)        + col     ← UI 트리의 자리
칸  번호 = row * 현재 colCount   + col     ← 퍼즐 로직의 row-major 번호
```

5×5 판에서 칸 7번은 슬롯 (1,2) = 11번에 그려진다. 변환은 패널 안에서 끝나므로 세션과 CoreAPI 는 칸 번호만 다룬다.

### ③ 퀘스트 시작 트리거 — 두 경로

**경로 A (메인 UI 경유 — 기본)** — `autoStart` 는 **기본값이 꺼짐**이므로 게임은 언제나 허브 메뉴에서 시작한다.

```
PuzzleUIMainPanel.initializeUI()        [UIComponent, Local, Screen Overlay]
   ├ createProgressTracker()            ← 영구 변수를 쓸 수 있으면 쓰고, 아니면 메모리
   └ new PuzzleHubModel(registry, progress)   ← 레지스트리 구독 (HANDLE_REGISTERED)
        (플레이어 입력)
        selectPuzzle(id)        → PUZZLE_DETAIL   (그 퍼즐이 화면을 꽉 채운다)
        startNewGame()          → 레벨 1
          또는 continueGame()   → 마지막 클리어 + 1 레벨
           └ PuzzleHubModel.startLevel(n)        ← 네 경로가 모두 지나는 단 하나의 문
                ├ 레벨 범위 검사 (1 .. getLevelCount())
                ├ handle.subscribeQuestEvents(...)   ★ 시작 "전" 에 구독한다
                │    (레벨 생성 실패 시 QUEST_FAILED 가 startLevel() 안에서
                │     동기적으로 발행되므로, 나중에 구독하면 결과를 놓친다)
                └ handle.startLevel(n)
                     ├ 레벨 번호 → (난이도, 판 순번) 변환   ← 핸들 안에서 끝난다
                     └ CoreAPI.startLevel(difficulty, fieldOrdinal)
```

`retry()` 와 `playNextLevel()` 도 같은 `startLevel(n)` 을 거친다.

**레벨 하나 = 퀘스트 라운드 하나 = 기획 판 하나.** 난이도 오름차순으로 판을 이어 붙인 것이
레벨 목록이며(`buildPuzzleLevelTable()`), 8종 합계 651레벨이다.
자세한 것은 `../구현 사항/작업기록_2026-09-02_메인UI_레벨진행_전환.md` 를 본다.

**경로 B (단독 구동)** — 퍼즐 하나만 테스트할 때 그 퍼즐의 `props.autoStart` 를 켜면
`start()` 가 곧바로 `startQuestByDifficulty()` 를 부른다. 이 경로만 난이도 전체를
(라운드 여러 판) 한 번에 돌린다.

### ④ CoreAPI — 카메라 (선택 사항으로 강등됨)

```
CoreAPI.startQuestByDifficulty(d)            [Switch_CoreAPI.ts:245]
   ├ enterInteraction()                      [:218]
   │    └ props.focusCamera === false ? → 즉시 리턴   ★ 기본값이 false 다
   │       (켰을 때만) enterPuzzleInteraction(component, setup)
   │            ├ LocalCamera.setCameraModeFixed()
   │            ├ owner.enterFocusedInteractionMode({ disableFocusExitButton: true })
   │            ├ applyFixedCamera(setup)          // boardCentre 정면 배치
   │            └ setTimeout 300ms / 1000ms 재적용  // 월드 재실행 시 무시되는 문제 대응
   └ session.startQuestByDifficulty(d)
```

**이 단계는 3D 보드 시절 입력의 전제 조건이었으나, 지금은 연출 목적의 선택 사항이다.** Custom UI 는 `Pressable` 이 직접 입력을 받으므로 Focused Interaction 없이도 동작한다.

| | 3D 보드 (이전) | Custom UI 보드 (지금) |
|---|---|---|
| Focused Interaction | **필수** (없으면 터치가 아예 안 온다) | 불필요 |
| 고정 카메라 | 사실상 필수 | 선택 (`focusCamera`, 기본 꺼짐) |
| `boardCentre` | 좌표계 정의 그 자체 | `focusCamera` 를 켰을 때 카메라가 볼 대상 |

**플레이어가 카메라에 갇히는 사고의 위험이 기본 설정에서 사라졌다.** `focusCamera` 를 켠 월드에서만 §2.3 규칙 3 의 해제 경로가 필요하다.

### ⑤ Session — 퀘스트/라운드 초기화

```
Session.startLevel(difficulty, fieldOrdinal)      ← 메인 UI 경로
   ├ tables.getQuestByDifficulty(d)   → 없으면 warn + false 반환 (이벤트 없음)
   ├ _fieldOrdinal = fieldOrdinal     ← 이 판 하나만 쓴다
   ├ _roundCountOverride = 1          ← 1라운드 고정
   └ beginQuest(quest)

Session.startQuest(questId)                       ← 퀘스트 전체 경로 (autoStart / 트리거)
   ├ tables.getQuest(questId)
   ├ _fieldOrdinal = undefined        ← 판은 무작위, 라운드 수는 테이블을 따른다
   ├ _roundCountOverride = undefined
   └ beginQuest(quest)

beginQuest(quest)                                 ← 둘의 공통 몸통
   ├ 상태 초기화: _roundIndex=0, 사용 이력=[], _roundsCleared=0,
   │              _remainingSeconds = quest.timeLimitSeconds
   ├ QUEST_START.publish(quest.questId)
   ├ ROUND_PROGRESS_CHANGED.publish
   └ startRound()
```

`_usedFieldIndexes` 는 한 퀘스트 안에서 같은 판이 다시 나오지 않게 하는 이력이다 (PUZ_00 §6 공통 수정 항목).

### ⑥ startRound() — 레벨 생성. 데이터 파이프라인의 종착점

```

   │    ├ buildLevel()               ← initialRows 직접 로드 또는 역셔플 생성
   │    └ validator.validate()       ← 해가 존재하는지
   │         └ undefined 반환 시 → session.fail() → QUEST_FAILED + GAME_END
   │              ★ 결과 이벤트 없이 멈추면 UI 가 영원히 대기하므로 반드시 실패로 수렴시킨다
   ├ Board.fromLevel(level)
   ├ new InputController(board)
   ├ (isTimeLimitPerRound 면 제한시간 리셋)
   ├ setState(ROUND_INTRO)
   ├ LEVEL_LOADED.publish(level)   ─────┐

   └ setState(PLAYER_INPUT)   ★ 여기부터 시간이 흐른다
                                        │
CoreAPI.onLevelLoaded(level) ◀──────────┘     [Switch_CoreAPI.ts:294]
   ├ for cell: presenter.setCell(cell, { isVisible: grid[cell] !== FREE })
   │      // §4 FREE 좌표에는 오브젝트가 없다. 숨긴 칸은 눌리지도 않는다
   ├ applyGridVisuals()      // 칸 색: 눌림 = 녹색 / 안 눌림 = 빨강
   ├ applyMaskVisuals()      // §9.5 우측 3×3 보조 격자 (예전엔 콘솔 로그만 찍었다)
   ├ PuzzleBoardStage.instance.mount(this._presenter)   ★ 보드를 화면에 올린다
   └ presenter.setInputEnabled(true)                    ★ 여기부터 입력을 받는다
```

**결론 — 게임 로직이 시작되는 지점은 세 개가 짝을 이룬다.**

1. `Session.startRound()` 끝의 `setState(PLAYER_INPUT)` — 시간이 흐르기 시작
2. `PuzzleBoardStage.mount(presenter)` — 보드가 화면에 나타남
3. `presenter.setInputEnabled(true)` — 입력을 받기 시작

3D 시절의 `mapper.refreshFrom()` / `collectChildEntities()` / `entity.position.set()` / `touchRouter.setEnabled(true)` 가 위 셋으로 대체되었다.

### ⑦ 입력 경로 — Pressable 에서 세션까지

```
Pressable onPress   → presenter.pointerDown(cell)   [PuzzleBoardUI_Presenter.ts:190]
```

프레젠터가 지키는 규약은 3D 라우터와 같다.

| 규약 | 근거 | 구현 |
|---|---|---|
| 단일 터치 전용 | PUZ_00 §8.1 | 진행 중인 누름이 있으면 두 번째 `pointerDown` 무시 |
| 보드 밖 좌표도 전달 | PUZ_00 §8.4 | `PUZZLE_BOARD_CELL_OUTSIDE`(-1) 를 `onCellMove` 로 |

| 숨긴 칸은 보드의 일부가 아니다 | PUZ_08 §4 | `isVisible: false` 칸의 `pointerDown` 거절 |

**`enter`/`exit` 순서를 신뢰하지 않는다.** 칸 A→B 로 손가락을 옮기면 `onExit(A)` 와 `onEnter(B)` 의 순서가 보장되지 않으므로, `pointerExit(cell)` 은 **지금 올라가 있는 칸이 그 칸일 때만** 밖으로 처리한다. 두 순서 모두 `PuzzleBoardUI_Tests.ts` 의 검증 항목이다.

# 2. 게임 전체 플로우 제안

## 2.1 지금 없는 것

`PuzzleUI_Model` 의 화면 상태머신(`MAIN_MENU → PUZZLE_DETAIL → IN_GAME ⇄ PAUSED → RESULT`)은 **"퍼즐 한 판"** 의 시작과 끝을 이미 잘 담당하고 있다. 반면 **"게임 한 판"** 의 개념 — 언제 플레이가 시작되고, 무엇을 달성하면 끝나고, 결과를 어떻게 집계하는지 — 는 어디에도 없다.

| 빠진 것 | 지금 상태 |
|---|---|
| 월드 진입 → 퍼즐 허브 진입 트리거 | 소유권 이전 즉시 UI 가 그려진다. "게임 시작 전" 상태가 없다 |
| 여러 퍼즐을 묶은 세션/목표/보상 | 개념 자체가 없다 |
| 종료 경로의 단일화 | 클리어·실패·포기·시간초과·**플레이어 퇴장**·소유권 상실이 각각 다른 곳에서 처리된다 |
| 정리(cleanup) 보증 | 아래 참조 |

### Custom UI 전환으로 정리 항목이 바뀌었다

| 정리 대상 | 3D 보드 | Custom UI 보드 |
|---|---|---|
| **보드 내리기** | (해당 없음 — 3D 오브젝트가 항상 거기 있었다) | **`PuzzleBoardStage.unmount()` — 신규 의무.** 빠뜨리면 게임이 끝났는데 보드가 화면에 남는다 |
| 입력 차단 | `touchRouter.setEnabled(false)` | `presenter.setInputEnabled(false)` (붙잡힌 누름도 마감한다) |
| 카메라·포커스 해제 | **필수.** 빠뜨리면 플레이어가 영구히 갇힘 | `focusCamera` 를 켠 월드에서만 필요 (기본 꺼짐) |
| 3D 오브젝트 상태 복구 | 키 캡 25개의 위치·색·가시성 | 없음 |

**위험이 옮겨 갔지 사라지지 않았다.** "카메라에 갇힘" 이 "보드가 화면에 남음" 으로 바뀐 것이므로, 종료 경로를 한곳에 모으는 §2.3 의 필요성은 그대로다. 셋 다 `CoreAPI.abort()` 가 한 번에 처리하므로 (`Switch_CoreAPI.ts:266`), **모든 종료가 `abort()` 를 지나게 만드는 것이 관건이다.**

## 2.2 제안 구조 — 계층 하나만 추가

기존 계층을 건드리지 않고 맨 위에 한 겹만 얹는다.

```
[신규] Puzzle_GameFlow.ts            ← 순수 로직. 게임의 시작과 끝.
[신규] Puzzle_GameFlowController.ts  ← Horizon 어댑터 (트리거·update·퇴장 감지)
         ↓ 지시
       PuzzleUI_Model  (허브 화면 상태머신)        ← 이미 있음
         ↓
       PuzzleHubRegistry / IPuzzleGameHandle      ← 이미 있음
         ↓
       *_CoreAPI → *_Session                      ← 이미 있음
         ↓
       PuzzleBoardPresenter → PuzzleBoardStage → PuzzleBoardUIPanel   ← 이미 있음
```

`Puzzle_GameFlow` 는 `horizon/core` 를 몰라야 한다. 그래야 기존 `*_Tests.ts` 10개와 같은 방식으로 Node 에서 전 종료 경로를 검증할 수 있다. **종료 경로야말로 인월드에서 재현하기 가장 번거로운 부분이다.** `PuzzleBoardUI_Tests.ts` 가 실제 `SwitchSession` 을 배선해 UI 탭만으로 D1 을 클리어하는 통합 검증을 이미 하고 있으므로, 같은 방식으로 게임 플로우까지 이어 붙일 수 있다.

### 순수 로직 (`Puzzle_GameFlow.ts`)

```ts
export enum EGameFlowState { IDLE, INTRO, PLAYING, SUMMARY }

export enum EGameEndReason {
    GOAL_REACHED,   // 목표 퍼즐 수 클리어
    TIME_UP,        // 게임 전체 제한시간 만료
    PLAYER_QUIT,    // 스스로 나감
    PLAYER_LEFT,    // 월드 이탈 / 소유권 상실
    ERROR,          // 레벨 생성 실패 등
}

export type GameFlowConfig = {
    puzzleOrder?: EPuzzleId[],       // 정해진 순서로 낼지. undefined = 허브에서 자유 선택
    targetClearCount?: number,       // 몇 개 클리어하면 게임 종료
    totalTimeLimitSeconds?: number,  // 게임 전체 제한시간. 0 = 없음
    allowRetry: boolean,
}

export class PuzzleGameFlow {
    readonly events: {
        GAME_STARTED, PUZZLE_ADVANCED, RESULT_RECORDED, GAME_ENDED, TOTAL_TIME_CHANGED
    };
    begin(config: GameFlowConfig): boolean;
    onPuzzleResult(result: PuzzleUIQuestResult): void;  // 허브가 그대로 넘긴다
    requestEnd(reason: EGameEndReason): void;           // 모든 종료가 지나는 단 하나의 문
    update(deltaSeconds: number): void;
    getSummary(): GameSummary;
}
```

`PuzzleUIQuestResult`(`PuzzleUI_Definitions.ts:96`)는 이미 8개 퍼즐 공통으로 정규화되어 있으므로 그대로 재사용한다.

## 2.3 시작·끝을 다루는 4가지 규칙

### 규칙 1 — 시작과 끝은 각각 함수 하나뿐

`begin()` / `requestEnd(reason)`. 지금 흩어져 있는 것들(구독 걸기, 보드 올리기, 입력 켜기, 카메라 고정 / 그 반대)의 **짝을 이 두 함수 안에서만 맞춘다.** 어느 한쪽만 실행되는 경로를 없애는 것이 목적이다.

### 규칙 2 — 모든 종료가 하나의 이벤트로 수렴

클리어·실패·포기·시간초과·퇴장·에러 6가지가 전부 `GAME_ENDED(reason, summary)` 하나로 나온다.

이 패턴은 이미 Session 계층에 있다. `succeed()` 와 `fail()` 이 둘 다 `GAME_END` 를 발행하고, 레벨 생성 실패조차 굳이 `fail()` 을 경유시켜 "UI 가 영원히 대기하는" 상황을 막고 있다. 같은 원칙을 게임 단위로 한 층 올리는 것뿐이다.

### 규칙 3 — 정리는 역순 + 멱등

```
requestEnd(reason)
  ├ 이미 IDLE / SUMMARY 면 즉시 리턴            ← 두 번 불려도 안전
  ├ hubModel.quitToMenu()
  │     └ handle.abort() → CoreAPI.abort()      [Switch_CoreAPI.ts:266]
  │          ├ session.abort()                       // 레벨 언로드, IDLE 복귀
  │          ├ presenter.setInputEnabled(false)      // 붙잡힌 누름 마감
  │          ├ PuzzleBoardStage.unmount(presenter)   ★ 보드를 화면에서 내린다
  │          └ releaseInteraction()                  // focusCamera 를 켰을 때만
  ├ 퀘스트 구독 해제
  ├ 전체 타이머 정지
  └ GAME_ENDED.publish(reason, summary)
```

멱등성은 이미 세 겹으로 확보되어 있다.

- `releaseInteraction()` — `_isInteractionActive` 가드
- `PuzzleBoardStage.unmount(presenter)` — 인자가 현재 보드가 아니면 거절 (남의 보드를 내리지 못한다)
- `presenter.setInputEnabled(false)` — 이미 꺼져 있으면 무이벤트

그 성질을 위 계층까지 이어 간다.

### 규칙 4 — 안전망을 서버에 둔다

클라이언트가 죽거나 플레이어가 갑자기 나가면 위 경로가 전부 건너뛰어진다. `Puzzle_LocalOwnership.ts:62` 의 `onPlayerExitWorld` 가 이미 있으므로, 여기서 `requestEnd(PLAYER_LEFT)` 를 쏘고 소유권을 되돌리도록 확장하는 것이 자연스럽다.

이 지점은 **리그 풀 작업(`../구현 사항/작업기록_2026-09-02_보드_CustomUI_전환.md` §6.2)의 3번 항목과 같은 곳**이다. 퇴장 시 리그를 반납하는 로직과 게임 플로우의 `PLAYER_LEFT` 종료를 한 번에 짝지어 구현한다.

## 2.4 게임 1회 플레이 시퀀스

```
월드 입장
  └ [서버] PuzzleLocalOwnership → 소유권 이전 (PuzzleController, BoardPanel, HubPanel)
       └ [클라] 8× *_CoreAPI.start()  (autoStart 전부 OFF) → 레지스트리 등록
            ├ PuzzleBoardUIPanel.initializeUI() → 81 슬롯 생성 + 스테이지 연결 (보드 없음)
            └ PuzzleUIMainPanel.initializeUI()  → 화면: IDLE(타이틀)

플레이어가 시작 트리거(오브젝트/버튼)를 밟음
  └ GameFlowController → flow.begin(config)
       ├ GAME_STARTED
       └ hubModel: IDLE → MAIN_MENU

  ┌─ 퍼즐 루프 ────────────────────────────────────────────────────┐
  │ 퍼즐 선택 → 상세 화면 → Start 또는 Continue                     │
  │    └ CoreAPI.startLevel(difficulty, fieldOrdinal)               │
  │         ├ enterInteraction()   ← focusCamera 켰을 때만          │
  │         └ session.startLevel → startRound → PLAYER_INPUT        │
  │              └ onLevelLoaded → Stage.mount + setInputEnabled    │
  │                                        ★ 게임 로직 시작          │
  │ ...플레이 (Pressable → presenter → session)...                  │
  │ QUEST_CLEAR / QUEST_FAILED                                      │
  │    ├ CoreAPI.onQuestEnd → 입력 차단 + 보드 내리기                │
  │    └ hubModel.onQuestEnded → RESULT (최종 판이 뒤에 보인다)      │
  │         └ flow.onPuzzleResult(result)                           │
  │              ├ 목표 미달 → RESULT (다시 도전 / 다음 / 메뉴)      │
  │              └ 목표 달성 → flow.requestEnd(GOAL_REACHED) ────────┼─┐
  └─────────────────────────────────────────────────────────────────┘ │
                                                                       ▼
flow.requestEnd(reason)
  ├ hubModel.quitToMenu() → abort()
  │     └ 세션 정리 + 입력 차단 + Stage.unmount + (카메라 반환)
  ├ 구독·타이머 정리
  └ GAME_ENDED → 결산 화면 → IDLE(타이틀)
```

**보드를 언제 내리는지가 3D 시절과 다른 핵심 지점이다.**

BoardPanel 과 HubPanel 은 **서로 다른 Custom UI gizmo** 라서 어느 쪽이 위에 그려질지를
코드가 정할 수 없다. 둘 다 화면을 꽉 채우는 불투명 배경을 그리므로, 동시에 켜 두면
허브의 전체 화면 오버레이(결과·일시정지)가 보드 뒤로 숨어 **버튼조차 누를 수 없게 된다.**

그래서 규칙은 **"한 번에 하나만 그린다"** 이다. 허브가 전체 화면을 쓰는 순간마다 보드를 내린다.

| 시점 | 보드 |
|---|---|
| `onLevelLoaded` | `mount()` — 인게임에서는 보드가 화면을 채운다 (허브는 상단 바만) |
| `pause()` | `unmount()` — 일시정지 오버레이에 자리를 내준다 |
| `resume()` | `mount()` — 세션이 실제로 재개됐을 때만 |
| `onQuestEnd` | `unmount()` — 결과 화면에 자리를 내준다 |
| `abort()` / `dispose()` | `unmount()` — 정리 |

`retry()` 와 `playNextLevel()` 은 다시 `startLevel()` 을 타므로 `onLevelLoaded` 에서 자동으로
다시 올라온다. 초판에 있던 "결과 화면 뒤로 최종 판이 보인다" 는 연출은 이 문제 때문에 포기했다.

## 2.5 이 구조를 위해 손대야 할 기존 코드

### (a) `PuzzleHubModel` 의 소유권을 패널 밖으로 뺀다

현재 `PuzzleUI_MainPanel.ts` 의 `initializeUI()` 안에서 `new PuzzleHubModel()` 을 한다. GameFlow 가 같은 모델을 조종해야 하므로, `PuzzleHubRegistry` / `PuzzleBoardStage` 처럼 싱글턴 호스트로 옮기고 패널은 참조만 하게 바꾼다. **`PuzzleBoardStage` 가 CoreAPI ↔ 패널 사이에서 이미 쓰고 있는 패턴과 같다** — 참고 구현이 생긴 셈이다.

### (b) `PuzzleHubModel` 에 직접 시작 API 와 IDLE 화면 추가

- `startQuestDirect(puzzleId, difficulty)` — 정해진 순서로 퍼즐을 낼 때 필요
- `EPuzzleHubScreen.IDLE` — 게임 시작 전 타이틀. 지금은 `MAIN_MENU` 가 최상위라 "게임 시작 전" 상태를 표현할 수 없다

IDLE 화면에서는 보드 패널도 비어 있어야 한다. `PuzzleBoardStage` 에 아무것도 마운트되지 않은 상태가 곧 그것이므로 추가 작업은 없다 (패널 prop `drawBackgroundWhenEmpty` 를 끄면 배경도 안 그린다).

### (c) 카메라 재적용 타이머를 컴포넌트별로 분리 — 우선순위 하락

`Puzzle_HorizonBridge.ts` 의 `_cameraRetryTimeoutIds` 가 **모듈 전역 배열**이라, 여러 CoreAPI 가 동시에 살아 있으면 A 의 `exitPuzzleInteraction()` 이 B 의 타임아웃 ID 를 `component.async.clearTimeout()` 에 넘긴다.

**`focusCamera` 가 기본 꺼짐이 되면서 이 경로를 아무도 타지 않게 되었다.** 초판에서 "선행 필수" 로 잡았던 것을 **"`focusCamera` 를 쓰기로 결정할 때 함께 고친다"** 로 내린다. 지금 당장은 문제를 일으키지 않는다.

### (d) 비활성 퍼즐의 매 프레임 update

8개 CoreAPI 가 각자 `connectPuzzleUpdate()` 로 `World.onUpdate` 를 물기 때문에 비활성 퍼즐도 매 프레임 `session.update()` 가 돈다. `isActive === false` 면 즉시 리턴하므로 비용은 작지만, GameFlow 가 활성 퍼즐 하나만 구동하는 형태로 바꿀 여지가 있다.

### (e) 신규 — 스테이지 소유권 규약을 명문화한다

`PuzzleBoardStage` 는 싱글턴이고 보드를 **한 번에 하나만** 올린다. 8개 CoreAPI 가 같은 스테이지를 공유하므로, 퍼즐 A 에서 B 로 전환할 때 A 가 `unmount` 하기 전에 B 가 `mount` 하면 A 의 `unmount(presenter)` 는 거절된다(현재 보드가 아니므로). 결과적으로 화면은 정상이지만, **A 의 프레젠터가 입력이 켜진 채로 남는다.**

지금은 허브 모델이 `disconnectQuest()` → `abort()` 를 먼저 부르므로 순서가 맞다. GameFlow 가 퍼즐을 자동 전환하게 되면 이 순서를 규칙으로 못박아야 한다.

> **전환 규칙:** 다음 퍼즐의 `startQuestByDifficulty()` 를 부르기 전에 이전 퍼즐의 `abort()` 를 반드시 부른다.
