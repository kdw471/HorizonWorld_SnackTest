# 격자 보드게임 구현과 최적화 방법론

> 2026-09-03 작성. 모바일 격자(그리드) 기반 2D 보드 게임에서 오브젝트 상호작용과
> 고정축 이동을 구현하는 표준 방식, 그리고 이 장르의 일반적 최적화 방법론을 정리한
> 참고 문서다. 특정 퍼즐의 구현 이력이 아니라 **장르 공통의 원칙**을 다루며, 마지막
> 절에서 이 프로젝트(Horizon Worlds Custom UI)에 적용할 때의 지침을 덧붙인다.

---

## §1 핵심 원칙 — 논리와 표현의 분리

거의 모든 격자 게임이 따르는 기본 구조다.

| 계층 | 역할 | 형태 |
|---|---|---|
| 논리 보드 (Model) | 셀 상태 저장, 게임 규칙 전부 | 2D 배열 또는 1D 배열 (`index = y * width + x`) |
| 표현 (View) | 논리 보드의 스냅샷을 그리기만 | 스프라이트 / UI 노드 |

- 이동 가능 여부, 매치 판정, 승리 조건은 전부 논리 보드에서 **순수 함수**로 처리한다.
- 오브젝트의 화면 위치는 논리 좌표에서 파생된 값일 뿐, 진실의 원천(source of truth)이
  아니다. 화면과 로직이 다투면 항상 로직이 이긴다.
- 이 분리의 실익:
  - 물리 엔진·충돌 검사 없이 **배열 인덱스 연산만으로** 상호작용을 판정한다.
  - 로직을 렌더러 없이 Node 환경에서 단독 테스트할 수 있다. 이 프로젝트의
    `*_Session.ts`(순수 로직) + `*_Tests.ts`(Node 테스트) 구조가 바로 이 패턴이다.

## §2 격자 상호작용 구현

### 2.1 터치 → 셀 좌표 변환이 전부다

오브젝트마다 콜라이더를 붙여 레이캐스트하는 방식은 격자 게임에서는 낭비다.
터치 좌표를 한 번 나누면 끝난다.

```ts
col = floor((touchX - boardOriginX) / cellSize)
row = floor((touchY - boardOriginY) / cellSize)
```

- 변환 후에는 `board[row][col]` 조회 한 번으로 어떤 오브젝트를 건드렸는지 O(1)에 안다.
- 이웃 탐색은 좌표 오프셋 배열로 처리한다: `[(0,1), (0,-1), (1,0), (-1,0)]`
  (대각선이 필요하면 8방향 배열).
- 경계 검사(`0 <= row < H`, `0 <= col < W`)를 변환 직후 한 곳에서만 한다.

### 2.2 입력은 상태 머신으로

```
Idle → Selected → Dragging → Resolving → Idle
```

- 애니메이션·연쇄 처리가 진행 중일 때(`Resolving`) 입력을 무시하거나 큐에 넣는다.
  이중 입력 버그의 대부분이 이 상태 구분이 없어서 생긴다.
- 상태 전이는 로직 계층이 소유하고, View 는 현재 상태를 표시만 한다.

### 2.3 모바일 터치 판정

- 셀의 시각적 크기보다 터치 판정 영역을 크게 잡는다(hit slop). 손가락은 커서보다
  훨씬 부정확하다.
- 드래그 중인 오브젝트는 손가락 위치보다 **위로 띄워** 보이게 해서 손가락에 가려지지
  않게 한다.
- 피드백(집기 표시, 하이라이트)은 ~100ms 이내로 즉각 준다. 이 세 가지는 이
  프로젝트의 터치 UX 기준이기도 하다
  (`구현 사항/작업기록_2026-09-02_드래그_조작_시각_피드백.md` 참조).

## §3 고정축(축 잠금) 이동 구현

드래그로 오브젝트를 한 축으로만 밀 때 — 2048, 러시아워, 슬라이딩 퍼즐류 — 의
표준 패턴. 네 단계로 정리된다.

### 3.1 축 결정

드래그 시작 후 이동량이 임계값(예: 셀 크기의 20~30%)을 넘는 순간
`|dx| > |dy|` 비교로 축을 확정하고, **그 제스처가 끝날 때까지 축을 고정**한다.
축을 매 프레임 다시 판단하면 경계에서 떨리는 조작감이 된다.

### 3.2 이동 범위 클램프

축이 확정되는 순간 논리 보드를 조회해 "이 방향으로 몇 칸까지 밀 수 있는지"를
**한 번만** 계산해 둔다(벽·다른 오브젝트까지의 거리). 이후 드래그 위치는 그
범위로 클램프만 한다.

- 충돌 검사가 드래그 중 실시간이 아니라 **드래그 시작 시 1회**로 끝난다.
- 러시아워처럼 차량 길이가 있는 경우, 차량의 머리/꼬리 기준으로 범위를 계산한다.

### 3.3 놓았을 때 스냅

손을 떼면 가장 가까운 셀 중심으로 반올림해 논리 이동을 확정하고, 시각적 위치는
짧은 트윈(100~150ms, ease-out)으로 셀 중심에 붙인다. 스냅 트윈이 없으면 어긋난
위치가 그대로 남아 보이고, 길면 조작이 굼떠 보인다.

### 3.4 논리 즉시 + 시각 애니메이션

이동이 확정되면 **논리 보드는 즉시 갱신**하고, 화면의 오브젝트만 이전 위치에서
새 위치로 보간한다. "논리도 애니메이션이 끝날 때 갱신"하는 방식은 논리와 시각이
어긋나는 기간을 만들고, 그 기간에 들어온 입력이 버그가 된다. 애니메이션 중 입력을
막고 싶으면 §2.2 의 `Resolving` 상태로 막는다 — 논리를 늦추는 것으로 막지 않는다.

## §4 최적화 방법론 — 로직 측

### 4.1 이벤트 구동, 폴링 금지

보드는 입력이 있을 때만 변한다. 매 프레임 보드를 검사하지 말고, 이동이 확정된
순간에만 매치 판정·낙하·연쇄를 계산한다. 격자 게임에서 `update()` 마다 도는
루프는 거의 항상 설계 착오다.

### 4.2 더티 플래그

변경된 셀 목록만 추적해서 갱신·재렌더·판정을 그 셀들과 이웃으로 한정한다.
보드 전체 스캔은 초기화 때 한 번이면 충분하다. 매치-3 류에서도 방금 움직인
두 셀 주변만 검사하면 된다.

### 4.3 데이터 표현

- **1D 배열 + 정수 인코딩**: 셀 상태를 객체 배열 대신 숫자 배열로 들면 GC 부담과
  캐시 미스가 줄어든다.
- **비트보드**: 8x8 이하 보드에서는 셀당 1비트로 점유 여부를 들고, 이동 가능
  판정·매치 검사를 비트 연산(시프트 + AND)으로 처리하기도 한다. 체스 엔진에서
  온 기법이지만 소형 퍼즐에도 유효하다.

### 4.4 프레임당 할당 제로

드래그 콜백처럼 매 프레임 불리는 경로에서 새 배열·객체·클로저 생성을 피하고
임시 버퍼를 재사용한다. **모바일 프레임 드랍의 최대 원인이 GC 스파이크**다.
할당이 필요한 계산(범위 계산 등)은 §3.2 처럼 제스처 시작 시 1회로 몰아 둔다.

### 4.5 결정론적 로직

난수는 시드 기반으로, 로직은 부수효과 없이 만든다. 그 대가로 얻는 것:

- 리플레이·되감기(undo)를 상태 스냅샷 없이 입력 기록만으로 구현할 수 있다.
- 생성한 레벨이 실제로 풀리는지 **솔버로 자동 검증**할 수 있다
  (이 프로젝트의 `*_LevelGenerator.ts` 가 이 방식).
- 테스트가 흔들리지 않는다.

## §5 최적화 방법론 — 렌더링 측 (일반 엔진 기준)

### 5.1 오브젝트 풀링

타일·블록·이펙트는 생성/파괴하지 않고 풀에서 재사용한다. 격자 게임은 최대
오브젝트 수가 보드 크기로 **상한이 정해져 있어** 풀링과 궁합이 가장 좋은 장르다.
초기화 때 보드 크기만큼 만들어 두고, 이후에는 켜고 끄고 내용만 바꾼다.

### 5.2 정적/동적 분리

격자 배경·테두리·눈금은 한 번 그리고 건드리지 않는다(별도 레이어, 정적 배치).
움직이는 것만 매 프레임 갱신한다.

### 5.3 드로우 콜 배칭

타일이 같은 텍스처(스프라이트 아틀라스)를 공유하게 해 보드 전체를 드로우 콜
1~2개로 묶는다. 셀마다 다른 머티리얼을 쓰면 셀 수만큼 드로우 콜이 생긴다.

### 5.4 애니메이션은 보간으로

셀 이동은 위치 두 점 사이 lerp(+ easing)면 충분하다. 물리 시뮬레이션·리지드바디를
쓰지 않는다. 낙하 연출조차 "도착 셀은 즉시 확정, 화면만 가속 보간"이 표준이다.

## §6 이 프로젝트(Horizon Worlds Custom UI)에 적용할 때

Custom UI 보드는 §5 의 "스프라이트" 대신 UI 노드와 `Binding` 으로 그린다.
같은 원칙이 이렇게 번역된다.

| 일반 원칙 | Custom UI 에서의 형태 |
|---|---|
| 오브젝트 풀링 (§5.1) | UI 노드 트리를 초기화 때 보드 크기만큼 한 번 만들어 고정하고, 이후에는 내용(색·표시 여부)만 바인딩으로 바꾼다. 노드를 만들고 지우지 않는다 |
| 더티 플래그 (§4.2) | 셀마다 `Binding` 을 하나씩 두고 **변경된 셀의 Binding 만 `set`** 한다. 보드 전체 리렌더는 셀 수만큼 비용이 커진다 |
| 정적/동적 분리 (§5.2) | 격자 배경은 바인딩 없는 고정 노드로, 상태가 변하는 칸 내용만 바인딩으로 |
| 할당 제로 (§4.4) | 드래그 중 매 이벤트마다 `set` 하지 말고, 값이 실제로 바뀐 경우(칸 단위 스냅이면 칸이 바뀔 때)만 호출한다 |

프로젝트 고유의 제약과 해법은 별도 문서에 있다:

- `Pressable` 이 연속 좌표를 주지 않는 제약과 칸 단위 추종
  → `구현 사항/작업기록_2026-09-02_드래그_조작_시각_피드백.md`
- `initializeUI()` 트리 64kB 한도와 `DynamicList` 복제 제거
  → `구현 사항/버그수정_2026-09-02_보드패널_64kB_한도초과.md`
- 뗄 때 `onExit` 이 드랍 지점을 지우는 문제
  → `구현 사항/버그수정_2026-09-02_드래그_놓기_판정_실패.md`
- 기기별 안전 여백과 정사각 보드 규격
  → `구현 사항/작업기록_2026-09-02_기기별_화면_규격.md`

## §7 요약

격자 게임은 **"배열이 진실, 화면은 투영"** 한 문장으로 요약된다.

- 상호작용 = 좌표 변환 + 배열 조회 (콜라이더·레이캐스트 불필요)
- 고정축 이동 = 축 확정 → 범위 1회 계산·클램프 → 놓을 때 스냅 트윈 → 논리 즉시 갱신
- 최적화 = 이벤트 구동 + 더티 플래그 + 풀링 + 프레임당 할당 제로
- 물리 엔진, 레이캐스트, 매 프레임 폴링은 이 장르에서 거의 항상 불필요하다
