## §1 현재 구조 — "순간순간 스냅 판단"은 하지 않는다

드래그 퍼즐 넷은 모두 방법론 §3의 3단계 구조를 따르고, 무거운 판단은 드래그 중에
일어나지 않는다. 러시아워(`RushHour_DragController.ts`) 기준:

| 단계 | 시점 | 하는 일 | 비용 |
|---|---|---|---|
| 잡기 | 터치 다운 1회 | 히트박스 보정으로 말 선택 + 이 축의 이동 가능 범위 계산 (`recomputeRange`) | 유일한 충돌 검사 |
| 이동 | 좌표가 올 때마다 | `beginValue + delta` 를 미리 구한 범위로 **클램프만** | O(1) 산수 |
| 스냅 | 릴리즈 1회 | 가장 가까운 칸으로 반올림해 논리 이동 확정 | 1회 |

화면 갱신도 미리보기 칸이 실제로 바뀔 때만, 바뀌는 발자국 칸만 다시 그린다
(더티 필터 — 방법론 §4.2 적용 완료). 레이저·정렬·연결도 같은 패턴이다.

**즉, 계산이 무거워서 느린 것이 아니다.** 병목은 아래 두 곳이다.

### 1.1 이동 감지가 칸 단위다

칸마다 `Pressable` 이 있고, 손가락이 칸 경계를 넘어 다음 칸의 `onEnter` 가 와야만
한 번 반응한다. 칸 안에서 움직이는 동안은 이벤트가 0건이다. 오브젝트가 손가락을
연속으로 따라오는 것이 아니라 **칸 경계에서만 점프**하고, Custom UI 이벤트 자체의
플랫폼 지연(커뮤니티 보고 ~100-250ms)이 **칸 전환마다** 얹힌다. "뚝… 뚝…" 하고
끌리는 체감의 원인이다.

`Pressable` 콜백이 좌표를 주지 않는 제약 때문에 선택한 구조다
(`작업기록_2026-09-02_드래그_조작_시각_피드백.md`).

### 1.2 놓는 순간 전체 리페인트가 몰린다

릴리즈 한 번에 같은 이벤트 턴 안에서 전체 리페인트가 여러 번 돈다.

| 퍼즐 | 릴리즈 시 전체 리페인트 | 경로 |
|---|---|---|
| 러시아워 | 최대 3회 | `PIECE_MOVED` 구독 → 전체, `USB_DOCKED/UNDOCKED` → 전체, `onDragEnd` 자신 → 전체 |
| 레이저 | 2회 | `BEAM_UPDATED`(광선 재계산) → 전체, `onDragEnd` 자신 → 전체 |

프레젠터 diff 가 실제 바인딩 갱신은 걸러 주지만, 릴리즈 순간에 패치 생성·비교
~250회와 바인딩 갱신 burst 가 몰린다. "스냅되는 그 과정이 유독 느리다" 는 체감과
정확히 일치하는 지점이다.

## §2 참고한 2D 보드게임 인터랙션 UX 방법론

1. **직접 조작 (direct manipulation)** — 드래그 중인 오브젝트는 포인터를 픽셀
   단위로 1:1 추종한다. 논리는 밑에서 칸으로 양자화하되 화면은 연속이다.
2. **첫 피드백 100ms 이내** — 잡는 순간의 시각 반응이 조작감을 결정한다.
3. **논리 즉시 + 시각은 보간** — 릴리즈 시 논리 보드는 즉시 갱신하고, 화면만
   짧은 트윈(100~150ms ease-out)으로 칸 중심에 붙인다.
4. **입력과 렌더의 해상도 분리** — 입력은 이벤트 해상도로 받고, 렌더는 프레임
   해상도로 그린다. 입력 처리가 렌더 비용에 막히면 안 된다.
5. **릴리즈는 단일 커밋** — 놓는 순간의 판정·갱신은 한 번에 끝낸다.

현재 코드는 3·5의 논리 측은 지키지만, **1(연속 추종)이 플랫폼 제약에 막혀 있고
5의 렌더 측(단일 커밋)이 깨져 있다.**

## §3 개선 제안

### 제안 1 — 드래그를 연속 좌표 스트림으로 전환 (구조적, 효과 최대)

`InteractionInfo.screenPosition` 이 **0~1 정규화 화면 좌표**를 준다는 것을
확인했다 (`types/horizon_core.d.ts`, Focused Interaction 입력). 보드 사각형의
화면 위치는 코드가 정확히 알고 있으므로(짧은 변의 90% + 여백 5%,
`computeBoardSquare`) 변환은 곱셈 몇 번이다:

```
gridCol = (screenX * screenShort - boardLeft) / cellSide
gridRow = (screenY * screenShort - boardTop) / cellSide
```

**하이브리드 입력 구조**를 제안한다.

- 잡기: 지금처럼 칸 `Pressable` 의 `onPress` (어느 오브젝트인지는 칸이 이미 안다)
- 이동·뗌: `PlayerControls.onFocusedInteractionInputMoved / Ended` 스트림
  (기존 `PuzzleTouchRouter` — `Puzzle_HorizonBridge.ts` — 의 배관을 재활용)

기대 효과:
- 칸 경계를 기다리지 않고 **입력 이벤트 해상도로 연속 추종** (방법론 1 충족)
- 뗌이 `inputEnded` 로 확정되어, 기기에서 세 차례 보고된 **릴리즈 유실 문제의
  근본 해결** (Pressable release 가 어느 요소에도 배달되지 않는 케이스가 사라진다)
- 드래그 컨트롤러들은 이미 연속 좌표(실수 격자 좌표)를 받도록 설계되어 있어
  로직 계층 수정이 거의 없다

리스크와 검증:
- **Screen Overlay 위 터치가 Focused Interaction 이벤트로도 들어오는지**가
  관건이다. UI 레이어가 터치를 소비해 스트림이 오지 않을 수 있다.
  → 기기에서 로그로 확인하는 실험이 선행되어야 한다. 안 들어오면 현행
  칸 단위 경로를 폴백으로 유지한다 (두 경로가 같은 컨트롤러 API 를 쓰므로 공존 가능).
- Focused Interaction 모드 진입이 이동/점프 버튼을 숨긴다 — 퍼즐 전용 월드라
  오히려 적합하지만, 진입/이탈 시점(퍼즐 시작/종료)을 정해야 한다.

### 제안 2 — 릴리즈 리페인트 통합 (즉시 적용 가능, 스냅 지연 직접 해소)

같은 이벤트 턴에서 전체 리페인트를 1회로 코얼레싱한다. 방법은 둘 중 하나:

- (a) "이번 턴에 이미 전체를 그렸다" 플래그를 두고 세션 이벤트 구동 리페인트가
  그 턴에는 스킵하게 한다. `onDragEnd` 가 마지막에 플래그를 세우고 1회 그린다.
- (b) 세션 이벤트(`PIECE_MOVED`, `USB_DOCKED` 등) 구독에서 리페인트를 빼고,
  릴리즈 경로의 마지막 1회만 남긴다. 단, 드래그 없이도 그 이벤트가 나는 경로
  (리셋, 힌트 등)가 있는지 먼저 확인해야 한다 → (a)가 더 안전하다.

기대 효과: 러시아워 릴리즈 3회 → 1회, 레이저 2회 → 1회. 패치 생성·비교가
릴리즈 순간에서 2/3 사라진다.

### 제안 3 — 릴리즈에도 더티 필터 확장

이동 확정 시 실제로 바뀌는 칸은 **출발 발자국 + 도착 발자국 + 이동 축 라인**뿐이다
(다른 말·도착 포인트·바탕은 그대로다). 이동 중에만 쓰는 더티 필터
(`applyDragTransitionVisuals`)를 릴리즈 리페인트에도 적용한다.

- 결합/분리(점유 칸 2↔3 변화)와 레이저의 광선 재계산처럼 **영향 범위가 판 전체일
  수 있는 경우는 전체 리페인트를 유지**한다 - 광선은 어느 칸이든 바뀔 수 있다.
- 제안 2를 먼저 넣으면 릴리즈가 1회가 되므로, 그 1회를 좁히는 것이 이 제안이다.

### 제안 4 — 스냅 트윈 (지금은 비추천, 제안 1 이후 재검토)

방법론 3의 표준은 릴리즈 스냅에 100~150ms ease-out 트윈이지만, **칸 단위 렌더에서는
즉시 확정이 더 빠르게 읽힌다** (트윈을 넣으면 오히려 굼떠 보인다). 제안 1로 연속
추종이 구현되면 그때 "연속 위치 → 칸 중심" 트윈이 의미를 가지므로 함께 재검토한다.

### 제안 5 — 릴리즈 이벤트 안의 console.log 제거

`USB_DOCKED`/`PLACEMENT_REJECTED` 등 릴리즈 턴 안에서 도는 `console.log` 는
브리지를 동기로 건넌다. 소소하지만 공짜 절감이다. 디버깅용은 남기되 릴리즈
핫 패스 밖으로 옮긴다.

## §4 우선순위와 진행 방식

| 순서 | 제안 | 성격 | 근거 |
|---|---|---|---|
| 1 | 제안 2 (릴리즈 코얼레싱) | 안전·즉시 | 스냅 지연의 확실한 원인, 몇 줄 수정 |
| 2 | 제안 3 (릴리즈 더티 필터) | 안전·즉시 | 제안 2의 남은 1회를 더 좁힌다 |
| 3 | 제안 5 (로그 정리) | 안전·즉시 | 공짜 |
| 4 | 제안 1 (연속 좌표 스트림) | 실험 선행 | 조작감의 근본 개선. Screen Overlay 위에서 Focused Interaction 스트림 수신 여부를 기기에서 먼저 검증 |
| 5 | 제안 4 (스냅 트윈) | 보류 | 제안 1 성공 시에만 의미 |

검증 기준: 기기(모바일)에서 러시아워 말을 빠르게 왕복 드래그했을 때 끊김 체감,
그리고 놓는 순간 스냅까지의 지연 체감. Real-Time Metrics 의 스크립트 시간으로
릴리즈 프레임의 스파이크가 줄었는지 함께 본다.
