# 브라우저 드래그 데모 대비 Custom UI 파이프라인 비교 — 끊김은 로직인가 플랫폼인가

> 2026-09-18 작성. 사용자가 브라우저(DOM `pointer*` 이벤트)로 만든 드래그 모듈 데모 세 종
> (자유 드래그 · 격자 스냅 · 존 드롭)이 **끊김 없이** 움직이는 것을 확인하고, 우리 Custom UI
> 드래그와 무엇이 다른지, 끊김이 Custom UI 의 고질적 문제인지를 묻는 질문에 답한다.
> 데모 원본: `../../SampleHtml/DragModules/` (`game.ts`, `index.html`)
> 실험 도구: `DragLab_Panel.ts` (`../ScriptDesc/DragLab_Panel.md`)
> 선행 문서: `../구현 사항/작업기록_2026-09-05_브라우저_샘플_대비_드래그_경로_보정.md` (러시아워 샘플과의
> 로직 비교), `2026-09-07_Horizon_CPU_TypeScript_최적화_가이드_분석.md` (공식 한도)

**한 줄 답.** 드래그 **로직**은 이미 같다 — 데모의 산술을 우리 코드에 대응시키면 항목마다 1:1 로
있다. 남는 차이는 전부 **입력과 화면 사이의 파이프라인**이고, 브라우저에는 그 파이프라인이 없다.
그래서 "데모가 매끄럽다" 는 사실만으로는 우리 끊김이 플랫폼 고유인지 우리 사용법인지 가릴 수 없다.
가리는 실험은 DragLab 에 이미 있고(§3), 이번에 데모의 세 탭을 DragLab 에 그대로 옮긴 조합을 추가했다(§4).

---

## §1 로직 대응표 — 데모의 산술은 우리 코드에 전부 있다

| 데모 | 하는 일 | 우리 대응 | 판정 |
|---|---|---|---|
| `FreeFormDraggable.onPointerDown` | `dragOffset = pointer - position` | `DragLab.beginDrag`: `_grabOffset = centre - point` (부호만 반대) / `FocusDragDemo` 동일 / 퍼즐은 2026-09-05 보정으로 실제 터치 지점 기준 | 같음 |
| `onPointerMove` | `position = pointer - dragOffset`, 매 이벤트 `style.left/top` 쓰기 | I0(FI 절대좌표) + 즉시 반영(R0/R1/**R12**) | 같음 |
| `setPointerCapture` | 손가락이 요소 밖으로 나가도 그 요소가 계속 받는다 | Focused Interaction 스트림은 애초에 **화면 전체의 터치**를 스크립트에 준다. 잡기만 `started` 좌표로 판정한다. 오히려 더 강하다 | 같음(더 강함) |
| `GridSnapDraggable.dropAt` | **놓을 때만** `round((pos - origin) / cell)` + clamp, 그 칸 중심으로 이동 | DragLab `drop mode: grid snap` (같은 식) / 퍼즐 컨트롤러의 릴리즈 스냅 | 같음 |
| `ZoneDropManager.handleDrop` | 상자 **중심**이 존 사각형 안이면 존 중심, 아니면 잡은 자리로 복귀. CSS `transition 0.2s ease-out` | DragLab `drop mode: zone drop`: 같은 판정 + `Animation.timing(200ms, Easing.out(quad))` | 같음 |
| `style.left = \`${x}px\`` | 정수 px 를 매 이벤트 쓴다 | **R12** `Binding<number>` 에 `Math.round(x * 화면px)` | 같음 |
| 드래그 중 재계산 | 없음 (스냅·판정은 놓을 때 1회) | 같음 — 러시아워·레이저는 잡을 때 범위 1회, 이동 중 클램프만 | 같음 |

> 헷갈리기 쉬운 것 하나. DragLab 의 **R8(격자 칸 넘을 때만 set)** 은 데모의 격자 스냅과 다른 것이다.
> R8 은 *드래그 중* 화면 갱신을 줄이는 실험이고, 데모의 스냅은 *놓을 때* 한 번이다.
> 데모 2번 탭에 해당하는 것은 R8 이 아니라 `drop mode: grid snap` 이다.

**결론: 로직에서 바꿀 것이 없다.** 계산량은 두 쪽 다 이벤트당 덧셈·나눗셈 몇 번이다.

## §2 파이프라인 대응표 — 차이는 여기에만 있다

| 단계 | 브라우저 (데모) | Horizon Custom UI (우리) |
|---|---|---|
| 입력 도착 | OS → 브라우저 → **같은 스레드**의 JS 핸들러. `pointermove` 는 프레임마다 병합(coalesce) | 네이티브 터치 → **브릿지** → JS VM 의 `onFocusedInteractionInputMoved` (프레임당 1회, 최대 5손가락 `InteractionInfo[]` 배열이 매번 새로 만들어진다) |
| 화면 반영 | `style.left` 쓰기 → 같은 프레임의 레이아웃·페인트. 지연 0~1 프레임 | `Binding.set` → **브릿지** → ReactVR/redux 저장소 → 다음 프레임 커밋. 공식 문서: `World.onUpdate` 안의 변경은 다음 프레임, 그 밖의 콜백은 **최대 2 프레임** 뒤 |
| set 1회의 비용 | DOM 속성 하나 | "**패널의 키-값 저장소 전체**를 ReactVR 에 넘긴다" (Custom UI optimization). 키가 많은 패널일수록 비싸다 |
| 빈도 한도 | 없음 (프레임당 병합) | **로컬 프레임당 set 10회**, 콜백 2프레임당 1회 (공식). 넘으면 "droughts/bursts" — *밀렸다가 몰아서* 처리된다고 문서가 직접 경고한다 |
| 프로세스 경계 | 없음 | 갱신 1회마다 브릿지 **2~3회** (입력 1 + set 축당 1) |
| 보간 | CSS `transition` 을 컴포지터가 | `Animation.timing` 을 네이티브가 (직렬화되어 스크립트 없이 재생). **동등하다** |
| GC | V8 세대별 GC, 보통 1 ms 미만 | 스크립트 VM 의 GC 특성은 문서화되어 있지 않다. 매 프레임 배열·`Vec3` 할당이 쌓인다 |
| 최소 입력→화면 지연 | ~1 프레임 | ~2 프레임 이상 (72 fps 기준 약 28 ms) |

브라우저 데모가 매끄러운 이유는 이 표의 왼쪽 열이 전부 "없음/같은 스레드" 이기 때문이지, 로직이
달라서가 아니다. 반대로 우리가 "밀렸다가 순간이동" 을 보는 후보는 오른쪽 열의 세 곳이다.

1. **set 파이프라인의 drought/burst** — 문서가 그 증상을 그대로 적어 두었다. 플랫폼 특성이지만
   **회피 가능**하다 (스로틀 + 네이티브 보간 = R2/R4/R11).
2. **JS VM GC 정지** — 입력 배열·Vec3·문자열 할당이 프레임마다 쌓인다. 우리 코드의 할당을 줄이면
   완화되므로 **부분적으로 우리 몫**이다.
3. **네이티브 렌더/메인 스레드 히칭** — 스크립트와 무관. **회피 불가**, 기기·플랫폼 문제.

## §3 "고질적 문제인가" 를 가리는 방법 — 데모 비교로는 안 되고 DragLab 으로는 된다

데모는 파이프라인이 없으니 위 세 후보를 전혀 구분해 주지 않는다. 구분하는 장치는 DragLab 에 있다.

| 관찰 (DragLab) | 어느 후보인가 | 성격 |
|---|---|---|
| **R10(드래그 중 set 0회)** 도 멈추고 **펄스 막대**도 같이 멈춘다 | 3. 네이티브 히칭 | 플랫폼/기기. 우리가 할 수 있는 것이 없다 |
| R10 은 매끄럽고, R1/R12(즉시 set)만 멈춘다, 펄스는 계속 돈다 | 1. set 파이프라인 | 플랫폼 특성이나 **회피 가능** — R2/R11 로 넘어가 사라지는지 본다 |
| 멈추는 순간 `[VM] gap` 이 찍힌다 (어느 R 에서든) | 2. GC | 우리 몫. 드래그 중 할당을 줄인다 |
| `[input] gap` 만 찍힌다 | 입력 스트림 자체 | I1~I3 으로 바꿔 비교 |

즉 **"Custom UI 의 고질적 문제인가"** 에 대한 정직한 답은 "**R10 과 펄스 막대가 말해 준다**" 다.
R10 이 깨끗하면 고질적이라 부를 수 없다 — 우리가 set 을 너무 자주 보내는 것이고, 스로틀로 푼다.
R10 까지 멈추면 그때 비로소 플랫폼(또는 그 기기)의 문제다.

내 예상을 적어 두면(실측 전 추정), 2026-09-04 FocusDragDemo 의 "얼었다가 순간이동" 은 문서의
drought/burst 서술과 가장 닮았으므로 1번이 가장 유력하고, 그 다음이 2번이다. 3번이면 다른 월드의
Custom UI 도 같은 기기에서 같은 주기로 멈춰야 한다.

## §4 데모를 DragLab 에 옮긴 테스트 케이스

로직이 같다는 §1 의 주장을 실기에서 확인할 수 있도록, 데모의 세 탭을 DragLab 에 그대로 넣었다.

### 4.1 R12 `web port: px Binding<number>`

데모의 `style.left = \`${x}px\`` 를 문자 그대로 옮긴 렌더 경로다. 입력마다 화면 비율을 **정수 px**
로 환산해(`Math.round(x * _pixelsPerScreenX)`, 화면 좌표 배율은 `screenPixelRatio`) 일반
`Binding<number>` 두 개(`left`, `top`)에 set 한다. 기존 R1 과의 차이는 (a) AnimatedBinding 이 아닌
일반 Binding, (b) `%` 가 아닌 px, (c) 정수 반올림(Meta 공식 샘플 `UtilsUI.ts` 도 이렇게 한다) 이다.

### 4.2 `drop mode` (버튼 4행의 조절 항목)

| 값 | 데모 탭 | 놓을 때 |
|---|---|---|
| `free` | 1. 자유 드래그 | 놓은 자리 그대로 |
| `grid snap` | 2. 격자 스냅 | 5열 격자(칸 = 상자 크기)의 가장 가까운 칸 중심으로 200 ms ease-out |
| `zone drop` | 3. 존 드롭 | 상자 중심이 `Zone A`/`Zone B` 안이면 존 중심으로, 아니면 **잡은 자리로 복귀** (200 ms) |

격자와 존은 입력을 받지 않는 그림이다(`View` 만). 놓은 결과는 HUD 와 콘솔에 `drop: snapped to
[col 2, row 1]` / `landed in Zone A` / `outside: returned to origin` 으로 남고, 측정 키에도
`/ drop grid snap` 처럼 붙는다.

트윈은 AnimatedBinding 계열(L·T)에서만 걸린다. 일반 Binding(S·O·P)은 `Animation` 을 받을 수 없어
놓는 순간 바로 뛴다 — 브라우저의 CSS `transition` 에 해당하는 것이 그쪽에는 없다.

### 4.3 데모와 같은 조건의 조합

| 데모 | DragLab | 보는 것 |
|---|---|---|
| 자유 드래그 | I0 + **R12** + `drop free` | **로직이 데모와 완전히 같은 조합.** 여기서 멈추면 §2 의 파이프라인이다. R1(AnimatedBinding %)과 비교하면 px/일반 Binding 의 차이가 갈린다 |
| 격자 스냅 | I0 + R12 + `drop grid snap` (트윈까지 보려면 R1) | 놓는 순간 스냅 지연. 릴리즈 프레임의 `[VM] gap` |
| 존 드롭 | I0 + R1 + `drop zone drop` | 200 ms 트윈이 매끄러운가 — 네이티브 보간의 품질. 원위치 복귀 시 스크립트 관여 없음 |

권장 순서는 `../ScriptDesc/DragLab_Panel.md` 의 "권장 절차" 와 같고, 그 앞에 **I0 + R12 + free** 를
먼저 한 번 돌려 데모와의 체감 차이를 기록해 둔다.

## §5 이 비교에서 우리 로직 쪽으로 가져올 것

로직은 같으므로 가져올 산술은 없다. 다만 데모가 상기시키는 원칙 두 가지는 유효하다.

1. **드래그 중에는 판정하지 않는다** — 스냅·존 판정은 릴리즈 1회. 퍼즐 컨트롤러는 이미 그렇다.
2. **정수로 반올림해서 보낸다** — `Math.round` 한 px 는 손가락이 느리게 움직일 때 같은 값이 되어
   set 이 생략된다. DragLab 의 `round step` 이 같은 역할이며, 실제 퍼즐 패널에도 적용할 만하다.

파이프라인 쪽 결론(스로틀 Hz, 보간 방식)은 DragLab 실측 뒤에 `2026-09-04_드래그_반응속도_개선_제안.md`
의 제안 1·4 를 갱신하는 형태로 적는다.
