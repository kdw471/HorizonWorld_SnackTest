## 장르·레지스터
- 장르: 기술 문서 (내부 개발 문서 색인 README). 본문의 9할이 마크다운 표이고, 산문은 표의 "내용/설명" 셀과 절 도입부 인용 블록에만 있다.
- 격식: **한다체('-다' 평서 격식체)** — "~한다 / ~했다 / ~이다". 표 셀 상당수는 명사 종결("~던 문제.", "**전체의 기준 문서**")로 끝나는데, 이는 격식 혼재가 아니라 색인 표의 관습이다. **윤문은 한다체와 명사 종결 관습을 둘 다 유지한다(양방향 불변).**
- risk_band: medium (risk_score 4) / 번역투 간섭지수 0.124 — 낮음. **번역투(A 계열 어휘 패턴)는 이 글의 문제가 아니다.** 지배 패턴은 전부 구조·리듬 쪽이다.

## 지배 패턴 (겨냥 순서)

1. **E-2** 동일 종결어미·동형 문말 반복 — 이 글을 가장 강하게 지배한다. 두 개의 큰 표가 각각 **하나의 문말 틀에 전량 고정**되어 있어, 행을 바꿔도 같은 문장을 다시 읽는 느낌을 준다.
   · 근거: 「목적별 진입점」 표 좌열 — "어떻게 ~는지"가 7회("퍼즐 하나가 어떻게 월드에서 도는지", "퍼즐 화면이 어떻게 배치되는지", "드래그가 화면에 어떻게 보이는지", "모바일/VR 에서 화면이 어떻게 맞춰지는지", "특정 퍼즐의 기획 데이터가 어떻게 들어갔는지", "보드 화면이 어떻게 배치되는지", "드래그가 왜 끊겨 보이는지"), "~안 될 때 / ~않을 때"가 5회. 「구현 사항」 표 — 설명 셀 첫 문장이 **"~던 문제."로 13회 연속** 시작한다("고정되지 않던 문제", "똑같아 보이던 문제", "놓이지 않던 문제", "보이지 않던 문제", "전부 잠기던 문제", "보이지도 눌리지도 않던 문제" …). 정량 앵커 lexical_diversity z=-1.77이 이 틀 반복의 결과다.
   → 처방: 두 틀을 **전부** 깨지 말고 각 표에서 3~4행만 다른 어형으로 바꾼다 — "~던 문제" → "~가 안 됐다 / ~가 어긋났다 / (명사구 단독)", "어떻게 ~는지" → "~의 구조 / ~를 어디서 고치나". 색인의 스캔성이 반복에서 나오므로 전면 변주는 과윤문이다.

2. **A-18** 긴 좌향 관형절 수식 (관형구 3중 이상) — 설명 셀 대부분이 6~12어절짜리 관형절을 하나의 명사 머리(문제·법·이유·증거·구멍·해결) 앞에 통째로 얹는다. 문장이 끝까지 가야 무엇에 관한 말인지 드러나 읽는 속도를 깎는다.
   · 근거: "칸 `Pressable` 의 release 와 스트림의 `inputEnded` 가 서로에게 마감을 미루던 구멍", "밀착 좌표를 판의 바깥 변으로 가정하던 계산", "`panelHeight` 가 좌표 해상도를 정한다는 가정이 실기에서 반증된 증거", "덧칠 리페인트가 `Binding.set` 을 수십 번 내는 것을 막는 법", "`showLayoutProbe` 로 `flex`·`%`·`aspectRatio` 가 어디까지 동작하는지 재는 법". 명사 머리 "~ 이유"만 6회("택하지 않은 이유" 2회, "분리한 이유", "불가능한 이유", "flush 하는 이유", "신경 쓰지 않아도 되는 이유").
   → 처방: 가장 긴 것부터 5~6개를 **머리 명사를 앞으로 빼고 관형절을 뒤에 서술절로 푼다** — "…미루던 구멍" → "구멍이 있었다. release 와 `inputEnded` 가 서로에게 마감을 미뤘다". 식별자·수치는 그대로 옮긴다.

3. **C-11** 연결어미 뒤 쉼표 — 정량 지표 중 가장 높은 축(ending_comma_rate z=+1.86, 값 0.1875). "-고," "-며," "-지만," 뒤에 습관적으로 쉼표가 붙어 한 셀 안에서 호흡이 기계적으로 끊긴다.
   · 근거: "도착 포인트에서 거꾸로 풀도록 바꾸고, **닿기만 해도 꽂히게** 했다", "마지막으로 올라가 있던 진짜 칸을 따로 기억하고, 격자 상자의 release 는 …", "칸마다 주는 `tint` 로 그림을 물들이며(…), 방향이 있는 부품은 **그림째 돌린다**", "코드에서 걷어내 이 폴더로 옮겼다" 계열 연결 구문 전반.
   → 처방: 연결어미 직후 쉼표를 제거하거나(기본), 절이 길어 호흡이 필요하면 쉼표 대신 **문장을 끊는다**. 열거 항목을 나누는 쉼표(A·B·C)는 건드리지 않는다.

4. **C-4** 셀 첫 문장 요약 공식 — 모든 설명 셀이 예외 없이 "① 한 문장 요약(문제/대상) → ② 굵게 강조한 핵심 → ③ 쉼표로 이어붙인 부연 열거"라는 **동일 3단 골격**을 반복한다. 셀 하나하나는 잘 쓰였는데 154줄 전체가 같은 금형으로 찍혀 나온 인상을 만든다. comma_segment_length z=+1.88(절 평균 8.3어절)은 ③ 구간이 길게 늘어난 결과다.
   · 근거: "'모바일에서 전체적으로 너무 작다' 의 해결. **보드 메인 패널을 직사각형(화면 가로 90%)으로**, 그 안의 **칸은 언제나 정사각형**, 트레이 부품은 **화면 아래 절반의 20% 이상**으로 두고 넘치면 …" / "트레이 오브젝트가 보이지도 눌리지도 않던 문제. **`DynamicList` 안에서는 … 높이 0** 이었다(…). 슬롯 8개를 …" — 두 셀의 골격이 완전히 같다.
   → 처방: 긴 셀 4~5개에서 ③의 쉼표 사슬을 2문장으로 나누거나, 요약 문장 없이 **핵심부터 바로 시작**하게 바꿔 골격을 어긋내다. 행 개수·열 개수·정보량은 그대로 둔다.

5. **C-10** 헤딩 부제 공식 "X — Y" — `###` 절 제목 **5개가 5개 모두** "라벨 — 부제" 대시 형식이다. 콜론 변종과 같은 기제이며, 자동 생성된 목차처럼 보이게 만드는 직접적 원인이다. 셀 안에서도 같은 대시가 동격 부연으로 반복된다(**J-3** 동반).
   · 근거: "### 가이드 — 지금 따라 하는 절차서", "### ScriptDesc — 스크립트에서 걷어낸 주석", "### 설계 — 구조와 방향", "### 구현 사항 — 현황과 이력", "### 데이터 테이블 구조 — 기획 CSV 적용 결과". 셀 내 대시: "**`EBoardCellGlyph`** - 광선을 되돌리는 변에 …", "**`PuzzleUI_Layout`** - 좁은 쪽에 맞춘 정사각형 …", "**스냅 판단은 순간순간 하지 않는다** - 병목은 …", "**`UINode.if` 로 마운트를 가른다** - 안 쓰는 퍼즐에서 …".
   → 처방: **헤딩 레벨과 절 순서는 절대 건드리지 않는다.** 부제만 손대되 2~3개만 — 부제를 떼어 라벨 단독으로 두거나 부제를 자연 어구로 흡수한다. 셀 안 " - " 부가설명은 2~3곳에서 마침표로 끊는다.
